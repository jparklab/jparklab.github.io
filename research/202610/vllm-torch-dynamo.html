TL;DR

  • Dynamo is the front end of torch.compile. It reads a Python function’s bytecode, records the tensor ops into an FX graph, and hands that graph to a backend.
  • vLLM uses Dynamo for one thing: trace the model’s forward once, as one full graph, dynamic only in the token count. Everything after that (splitting, Inductor, caching, CUDA graphs) is vLLM’s own backend, VllmBackend.
  • vLLM turns off the part of Dynamo that makes it safe for general code: guards. After the first trace, Dynamo never runs again. That keeps the serving path free of recompiles, but it means vLLM is betting that the traced graph is valid for every batch size.
  • The rules model authors must follow (no graph breaks, no branching on token count, attention hidden in a custom op, no buffer mutation in forward) all fall out of that bet.

1. What Dynamo does (the parts that matter here)

  1. Frame hook. torch.compile(fn) installs a CPython frame-evaluation hook (PEP 523). When fn’s code object is about to run, Dynamo intercepts it.
  2. Symbolic bytecode execution. Dynamo interprets the bytecode with fake tensors. Tensor ops go into an FX graph. Python control flow, attribute lookups, and calls to other Python functions are evaluated at trace time and inlined (InliningInstructionTranslator). The result is straight-line tensor code.
  3. Guards. Every assumption it made while tracing (a tensor’s dtype, a dim being ≥ 2, a config attribute’s value, x.size(0) > 10) becomes a guard. Next call: guards pass → reuse; any fails → retrace (a recompile).
  4. Graph breaks. Code it cannot trace (unsupported Python, data-dependent control flow, some C extensions) splits the function into several graphs with eager Python in between. fullgraph=True turns a graph break into an error.
  5. Bytecode rewrite. Dynamo emits new bytecode that unpacks the module’s tensors and calls the compiled graph, and caches it on the original code object.
  6. Backend. The FX graph plus example (fake) inputs go to a backend callable backend(gm, example_inputs) -> callable. Normally that is Inductor. In vLLM it is VllmBackend.

Dynamic shapes. mark_dynamic makes a dim a backed symbol: it has a real hint, can be guarded on, and is specialized for 0/1 (so a backed symbol implies ≥ 2). mark_unbacked makes an unbacked symbol: never guarded, never 0/1-specialized, but a branch on its value can raise a data-dependent error.

2. Call path in vLLM

@support_torch_compile class LlamaModel(nn.Module)        decorators.py
  └─ __call__ (first call, from profile_run's _dummy_run)
       ├─ mark_dynamic / mark_unbacked on dim 0 of input_ids, positions, …
       ├─ patch InliningInstructionTranslator.inline_call_  → record traced files
       └─ TorchCompileWithNoGuardsWrapper.__call__           wrapper.py
            └─ torch.compile(forward, fullgraph=True, dynamic=False,
                             backend=VllmBackend, guard_filter_fn=skip all)
                 └─ Dynamo traces forward → FX graph
                      └─ VllmBackend(graph, example_inputs)  backends.py
                           ├─ hash config + env + traced source → cache dir
                           ├─ split_graph at attention custom ops
                           ├─ Inductor-compile each piece (PiecewiseBackend)
                           └─ return VllmSerializableFunction (+ CUDA-graph wrapper)

The first trace happens during memory profiling (vllm/v1/worker/gpu_worker.py:641 determine_available_memory → profile_run → _dummy_run) with max_num_batched_tokens tokens. Later warmup and CUDA-graph capture runs reuse the same compiled function. No request ever triggers a compile; that is a stated design goal in docs/design/torch_compile.md.

3. The pieces, one by one

3.1 @support_torch_compile (vllm/compilation/decorators.py)

  • It is a class decorator on the inner model (e.g. LlamaModel, not LlamaForCausalLM), so the LM head and sampler stay outside the graph.
  • It appends TorchCompileWithNoGuardsWrapper to the class’s bases (decorators.py:367) and wraps __init__ and __call__.
  • Dynamic dims. dynamic_arg_dims names which arguments have a dynamic dim. If omitted, it is inferred from type hints: every torch.Tensor / Optional[torch.Tensor] / IntermediateTensors gets dim 0. Llama declares them all with one shape id, {0: "b"} (vllm/model_executor/models/llama.py:337), so with unbacked shapes they share a single symbol. _mark_dynamic_inputs (decorators.py:445) calls mark_dynamic or mark_unbacked depending on DynamicShapesConfig.type.
  • An argument that is None must always be None. With guards dropped, Dynamo will not notice it flipping.
  • Traced-file tracking. It monkeypatches InliningInstructionTranslator.inline_call_ during tracing (decorators.py:652) to record every source file Dynamo inlines. Those files’ contents go into the compile cache key (see 3.3). Editing layernorm.py invalidates the cache; editing a file that is only called inside a custom op does not.
  • Compile-time trims. It disables enable_cpp_symbolic_shape_guards (decorators.py:664) because the guards are thrown away anyway.
  • Re-entrancy. If torch.compiler.is_compiling() is true (a caller up the stack is already compiling, e.g. TPU), it just calls forward (decorators.py:537).

3.2 TorchCompileWithNoGuardsWrapper (vllm/compilation/wrapper.py)

This is where vLLM changes how Dynamo behaves.

  • torch.compile(..., fullgraph=True, dynamic=False, ...) (wrapper.py:169). fullgraph=True turns any graph break into an error. dynamic=False stops Dynamo from making extra dims dynamic on its own after a recompile; only the dims marked explicitly are symbolic.
  • Guard dropping. For every mode except STOCK_TORCH_COMPILE, guard_filter_fn is set to torch.compiler.skip_all_guards_unsafe (wrapper.py:143), or a lambda returning all False on older torch. The compiled code runs for any input without checking anything. The opt-in evaluate_guards (requires VLLM_USE_BYTECODE_HOOK=0) keeps only SHAPE_ENV guards and wraps later calls in set_stance("fail_on_recompile") (wrapper.py:216), so a violated shape assumption raises an error instead of silently retracing.
  • Bytecode hook (VLLM_USE_BYTECODE_HOOK=1, the default). It registers torch._dynamo.convert_frame.register_bytecode_hook (wrapper.py:179) to capture the bytecode Dynamo emits for forward. After the first call it swaps forward.__code__ for that bytecode (_dispatch_to_compiled_code, wrapper.py:294) and calls forward directly. This skips Dynamo’s frame hook and cache lookup on every step. It relies on Dynamo keeping the rewritten code’s args, cell vars, and free vars identical to the original.
  • Buffer-mutation check. If the rewritten bytecode references update (Dynamo’s way of writing back to nn.Module buffers) and CUDA graphs are on, it raises an error (wrapper.py:273). A buffer write inside a captured CUDA graph would replay stale data.
  • _compilation_context raises cache_size_limit to 2048 (wrapper.py:45). Each new backend instance can count as a recompile, and multimodal models create several.

3.3 VllmBackend (vllm/compilation/backends.py:1048)

Dynamo calls this exactly once per compiled module (assert not self._called, backends.py:1201).

  • Cache key = hash(env factors, vllm_config.compute_hash(), compiler/torch config hash, contents of every traced file) (backends.py:1083). Output goes to ~/.cache/vllm/torch_compile_cache/<hash>/rank_<r>_<dp>/, plus computation_graph.py (the split FX graph) and transformed_code.py (Dynamo’s bytecode decompiled with depyf).
  • Splitting. split_graph (backends.py:576) cuts the FX graph at splitting_ops, which default to the attention-like custom ops listed in CompilationConfig._attention_ops (vllm/config/compilation.py:768). A Llama graph splits into three unique pieces (pre-first-attention, the repeated inter-attention layer, and post-last-attention). Identical pieces share one Inductor artifact.
  • Compile everything up front. PiecewiseCompileInterpreter runs the split graph on fake inputs and compiles each piece for the general symbolic shape and for every compile_sizes / compile range, before returning.
  • 0/1 specialization patch. With evaluate_guards + backed shapes, it rewrites symbol ranges whose lower bound is 2 back to 0 (backends.py:1289), so the kept guards do not reject batch size 1.

3.4 Custom ops: how vLLM keeps Dynamo out

Attention touches the KV cache, block tables, and backend-specific metadata, none of which Dynamo should trace. vLLM wraps it in torch.ops.vllm.unified_attention_with_output, registered with direct_register_custom_op (vllm/utils/torch_utils.py:1059) with a fake impl. Dynamo treats the op as opaque and only needs the fake impl to know the output shape (same as the query). Attention metadata comes from the global forward context, not from arguments, so it never becomes a graph input.

This custom-op boundary serves three purposes at once: 1. Dynamo can capture the model as one full graph. 2. split_graph uses it as the cut point. 3. Piecewise CUDA graphs run the attention op eagerly between captured pieces. That is why the op takes its output buffer as an argument: the allocation stays inside the captured graph.

The same trick is the documented fix for a token-count branch you cannot remove: move it into a custom op (docs/design/debug_vllm_compile.md).

3.5 AOT compile (VLLM_USE_AOT_COMPILE, default on for torch ≥ 2.10 with the cache enabled)

  • Instead of Dynamo tracing at runtime, torch._dynamo.config.enable_aot_compile produces a serializable compiled function, including Dynamo’s output (decorators.py:705). It is saved under torch_compile_cache/torch_aot_compile/<hash>/rank_*/model.
  • On the next start, _try_load_aot_compiled_fn (decorators.py:596) loads it with torch.compiler.load_compiled_function and calls disable_guard_check(). Dynamo does not run at all on a warm start. This is the main cold-start win over the older cache, which cached only Inductor output and still re-ran Dynamo.
  • The AOT hash cannot include traced files (they are unknown until Dynamo runs). Instead, on load it checks the source files recorded in the artifact (_verify_source_unchanged).
  • VLLM_USE_MEGA_AOT_ARTIFACT (default on for torch ≥ 2.12) goes further and stores the split graph plus all piece artifacts as one blob, so loading skips re-splitting.

4. After Dynamo: splitting, Inductor, caching, CUDA graphs

Dynamo hands VllmBackend one FX graph of the model’s forward, with the token count as a symbolic size s0. These four steps turn that graph into what runs on each serving step. All of it happens once, during startup warmup.

4.1 Splitting: cut the graph at attention

Why it’s needed. Attention is the only part of a layer that depends on the batch’s makeup: KV-cache block tables, prefill vs. decode, per-request lengths. Everything else (norms, QKV/MLP matmuls, RoPE, activations) works token by token and only cares how many tokens there are. Splitting separates the two kinds of work so each can be handled differently.

How it works. split_graph (vllm/compilation/backends.py:576):

  • It walks the graph’s nodes in order and starts a new subgraph id at every splitting op. These are the opaque custom ops in CompilationConfig._attention_ops (vllm/config/compilation.py:768): vllm::unified_attention_with_output, the MLA variant, mamba and linear-attention ops, and others. Each splitting op gets a subgraph of its own, and consecutive splitting ops stay together.
  • Some cleanups keep the pieces compilable. _decompose_size_nodes rewrites x.size() into one size call per dimension, because AOTAutograd can’t accept a torch.Size tuple as an input or output at a cut. A getitem stays in the same piece as the tuple it indexes. A piece that would hold nothing but a torch.empty is merged into the previous piece, so no CUDA graph gets captured for an empty piece.
  • torch.fx.passes.split_module(..., keep_original_order=True) then builds a parent graph module that calls submod_0, submod_1, … in order. Keeping the original order matters because the attention ops write into an output buffer, and reordering around those writes would change the results.

Result for Llama with N layers. The pieces are: everything before the first attention, attention, the inter-attention block (o_proj → residual → norm → MLP → norm → QKV → RoPE) repeated N−1 times, attention, and the final norm. Only 3 of these are distinct non-attention graphs, so Inductor reuses one artifact for the middle pieces. That’s why the cache log shows the 1st and 15th graphs with the same key.

Alternative. With use_inductor_graph_partition=True, vLLM doesn’t split the FX graph itself and leaves the partitioning to Inductor (backends.py:1207).

4.2 Inductor: compile each piece into Triton kernels

PiecewiseCompileInterpreter runs the split graph on fake tensors. For each non-attention piece it creates a PiecewiseBackend (vllm/compilation/piecewise_backend.py), and that backend compiles the piece right away.

Compile ranges. A piece is compiled once per range of token counts, not once per batch size.

  • The default is a single range, [1, max_num_batched_tokens], compiled with symbolic shapes.
  • Some fusion passes add extra cut-points. For example, all-reduce+RMSNorm fusion only pays off below a token threshold, so it adds a boundary at that threshold (vllm/config/vllm.py:2643).
  • Each entry in compile_sizes adds a single-size range. That piece is then compiled with concrete shapes, and max_autotune / coordinate-descent tuning can be turned on for it (set_inductor_config, compiler_interface.py:772).
  • At runtime, PiecewiseBackend.__call__ reads the token count from the piece’s inputs and picks the entry: an exact size if there is one, otherwise the range that contains it.

Compiler choice (make_compiler, backends.py:97):

  • The default is InductorStandaloneAdaptor, which wraps torch._inductor.standalone_compile (VLLM_USE_STANDALONE_COMPILE=1). It produces artifacts that can be serialized.
  • InductorAdaptor is the older compile_fx path. It hooks Inductor’s FX-graph cache: it swaps in an AlwaysHitShapeEnv so cache lookups never fail on guards that vLLM drops anyway.
  • backend=eager → EagerAdaptor, which skips Inductor. That’s useful for isolating bugs.

Inside Inductor:

  1. AOTAutograd functionalizes the graph: in-place ops become pure ops, mutations become explicit copies.
  2. Ops are decomposed to aten/prims.
  3. vLLM’s custom passes run. These are the main reason to use vLLM-compile rather than stock torch.compile. The pre-grad slot gets VllmIRInplaceFunctionalizationPass. The post-grad slot gets PostGradPassManager (vllm/compilation/passes/pass_manager.py), which pattern-matches multi-op sequences and replaces them with hand-written fused CUDA kernels. Fusions include RMSNorm+quant, SiLU-mul+quant, all-reduce+RMSNorm (FlashInfer), QK-norm+RoPE, RoPE+KV-cache write, and attention+output quant, plus no-op elimination and a functionalization fixup. Which passes run is set by pass_config and the -O level. Inductor’s own fusion can’t do these, because the target kernels are external.
  4. Inductor schedules the remaining elementwise and reduction ops, fuses them, and generates Triton kernels. Matmuls go to cuBLAS by default, or to Triton templates when autotuning a fixed size.
  5. Output is a Python wrapper that launches the kernels in order.

The whole compile is finished before VllmBackend returns. No range is compiled lazily later (compile_all_ranges).

4.3 Caching: never compile the same thing twice

Layer Key Location What a hit skips
vLLM compile cache sha256(env factors, vllm_config.compute_hash(), torch/Inductor config hash, contents of every file Dynamo traced) ~/.cache/vllm/torch_compile_cache/<hash>/rank_<r>_<dp>/<prefix>/ Inductor for each piece
AOT artifact Same factors minus traced files (unknown before Dynamo runs). Source files are checked on load instead (_verify_source_unchanged) …/torch_aot_compile/<hash>/rank_*/model Dynamo and Inductor. Loaded with torch.compiler.load_compiled_function + disable_guard_check()
Inductor / Triton caches Inductor’s own FX-graph hash; Triton kernel hash inductor_cache/ under the vLLM dir, TRITON_CACHE_DIR Kernel codegen and Triton → PTX/cubin compile

Inside the compile-cache directory:

  • vllm_compile_cache.py: a Python literal (read with ast.literal_eval, never eval) that maps (range, graph_index, compiler_name) to an Inductor handle (backends.py:176). On startup, CompilerManager.compile checks this first and calls compiler.load(handle) on a hit.
  • cache_key_factors.json: the raw factors behind the hash. Diff two of these to find out why the cache missed.
  • computation_graph.py and transformed_code.py: debug dumps of the split graph and Dynamo’s rewritten bytecode.

Mega artifact. On by default with torch ≥ 2.12. It bundles the split graph and every piece’s serialized Inductor output into one blob, so a warm start doesn’t re-split the graph or rebuild each piece’s backend.

Points to know:

  • The cache is per rank, and the hash includes parallel config. Changing TP or DP size misses.
  • Code that runs only inside a custom op isn’t traced by Dynamo, so it’s not in the key. Edit an attention backend and you may load stale artifacts. Use VLLM_DISABLE_COMPILE_CACHE=1 in that case.
  • You can copy the whole torch_compile_cache directory, plus TRITON_CACHE_DIR, to other machines to cut cold-start time.

4.4 CUDA graphs: remove CPU launch overhead

The problem. A decode step for a small batch might launch about 1,000 tiny kernels. Python plus the kernel-launch API can take longer than the GPU work itself. A CUDA graph records a sequence of kernel launches with fixed pointers and shapes, then replays the whole sequence with one call.

The constraint. A captured graph is frozen: same input addresses, same shapes, same control flow. So vLLM:

  1. Captures one graph per batch size in cudagraph_capture_sizes. The default is [1, 2, 4, 8, 16, …, 248] in steps of 8, then steps of 16 up to min(2·max_num_seqs·decode_query_len, 512) (1024 on datacenter Blackwell) (vllm/config/vllm.py:2392).
  2. Pads each batch’s token count up to the next captured size. Batches larger than the biggest size run without a CUDA graph.
  3. Uses fixed input buffers. make_copy_and_call (backends.py:59) copies the runtime input_ids and positions into persistent buffers before each call, so the graph always reads from the same addresses. Intermediate buffers live in a shared CUDA-graph memory pool.

Modes (CUDAGraphMode, vllm/config/compilation.py:53):

  • PIECEWISE. wrap_with_cudagraph_if_needed wraps each non-attention piece in a CUDAGraphWrapper. Attention runs eagerly between the replays, so it can handle any mix of prefill and decode. This is why attention takes its output buffer as an argument: the allocation stays inside a captured piece and only the kernel call runs eagerly.
  • FULL. One wrapper around the whole model captures attention too. This is fastest, but only works for attention backends that support graph capture, and usually only for uniform batches (every request has the same query length, e.g. pure decode).
  • FULL_AND_PIECEWISE (the default with piecewise compilation): full graphs for uniform decode batches, piecewise for mixed or prefill batches. FULL_DECODE_ONLY: full graphs for decode, eager for everything else.

Dispatch. The two wrapper levels are nested: the outer FULL wrapper sits around the model, and the inner PIECEWISE wrappers sit around each piece.

  • Before each step, CudagraphDispatcher builds a BatchDescriptor(num_tokens, uniform) for the padded batch.
  • It picks a runtime mode in priority order FULL > PIECEWISE > NONE, based on which keys were captured, and writes the choice into the forward context.
  • Each CUDAGraphWrapper.__call__ (vllm/compilation/cuda_graph.py:235) checks the forward context. If the chosen mode isn’t its own, it just runs the code it wraps, so exactly one level is active.

Capture and replay.

  • Capture happens during warmup _dummy_runs, after the compile is done. Garbage collection and empty_cache are patched to no-ops during capture, because otherwise they’d run once per piece (about once per layer) and make capture very slow.
  • Outputs are kept as weak references to save memory.
  • Replay is entry.cudagraph.replay(), which returns the output tensors stored at capture. In debug mode it also asserts that input addresses haven’t changed.

4.5 How the four fit together

  • Splitting decides what can be captured as a CUDA graph (everything except attention).
  • Inductor makes those pieces faster.
  • Caching saves the time Dynamo and Inductor took.
  • CUDA graphs remove the cost of launching the many small kernels left over.

The design doc’s Llama example shows the split: Inductor compiles 3 unique pieces, and with piecewise CUDA graphs, roughly one graph is captured per piece per capture size.

5. Compilation modes

-cc.mode Name What Dynamo does
0 NONE Not used. Eager.
1 STOCK_TORCH_COMPILE model.compile(fullgraph=True) with normal guards and recompiles. The decorator steps aside.
2 DYNAMO_TRACE_ONCE One trace, guards dropped, but no VllmBackend (plain backend).
3 VLLM_COMPILE (default) One trace, guards dropped, VllmBackend: split, Inductor, passes, cache, piecewise CUDA graphs.

--enforce-eager turns off both compile and CUDA graphs. -cc.backend=eager keeps Dynamo and splitting but skips Inductor, which is the quickest way to tell a Dynamo problem from an Inductor problem.

6. Dynamic-shape modes (-cc.dynamic_shapes_config.type)

Mode Symbol Guard risk Cost
backed (default) mark_dynamic Guards get added and then silently dropped. Fast, but unsound if one mattered. none
backed_size_oblivious backed + backed_size_oblivious=True Fewer 0/1 specializations in framework code. Experimental. small
unbacked mark_unbacked with hint_override No guards by construction. Branches may raise data-dependent errors. evaluate_guards is rejected because there are no guards to check. can miss optimizations, e.g. extra contiguous() clones

shape_invariants on the decorator lets a model add torch._check(...) relations (for example input_ids.size(0) == inputs_embeds.size(0)) so unbacked mode does not hit data-dependent errors.

7. Rules this imposes on model code

  1. No graph breaks in forward. fullgraph=True makes them errors. Typical causes: unsupported Python, print/logging, .item(), .tolist(), calling into non-traceable C extensions.
  2. No Python branching on the token count (if x.size(0) % 128 == 0). With guards dropped, whichever branch the profiling-run batch took is baked in for all sizes. Symptoms: wrong output, illegal memory access, ConstraintViolationError. Check tlparse compilation_metrics for constraints on the batch symbol.
  3. Everything that isn’t a dynamic input must stay constant for the model’s lifetime: config values, None-ness of optional args, module attributes read in forward. Dynamo turned them into constants, and nothing re-checks them.
  4. No writes to nn.Module buffers in forward when CUDA graphs are on (enforced by the bytecode hook).
  5. Opaque or stateful kernels go behind a custom op with a fake impl.
  6. Code reached only through custom ops is not in the cache key. Edit a kernel wrapper and you may need VLLM_DISABLE_COMPILE_CACHE=1.

8. Debugging toolkit

  • TORCH_TRACE=<dir> + tlparse <file> gives the full Dynamo/Inductor log, graph breaks, guards, and the split graph (vllm_piecewise_split_graph).
  • <cache>/transformed_code.py holds Dynamo’s rewritten forward and <cache>/computation_graph.py holds the split FX graph. Use compile_cache_save_format=unpacked to get readable Inductor code too.
  • VLLM_LOGGING_LEVEL=DEBUG lists traced files and reports the “Dynamo bytecode transform time”.
  • To isolate a failure, turn off one layer at a time: -cc.mode=0 / -cc.backend=eager / -cc.cudagraph_mode=NONE / --enforce-eager.

9. Takeaways / open questions

  • vLLM uses Dynamo as a one-shot graph capturer, not as a JIT. Its main value is “turn Python model code into an FX graph without making people write graph code”. Guards, the recompile cache, and the runtime frame hook are all turned off or bypassed.
  • The guard-dropping bet is the main correctness risk. evaluate_guards and unbacked are the two hedges. It is worth watching whether unbacked becomes the default as PyTorch reduces data-dependent errors. The Llama decorator still has mark_unbacked_dims commented out with TODO[#32068]: Investigate recompilation.
  • The bytecode-hook trick (swapping forward.__code__) depends on undocumented Dynamo internals (it walks stack frames to find convert_frame._compile). AOT compile looks like the path that replaces it.
  • Follow-ups worth a separate dig: what each fusion pass in vllm/compilation/passes/ matches and which -O level turns it on, vLLM IR (docs/design/vllm_ir.md), and attention-backend CUDA-graph support levels (docs/design/cuda_graphs.md).
