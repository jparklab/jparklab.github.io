vLLM throughput depends mostly on how many sequences decode together in each engine step, and that number is capped by the GPU memory left for the KV cache (the stored attention keys and values of running requests). Current V1 releases already enable most per-step efficiency features by default, so tuning is two jobs. First, buy KV headroom cheapest-first: raise memory utilization, cap context length, move weights to FP8 (NVFP4 on Blackwell where kernels and accuracy allow), test an FP8 KV cache for long contexts, and prefer replicas over sharding while each replica keeps a full batch. Second, sweep the two batching knobs against a latency target on production-like traffic. Speculative decoding, KV offload and large token budgets help in some regimes and hurt in others, so each is settled by an A/B benchmark, not by a rule.

1. What Limits vLLM Throughput

1.1 Two phases, one batch

Every request passes through two phases. Prefill processes the whole prompt in one large matrix multiply and is compute-bound. Decode produces one token per request per step. Each step streams all weights plus the request’s KV cache from high-bandwidth memory (HBM) for very little arithmetic, so it is memory-bandwidth-bound [1, 2]. Batching fixes this: 64 requests sharing one weight load split its cost 64 ways. Because vLLM’s continuous batching admits and retires requests at every step, the question is how large the decode batch can grow. PagedAttention, the design behind vLLM, found that earlier systems used only 20.4-38.2% of reserved KV memory for real tokens [3]. Paging the cache in fixed-size blocks removed that waste and gave 2-4x throughput at equal latency [3].

1.2 A worked memory budget

One token’s KV footprint is 2 (key and value) × layers × KV heads × head size × bytes per element [2]. For Llama-3.1-8B (32 layers, 8 KV heads, head size 128, BF16) that is about 128 KiB. An 80 GB H100 at the default --gpu-memory-utilization of 0.92 gives vLLM about 74 GB [4]. Minus 16 GB of weights and a few GB for activations and CUDA graphs, roughly 50 GB remains: about 380,000 tokens, or 190 concurrent 2,000-token requests. An FP8 KV cache roughly doubles that, and FP8 weights free another 8 GB. This is arithmetic, not a benchmark, but it shows why most levers below buy the same KV blocks at different prices.

1.3 The knee and the host

Past a saturation batch size the step turns compute-bound: step time grows with batch, so per-user latency rises while throughput flattens [2]. Long contexts and mixture-of-experts (MoE) models, which activate only a few experts per token, push this knee later. The CPU host is a separate limit. Under vLLM v0.5.x, Llama 3 8B on one H100 spent only 38% of its time in GPU execution, against 33% in the HTTP server and 29% in scheduling [5]. V1 split the API server from the engine core for up to 1.7x the throughput of V0 [6]. Asynchronous scheduling (preparing the next step on the CPU while the GPU runs the current one) became the default in v0.14.0 [7].

Regime What dominates a step What raises throughput What stops helping
Small batch, short context Weight loading (memory-bound) Larger batch, weight-only 4-bit, speculative decoding Nothing yet
Large batch, short context Arithmetic (compute-bound) FP8/FP4 activation formats Large-K speculation, weight-only 4-bit
Large batch, long context KV loading (memory-bound again) FP8 KV cache, more KV memory Anything adding KV pressure
Small model, fast GPU CPU overhead (host-bound) Async scheduling, API-server scale-out Raising batch knobs

Throughput is batch size times step efficiency: memory sets the first factor, kernels and host overlap the second. Most blanket tuning advice holds in one row of this table and fails in another.

2. Measuring Throughput: Benchmark Method and Metrics

2.1 Metrics and the knee

Throughput is reported as output tokens/s, total tokens/s (prompt plus output) or requests/s. Latency is reported as time to first token (TTFT), time per output token (TPOT, decode time averaged over later tokens) or inter-token latency (ITL, the gap between streamed chunks) [8]. TPOT and ITL diverge under speculative decoding [8]. Goodput joins the two: the rate of requests meeting every target in a latency service-level objective (SLO). In NVIDIA’s AIPerf walkthrough (eight Qwen3-0.6B replicas on eight H200s, vLLM v0.11.0), the server completed 26.67 requests/s but only 7.43 met both latency targets [9]. Because the peak-throughput point and the best-latency point differ, the vLLM Blackwell study warns that “single-point metrics can be misleading” [10]. It plots Pareto frontiers (the configurations no other beats on both throughput and latency) instead [10].

2.2 A defensible protocol

vllm bench serve offers the three load models in the table [8]. vllm bench sweep serve restarts the server per configuration, resets the prefix cache between runs and repeats each point three times; serve_sla then finds the highest load meeting a P99 target [11]. The auto_tune script first finds the highest memory utilization that does not crash, starting at 0.98. Only then does it search max_num_seqs × max_num_batched_tokens under a P99 cap [12]. In other words, claim memory first, then tune the batch. A sound protocol ranks structural options offline with vllm bench throughput, then measures goodput at the SLO on one dataset whose input/output length ratio matches the use case, with caches reset.

Tool or mode Answers Blind spot
vllm bench throughput Offline ranking of options No HTTP or streaming cost
bench serve --request-rate inf Peak capacity Queueing latency is meaningless
bench serve --max-concurrency N Throughput at fixed in-flight load Hides burst tails
Finite rate with --burstiness Production-like goodput Needs a rate sweep
bench sweep serve_sla, auto_tune Maximum load within P99 targets Only as realistic as the dataset; auto_tune uses one fixed input/output length

Three traps outweigh any knob.

  • Stale caches and cold graphs. A warm prefix cache inflates repeat runs [8], and an under-warmed CUDA-graph baseline distorts A/B deltas (section 8).
  • Unrepresentative workloads. Workload shape can reverse a verdict: on an A100 serving Qwen2.5-1.5B, CPU offload through LMCache (an external KV-cache store) was neutral on a prefix-repetition dataset but cut ShareGPT output from 4,924 to 3,719 tokens/s, a 24% loss [13]. That is why Red Hat builds test sets matching production shapes [14].
  • Untuned engine comparisons. Engine shoot-outs mostly measure configuration and version: an LMSYS post showing SGLang at up to 3.1x vLLM used “vLLM 0.5.2 with default arguments” against tuned rivals [15]. That release line also carried the real host overhead described above, which vLLM v0.6.0 cut for 2.7x over v0.5.3 [5].

3. Scheduler and Batching Knobs

Each engine step has a token budget, max_num_batched_tokens, and a cap on running requests, max_num_seqs. The V1 scheduler gives every running decode one token, then fills the rest of the budget with prompt chunks. This chunked prefill is on by default wherever the model supports it [16]. It descends from Sarathi-Serve, which let prefill chunks ride along on arithmetic-idle decode steps and raised serving capacity 2.6x for Mistral-7B on an A100 [1]. Larger budgets favor TTFT and throughput, smaller ones ITL, and the docs recommend a budget above 8,192 for optimal throughput, especially for smaller models on large GPUs [16].

3.1 Defaults are chosen per GPU

When these knobs are unset, vLLM picks them from the detected GPU [17].

GPU class (detected) Token budget: offline LLM / API server max_num_seqs
≥160 GB (B200, B300) 16,384 / 16,384 1,024
≥70 GB, not A100 or GB10 (H100, H200) 16,384 / 8,192 1,024
A100, smaller GPUs, GB10 8,192 / 2,048 256
--performance-mode throughput Doubles each unset value Doubles if unset

The small A100 tier is deliberate. A code comment cites PR #17885 [17], in which Llama-3.1-70B on A100 at TP=2 rose from 1,054 to 1,438 tokens/s (+36%) with a smaller budget while TP=4 moved −2% [18]. A large GPU finishes a big step quickly and spreads fixed overhead over more tokens. An A100 saturates compute sooner, so extra tokens only lengthen each step. Plausibly (the PR does not say), they also enlarge the activation reserve taken from the KV pool.

3.2 Where chunking and caps backfire

Too small a budget also costs: PrefillOnly lost 14% throughput cutting 20,000-token inputs into 512-token chunks, a 39-way split [19]. One unreplicated report saw a hybrid state-space model fall from 47 to 5.7 tokens/s when chunked prefill was forced on [20], a reason not to override V1’s per-model choice. max_num_seqs is a ceiling that cuts both ways. Below what the KV pool holds, raising it enlarges the decode batch, and a throughput plateau exactly at the cap value means the cap binds. Above KV capacity it only adds preemptions, and above the 512 graph-capture size it also loses full CUDA graphs (section 8). Red Hat sets it where measured throughput plateaus so that excess requests queue instead [14]. Under data parallelism it applies per rank [21]. --scheduling-policy priority replaces first-come-first-served admission, which changes who waits rather than aggregate tokens/s [4].

The evidence supports starting from the defaults. On H100-class or larger servers with long prompts or offline work, try 16,384 and then 32,768 and stop at the plateau. On A100, sweep downward as well. Try --performance-mode throughput early [17]. No published V1-era budget sweep exists, so measure this curve locally.

4. GPU Memory and KV Cache Configuration

At startup vLLM profiles memory, loads weights, reserves activation and CUDA-graph space, and turns the remainder of its share into 16-token KV blocks [2]. Every lever here enlarges that pool or shrinks each request’s share of it. When the pool runs dry, V1 preempts a request in RECOMPUTE mode, discarding its KV to recompute later. The documented fixes are higher memory utilization, a lower max_num_seqs or budget, or more tensor or pipeline parallelism [16].

4.1 Claim memory and right-size context

--gpu-memory-utilization defaults to 0.92 in current docs [4]; older guides cite 0.90. Red Hat found the unclaimed remainder “often remains unused”, up to 8 GB on an H100, and advises raising the value until startup or peak load fails, then backing off [14]. Offline batch guides suggest about 0.95 [22]. In the worked example, each extra 0.03 adds about 18,000 Llama-8B tokens. Pinning the pool with --kv-cache-memory-bytes speeds restarts, but “a conservative value caps batch concurrency (and therefore throughput)” [16]. For context, Anyscale recommends sizing --max-model-len to the P95 or P99 of real traffic rather than a 128K model maximum [23].

4.2 FP8 KV cache and CPU offload

--kv-cache-dtype fp8 halves the bytes per cached token. In the vLLM team’s April 2026 H100 study, Llama-3.1-8B at concurrency 8 with inputs of about 20k tokens gained 14.9% output throughput, because the saving “allows the scheduler to pack more concurrent requests” [24]. The gains are conditional: gpt-oss-20b, which has sliding-window layers, gained 2.6% (4.8% with those layers kept in BF16). The single-request break-even context, above which FP8 decodes each token faster than BF16, fell from 24,889 tokens on v0.10.2 to 7,010 on v0.19.1. Even so, a KV-bound server with shorter prompts can still gain from the extra capacity.

Prefill regressed on head_dim=256 models (TTFT quadratic coefficient about 1.6x larger) [24]. Accuracy mostly held within 1-2 points, but an earlier FlashAttention-3 FP8 path cut 128k needle-in-a-haystack accuracy from 91% to 13% before a fix [24]. For that reason, pair KV quantization with automated evaluation [14].

CPU KV offload (--kv-offloading-size) extends the cache into host RAM [4]. vLLM’s up-to-9x result on Llama-3.1-8B/H100 used unique prompts, high CPU hit rates and GPU prefix caching disabled [25]. The 24% ShareGPT loss above came from the LMCache backend, not this native connector, and both results are edge cases. Together they suggest offload pays only when reusable KV exceeds what the GPU can hold.

KV-headroom lever (cheapest first) Headroom gained Price paid
Raise gpu_memory_utilization Up to ~8 GB on H100 [14] Out-of-memory risk under spikes

The cheapest-first order is reasoned from the mechanism, not measured end to end; re-measure after each row.

5. Parallelism and Deployment Layout

With parallelism basics assumed, the throughput question is how each layout spends KV headroom. For dense models, data parallelism (DP) runs independent replicas, each with its own KV cache and no cross-GPU communication [21]. Tensor parallelism (TP) splits each layer across GPUs, leaving each “more memory available for KV cache” but adding an all-reduce (a collective sum across GPUs) in every layer [16]. Pipeline parallelism (PP) instead splits the layers into stages that pass activations once per stage boundary, which suits multi-node or weak-interconnect setups. Its stages stay busy only when enough requests are in flight, and async scheduling helps it (section 8). Red Hat finds the fewest GPUs that hold the model with sufficient KV, deploys as many such replicas as fit, then tests fewer, larger ones [14].

On PCIe (the general bus, far slower than direct NVLink links between GPUs), measurements favor replicas under load. On 4× RTX 3090 over PCIe (vLLM 0.21), two TP=2 replicas beat one TP=4 instance at every concurrency, from +4% at 1 request to +136% at 128 (1,437 against 610 tokens/s) [26]. KV was not scarce, so all-reduce cost decided the result [26]. ScaleLLM found four TP=2 Mixtral replicas ahead above roughly 128 concurrent requests but a single TP=8 replica best at low concurrency, since light traffic cannot fill several replicas [27]. No matched V1 benchmark compares the two over NVLink, so replicating until KV runs short is a procedure to verify, not a measured law.

Two cases change the default. DeepSeek-style multi-head latent attention (MLA, a compressed KV format) duplicates latent projections under TP. vLLM therefore pairs data-parallel attention with expert parallelism (EP, spreading MoE experts across GPUs), reaching about 2.2k tokens/s per H200 with dual-batch overlap of communication and compute [28]. Prefill/decode disaggregation “DOES NOT improve throughput” according to vLLM’s v0.9-era docs [29]. DistServe, however, serves 7.4x more requests within SLO [30]: disaggregation buys goodput, not raw throughput.

Situation Layout that tends to win Reason
Model plus ample KV fits one GPU DP replicas No communication
PCIe-only GPUs Smallest TP that fits (≤2), then replicate All-reduce cost dominates [26]
Low concurrency TP across GPUs Replicas would sit idle [27]

6. Quantization

Quantization stores numbers in fewer bits. Weight-only formats such as W4A16 (4-bit weights, 16-bit activations; GPTQ or AWQ on Marlin, vLLM’s optimized 4-bit-weight kernels) cut the bytes loaded per step but still compute in 16-bit. Weight-and-activation formats such as W8A8 (FP8 or INT8) and NVFP4 (NVIDIA’s 4-bit float) also run faster tensor-core math. Weight-only formats therefore win while decode is memory-bound and fade once it turns compute-bound.

Kurtic et al., across more than 500,000 evaluations on vLLM, found that “W4A16 is the most cost-efficient for synchronous setups, while W8A8 dominates in asynchronous continuous batching”, with FP8 effectively lossless and tuned INT8 losing 1-3% [31]. The crossover varies with model and hardware [31]. Much of the gain is capacity. Databricks’ 2.2x FP8 result on H100 (TensorRT-LLM, not vLLM) compared FP8 at batch 64 with FP16 at batch 32, and per-token speed improved only about 10% [32]. Weight-only INT8 was about 30% faster below batch 8 and gave “little to no speedup” above it because its arithmetic stayed in FP16 [32]. Re-tune the batch knobs after any format change.

FP8 W8A8 needs Ada, Hopper or newer; INT8 W8A8 runs on Turing and Ampere; Marlin weight-only kernels run from Ampere on [33]. On MiniMax-M2.5 served with vLLM, B200 NVFP4 gave up to 8.2x the performance per dollar of H100 FP8: 2.94x from the GPU and 2.77x from NVFP4 [34]. That precision step was “unlocked by” a new MoE kernel (PR #36307) [34]. It shrank to 1.65x at 22 tokens/s per user (the high-batch end where throughput tuning happens) and came without accuracy data [34].

GPU class Throughput default Low concurrency or memory-limited Accuracy evidence
Ampere (A100, A10G) INT8 W8A8 W4A16 (Marlin) INT8 loses 1-3% [31]
Ada / Hopper (L40S, H100, H200) FP8 W8A8; FP8 KV for long contexts W4A16 FP8 effectively lossless [31]
Blackwell (B200, B300) NVFP4 where a tuned kernel exists, else FP8 W4A16 NVFP4 unreported; run evaluations

7. Prefix Caching and Speculative Decoding

7.1 Prefix caching

Automatic prefix caching (APC) reuses the KV blocks of a shared prompt prefix, such as a system prompt, instead of recomputing them [35]. Cached blocks that no running request references stay in the free block queue, keeping their contents until reallocated [2], so they give up their space the moment a live request needs it. V1 enables APC by default because it costs “less than 1% decrease in throughput even when the cache hit rate is 0%” [6]. It saves only prefill work, so its value scales with reuse. Offline jobs can sort requests to group shared prefixes [22], and each DP rank keeps its own cache [21].

7.2 Speculative decoding

Speculative decoding (SD) has a cheap drafter, often an EAGLE head (a small network trained on the target model’s hidden states), propose K tokens that the target model verifies in one pass. Each accepted token saves a decode step, so a low acceptance rate turns a larger K into wasted work. At low load this spends idle arithmetic. At high load, verification adds batch size × K tokens of work to a GPU that may already be compute-bound, and draft tokens occupy KV slots that could hold more requests.

The case for caution at saturation is real. vLLM’s docs target medium-to-low QPS, memory-bound workloads, though their method table still rates EAGLE-style drafters as gaining at high QPS [36]. A 2024 vLLM post measured 1.4-1.8x slowdowns at high request rates with fixed K [37]. A study inside vLLM found SD beating no-SD in every tested workload, but EAGLE’s speedup on Llama3-70B eroding from 1.96x to 1.72x between batch 1 and 32 as verification dominated [38]. The Dynamic SD docs illustrate K=3 up to 64 concurrent requests, K=1 up to 128 and K=0 beyond [39].

The case for it is measured too. Red Hat ran gpt-oss-120b, an MoE model, with an Eagle3 drafter at K=3 on an H200 (vLLM 0.13.0) [40]. Peak output rose from 2,024 to 2,574 tokens/s (+27.2%) and the geometric mean across load levels rose 20.7%, with at most about 100 requests in flight [40]. Long prompts at TP=1 cut the gain to +9.5%, and K=4 gave 13% lower peak throughput than K=3 [40]. MagicDec reached up to 2.51x on Llama-3.1-8B at batch 32-256 once contexts of about 16k tokens or more made KV loading dominant [41]. It used a sparse-KV self-drafter rather than a stock vLLM drafter [41]. The regime model reconciles both sides: sparse MoE activation and long contexts keep decode memory-bound to larger batches.

The evidence supports SD as a load-dependent lever: likely gains for MoE models with a native drafter at K=2-3 up to about 100 concurrent requests. For dense models at high load, the only measured loss is the fixed-K 2024 result. Acceptance explains why small K wins. In PayPal’s EAGLE3 study of a dense 8B model on vLLM, K=3 held about 35.5% acceptance and gained up to concurrency 32, while K=5 fell to about 25% and helped only at concurrency 4 or below [42]. Both were measured against an NVIDIA NIM baseline rather than vLLM without SD [42].

A/B it at the target concurrency with Dynamic SD, which picks K from the running-request count and stops speculating above a set threshold [39]. Dynamic SD reverts to a fixed K under data parallelism, however [39]. Because each speculative decode consumes 1+K tokens of the step budget, re-sweep max_num_batched_tokens with SD on; this follows from the scheduler’s design and has not been measured.

8. Compilation, CUDA Graphs and Kernel Backends

A CUDA graph records a sequence of GPU kernel launches once and replays it, removing per-launch CPU cost; torch.compile fuses operations into fewer kernels. The default -O2 level enables fusions and FULL_AND_PIECEWISE graphs (a full graph for uniform decode batches, piecewise graphs otherwise). Level -O3 currently equals -O2, and -O0 and -O1 trade speed for faster startup [43]. The docs call FULL_AND_PIECEWISE “generally the most performant setting” [44], so the main risk is opting out: a leftover --enforce-eager costs “steady-state decode performance” [16].

No published source compares -O levels, but the eager-versus-graph gap is measured. On a 4B model on an H100 (vLLM 0.21), compiled CUDA graphs cut p95 ITL from 24.2 to 6.5 ms and raised throughput from about 5,000 to 8,700 streamed chunks/s in a run where launch overhead dominated [45]. The same study’s under-warmed first baseline inflated a +30-50% gain from raising max_num_seqs 32 to 64 into an apparent +137%, so compare warm runs only [45].

Graphs are captured up to batch 512 by default (1,024 on data-center Blackwell). Larger decode batches run without full graphs unless --max-cudagraph-capture-size is raised, which spends KV memory [4]. The automatically selected attention backend also limits graph support: FlashAttention 3 always, FlashAttention 2 and FlashMLA for uniform batches, standard FlashInfer for single-token decode only, with silent downgrades otherwise [44]. Check the startup log before and after overriding it [44].

On the host, async scheduling with pipeline parallelism added 30.8% end-to-end throughput in v0.16.0 [46], a gain that scales with the host’s share of each step. vLLM needs at least 2 + N physical CPU cores for N GPUs [16]; --api-server-count scales out the front end, and --stream-interval above 1 “may increase throughput” [4]. For small host-bound models, the experimental Model Runner V2 lifted Qwen3-0.6B on a GB200 from 16K to 25K tokens/s (+56%) [47].

9. Step-by-Step Tuning Playbook and Pitfalls

9.1 Procedure

Structural decisions come first because they change what the fine knobs should be. The order is a synthesis to verify, not a measured optimum.

  1. Upgrade and keep the defaults. Use a current V1 release with async scheduling, -O2 and prefix caching on, and no leftover --enforce-eager or hand-set batch flags [7, 43].
  2. Fix the workload and SLO. Capture real length distributions and prefix reuse, set P99 targets and record a baseline concurrency sweep [14, 11].
  3. Claim memory. Raise --gpu-memory-utilization until startup or peak load fails, then back off [14, 12].
  4. Right-size context. Set --max-model-len near the real P99 [23].
  5. Shrink weights, then KV. Pick the format from the section 6 table, A/B an FP8 KV cache and evaluate accuracy after each change [31, 24]. Expect gains mainly where freed memory becomes a larger batch: FP8 weights gave only about +4% on a 4B model with KV to spare [45].
  6. Choose the layout. Follow the section 5 table, adding replicas only while each still fills its batch; doubling replicas at fixed load cut per-GPU throughput about 20% in one H100 study [45].
  7. Sweep the batch knobs. Run max_num_seqs {256, 512, 1024} × max_num_batched_tokens {2,048 … 32,768} through serve_sla or auto_tune under the P99 limit, and try --performance-mode throughput [11, 12, 17].
  8. A/B the conditional features. SD at K=2-3 with bucketed K at target concurrency (then re-sweep the budget), and CPU offload at real hit rates [40, 25].
  9. Lock and re-verify. Discard warmup and report goodput from three warm, cache-reset repeats (vLLM’s convention, not an evidence-derived count); re-tune after any change of model, version or traffic [11, 45].

9.3 Pitfalls and outlook

The costliest mistakes are measurement mistakes: quoting unlimited-rate peaks as capacity, judging from one synthetic dataset, benchmarking on a warm prefix cache or a cold compiled graph, and comparing single points instead of frontiers [9, 13, 10, 45]. Next come transplanted rules: large token budgets on an A100 [18], TP=4 over PCIe [26], FP8 KV for short chats [24], drafts of K≥4 [40], and max_num_seqs beyond KV capacity [16]. Version drift is the last trap; FP8 KV behavior alone changed sharply between v0.10.2 and v0.19.1, so re-benchmark after every upgrade [24].

Four gaps in the published evidence map onto local experiments: replicas against TP over NVLink; every precision format on one machine with retuned batch knobs; SD on a dense model at production concurrency; and a 2,048-32,768 token-budget sweep on your own prompt mix, with and without SD. When defaults shift again, rerun the measurement protocol rather than reuse the numbers quoted here.
