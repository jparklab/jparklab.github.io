Neither single-pass nor split-KV decode attention wins in general. Every vLLM backend implements the same inequality, just with different inputs. Split-KV wins when the single-pass launch can’t saturate HBM bandwidth. The unsplit grid is batch × KV heads per GPU × query tiles. Split-KV wins when that grid falls below about one wave of the GPU, or lands in a mostly empty final wave. It also wins when each thread block has a KV walk too long to hide memory latency. Splitting is safe if you stay within about one wave of split blocks and keep at least 64–128 KV tokens per split. Deep in underfill, a wrong single-pass choice has cost 5–49x at kernel level, and a wrong split at most 1.21x [1, 2]. Near one wave, both mistakes cost about 1.1–1.4x [3, 4, 2]. Serving gains show up mostly at low concurrency with long contexts, and on ragged lengths. vLLM Triton decides from batch size, FA3 from live lengths on the device, FlashInfer from a CPU plan, and XQA and trtllm-gen from max_seq_len. ROCm’s HIP default always splits. CUDA graphs push decisions toward a capture-time worst case. And batch invariance forces single-pass in vLLM’s FA, Triton and FlashInfer paths [5, 6, 7], which costs 15–41% on ragged-length loads [8].

1. Single-Pass vs Split-KV Decode: Mechanics and Why the Choice Exists

1.1 Two ways to split the same reduction

In the decode phase of LLM inference, each sequence adds one new query token per iteration. With speculative decoding it adds 1+K tokens, when the model checks K proposed tokens at once. That query attends over the sequence’s whole key/value (KV) cache. Kernels split the work into independent pieces and hand them to CTAs (cooperative thread arrays, i.e. thread blocks; AMD calls them workgroups). The GPU schedules CTAs onto its streaming multiprocessors (SMs; compute units, or CUs, on AMD). The two strategies differ in only one thing: how many independent pieces they create.

A single-pass kernel gives one CTA to each (sequence, KV head, query tile). That CTA walks every KV tile in order with online softmax. It keeps a running maximum, exponential sum and accumulator, and writes the normalized output once. vLLM’s Triton 2D kernel launches exactly this grid, (total_num_q_blocks, num_kv_heads) [6]. FlashAttention’s num_splits = 1, the legacy CUDA PagedAttention V1 and trtllm-gen’s persistent fallback are the same design [9, 10, 11].

Flash-Decoding adds a third parallel axis: the KV length. It cuts the cache into chunks and computes partial attention for each chunk in parallel, while writing “1 extra scalar per row and per split: the log-sum-exp” [12]. Then it reduces across splits, using that log-sum-exp (LSE) to rescale each piece [12]. vLLM’s Triton 3D kernel is this design. It launches a grid of (total_num_q_blocks, num_kv_heads, num_par_softmax_segments), then a reduce_segments kernel that rescales each segment by exp(segm_max - overall_max) [6]. The second launch exists because “Triton does not provide a global barrier, this reduction requires launching a second kernel, introducing a trade-off between additional parallelism and launch overhead” [13]. The legacy CUDA paged_attention_v2 had the same two-kernel shape [14]. XQA and FlashInfer’s persistent kernel do the merge inside the kernel instead [15, 16].

The merge is exact in real arithmetic. FlashInfer documents merge_state as producing output “equivalent to attention with merged KV-segment” from two partials and their float32 LSEs [17]. But it isn’t bitwise exact in floating point, because the summation order follows the split boundaries. vLLM PRs record greedy outputs drifting into “equally plausible continuations” when only the segment layout changed [18, 1]. That is the root of the batch-invariance constraint.

1.2 Why the choice exists at all

Prefill has thousands of query rows to spread across the GPU. Decode has one per sequence. As the Flash-Decoding authors put it, “if the batch size is smaller than the number of streaming multiprocessors (SMs) on the GPU (108 for an A100), the operation will only use a small part of the GPU” [12]. GQA (grouped-query attention, where several query heads share one KV head) packs a KV head’s query heads into one CTA. So the grid scales with KV heads. Tensor parallelism (TP) shards those heads across GPUs, “further reducing the number of SMs activated per GPU during the decode phase” [19]. A Llama-70B-class model at batch 1 runs 8 CTAs on an H100’s 132 SMs [20]. At TP8 the unsplit grid equals the batch size. Single-pass also ran into hard limits. Legacy vLLM forced V2 above 8,192 tokens to avoid shared memory shortage [10]. And TensorRT-LLM forces multi-block mode when its shared memory, which grows with sequence length, runs out [21].

2. The Cost Model: SM Occupancy, Reduction Pass, and Scratch Memory

Split-KV pays three costs for one benefit. The benefit is more CTAs in flight issuing memory loads, which pulls more of the GPU’s HBM (high-bandwidth memory) bandwidth. The costs are wave quantization, the reduction pass, and scratch memory for partial results. Wave quantization works like this: CTAs run in waves, and each wave fills every resident slot once. So a grid slightly larger than one wave pays for two.

2.1 One normalized variable

Let C₁ be the unsplit CTA count: batch × KV heads per GPU × ⌈query tokens × GQA ratio / BLOCK_M⌉. Let W be the unsplit wave fill, C₁ / (SMs × resident CTAs per SM). The production thresholds look unrelated. But each one reads W plus a length term. FA3 returns one split at total_mblocks >= 0.8f * num_SMs [9]. Otherwise it picks the smallest split count that reaches 85% of the best wave efficiency [9]. Upstream FA2 uses the same rule with the SM count doubled [22]. FlashInfer skips splitting when batch_size * gdy >= max_grid_size, with the grid size taken from measured occupancy [23]. trtllm-gen goes single-pass when oneWaveSplits = SMs / baseNumCtas is 1 or below [11]. AITER’s Triton unified attention runs 2D when num_2d_prgms exceeds cu_count * 4 [24].

vLLM’s own Triton gate is the exception. It sets seq_threshold_3D = MIN_LAUNCH_GRID_SIZE_2D // num_heads_kv with MIN_LAUNCH_GRID_SIZE_2D = 128 [25]. That is a fixed CTA count, not one that scales with the SM count. We worked out the W cutoffs from the constant and published core counts. They come out at about 0.97 on a 132-SM H100 and 0.42 on a 304-CU MI300X [26]. On a 148-SM B200 the cutoff is 0.86 [27], and on a 188-SM RTX PRO 6000 (SM120, workstation Blackwell) it is 0.68 [2]. If one CTA is resident per SM, the Triton default is tuned to H100 scale and switches to single-pass too early on larger parts. That is our inference. And the one measured per-platform retune (gfx1201, open PR #60418) moved the threshold down instead.

2.2 The test is bandwidth, not idle SMs

W < 1 is only a proxy. The real test is whether the unsplit launch can saturate HBM. Three 2026 measurements show split-KV winning at W ≥ 1:

  • FlashInfer’s SM90 fp8 XQA launcher dropped to one split once batch × KV heads went past about 50: “One CTA per SM cannot cover HBM latency, so large-batch long-context decode with few KV heads ran at 60-75% of bandwidth” on GH200 [4].
  • On MI355X (gfx950, CDNA4) at context 8,192, AITER’s partitioned V2 still beat single-pass V1 by 2.00x at batch 128, with 64 query and 8 KV heads at head size 128 (2.92x at head size 64) [28, 29]. V1’s grid already holds 8,192 programs there [28, 29]. Part of the gap is kernel design, not split policy: V1 launches one program per query head (num_seqs * num_q_heads). That is our reading of the dispatch code [29].
  • On SM107 (a Blackwell variant), growing a batch of 9K-token sequences from 208 to 209 requests made the call 1.39x slower for 0.5% more work. The 209th CTA opens a nearly empty second wave [3].

Below saturation, the speedup tracks the number of parallel CTAs. On SM120 at 131k, 16 and 64 segments beat one 2D CTA by 15x and 48x [18, 2]. By our arithmetic, that’s about 0.94 and 0.75 parallel efficiency. At 4k context, 16 segments gave only 6.3x (142.9 → 22.6 µs), because a launch-plus-reduce floor of about 22 µs dominates [18, 2].

The counter-case: FlashInfer’s 2024 launch post found split-KV gave nothing on RTX 4090 and RTX 6000 Ada [30]. On those cards, a fraction of the SMs already saturates GDDR bandwidth for a kernel that isn’t compute-bound. It did help on an A100, where the CUDA-core kernel was compute-bound [30]. No source states the general rule, but these measurements together imply it: split when C₁ × (bandwidth one CTA can sustain) is below HBM peak. Memory type doesn’t decide it, since the 2024 result is about a CUDA-core, non-GQA kernel. Modern GQA decode kernels on GDDR and LPDDR parts still gain a lot from splits at batch 1 and long context (R9700, RTX PRO 6000, gfx1151 and RTX 3090 results in 4.3 and 8.1) [18, 1].

2.3 Three cost terms, and which one bites

Wave quantization is the largest measured over-split cost. SGLang’s AMD MLA decode code (MLA is multi-head latent attention, DeepSeek’s compressed-KV design) records that crossing the one-wave split budget costs a whole wave [31]. At batch 24 and 68k context, 21 splits (504 blocks) took 358 µs and 22 splits (528 blocks) took 528 µs: +47% for 4.8% more blocks [31]. The 208→209 cliff is the same effect hitting single-pass. LeanAttention’s critique of fixed-split decoding rests on the same partly full waves [32].

The reduction pass is cheap in isolation; what it drags along is not. Two isolated timings exist. A research kernel on an RTX 3060 merged in 0.014 ms against 1.263 ms of decode, about 1.1% [33]. Yet the same paper sent contexts below 16k back to FlashInfer, because split and merge dominated there [33]. FlashInfer PR #4702 cut a B200 MLA decode call at 4k KV from 12.03 to 11.46 µs median, about 5% [34]. It did that by changing only the reduction, moving it from global memory to a thread-block cluster [34].

Production caps treat the reduction as a real cost. XQA caps splits at round(sqrt(8n)) because otherwise the final reduction may dominate [35]. trtllm-gen allows at most ceil(window / (2*stepKv)) splits [11]. In trtllm-gen, 16 splits reduced through a CGA (a thread-block cluster sharing distributed shared memory) “beat 17-32 splits on the GMEM path whenever each CTA walks ≤ 4096 KV tokens” [36]. The reduce starts to matter when per-split work shrinks toward its size. On gfx950 the measured crossover is 64–80 KV tokens per segment [37]. A gate at 80 had a worst case of −1.0% over 250 configurations, against −60.9% for a 256-token gate [37]. FlashDecoding++’s widely quoted 18.8% measures “synchronized partial softmax update” overhead, not the combine pass [38].

Scratch memory is a capacity and CUDA-graph problem more than a time problem.

  • FA3 allocates fp32 out_accum of shape [num_splits, batch, heads, seqlen_q, head_dim] plus softmax_lse_accum, with num_splits ≤ 256 [39]. That’s why vLLM fixes FA’s split count under full graphs, so the buffers can be allocated at capture [5].
  • FlashInfer’s persistent scheduler caps partials at 2 × #CTA [16].
  • XQA reserves 6,000 sub-sequences, about 12 MB for llama v2 70b [40].
  • vLLM Triton’s preallocated partials cost +24 to +42 MiB per rank for MiniMax-M3 TP8 [2].
  • ROCm’s HIP path allocates per call, sized by the batch’s max_seq_len [41]. By our arithmetic from its partial shapes, batch 256 with 32 query heads, head size 128 and 32k context needs about 277 MB per layer call [41].

Capped-split scratch is small next to a multi-gigabyte KV cache. The HIP path’s is not. For all of them, the binding constraint is that graph-replayed buffers must be sized at capture for the largest split count.

Correctness surface is the cost kernel benchmarks never show. In 2025–2026 the split reduction path produced at least four bugs:

  • FA2’s varlen combine wrote every batch to the same output address when a real split happened [42].
  • vLLM Triton’s 3D path corrupted rows whose keys were all masked within a segment, with a maximum absolute error of about 4 [1].
  • #56148 fixed the same -inf-clamp hazard for empty segments [2].
  • AITER’s HIP persistent-split reduce gives wrong outputs above 32 partitions, with relative error up to 2.8 at 33 splits [43].

Single-pass kernels have no cross-program merge, so they have no matching bug class.

2.4 The rule and its two guards

Under-splitting wastes memory parallelism, in proportion to how far the grid sits below saturation. Over-splitting costs a fraction of a wave plus a cheap merge, until one of two guards is broken. The guards are about one wave of split CTAs, and a floor of about 64–128 tokens per split. The measured wave cliffs come from opening a partial wave, not from multi-wave grids at long KV.

3. vLLM Triton Unified Attention: 2D vs 3D Kernels

The Triton backend (TRITON_ATTN) is the one place where vLLM itself makes the split decision. A launcher gate picks, per batch, either the 2D kernel (single-pass) or the 3D kernel (segmented, plus a reduce_segments step). An April 2026 talk calls it the default for AMD deployments [26]. But vLLM main ranks it last among ROCm backends, behind ROCM_ATTN, which merged PR #36702 put first [47]. So it is chosen when those backends decline a shape. Nearly every change to its boundary came with a measurement.

3.1 The gate, as of vLLM main (October 2026)

The launcher runs 2D in any of these cases: scratch is missing or too small; max_seqlen_q > 1 and the query exceeds MAX_3D_QUERY_LEN or masking is non-causal; num_seqs * cdiv(max_seqlen_q, BLOCK_Q) > seq_threshold_3D; or batch invariance is enabled [6]. The query test reads the batch maximum. So when an iteration carries a chunked-prefill chunk, all its decodes run on 2D. FlashInfer, by contrast, plans decode rows separately [7], and FA3 handles mixed varlen batches in one call [5]. No source measures what this costs in serving. On main, MAX_3D_QUERY_LEN is 8 for the unified kernel [6, 25]. (The DiffKV variant, fixed by #59085, admits verify widths up to 16 [48, 1].) PR #56148’s final commit text states that admission is “widths 2..5 on every platform; width >= 6 uses 2D”, enforced on top of that constant [2].

The threshold is 128 // num_heads_kv. Under full decode graphs it snaps to the CUDA Graph capture size closest to self.seq_threshold_3D, so each captured graph covers one kernel [25]. PR #28306 added the snap, along with a guard [49]. If snapping would push the threshold above 4x its unsnapped value, the guard resets it to 0, which means 2D only. A reviewer called 2D-only a safe choice for CUDA graph compatibility [49]. The 3D kernel fixes the segment count per sequence. So short sequences produce empty segments, which reduce_segments masks out [6]. The count is 16. It rises to 64 on SM120 when 16 segments would underfill the GPU [25]. The gate reads batch size, KV heads, query width and capture sizes. It never reads KV length.

3.2 How the boundary moved, PR by PR

PR #19152 (June 2025) introduced 3D with 16 segments. It reported “more than a factor of two” end to end at batch 1 with long outputs on H100 [50]. The authors’ paper confirms 3D was “only launched for decode attention on small batches involving longer sequences” [51]. But until October 2026, any max_seqlen_q > 1 forced 2D. So a single-stream verify ran “(1, 4) = 4 CTAs on a 70-SM GPU, each CTA sequentially walking the entire KV history” [1]. That was a 19.6–48.7x kernel penalty at 65–67K KV [1]. On gfx1151 (an RDNA client GPU), a verify iteration took 581 ms, against 92 ms without speculation, until the 3D fix brought it to 162 ms [1].

PR #56148, merged 2026-10-13, let short multi-query batches into 3D through the same shape-only gate. It was measured on a width-6 MiniMax-M3 TP8 shape at 128k, before admission was narrowed to widths 2..5. There the attention kernel ran roughly 10x faster on SM120 and H200, and the worst admitted shape lost 1.21x [2]. PR #58482 (merged 2026-10-01) made SM120’s segment count adapt to occupancy. A constant 64 had regressed Llama-3.1-8B with EAGLE3 (a speculative-decoding head) to 0.962x tokens/s, at concurrency 8 and 768-token prompts [18]. The reason given: “Once the grid fills the GPU, more segments only add partial-result traffic and reducer work” [18]. Across 176 SM120 verify shapes timed for #56148, 64 segments beat 16 by 1.15–3.6x from 8k context up. They lost only at 2k context, by at most 6% [2].

Two widely cited PRs are not shipped behavior. PR #46724 (unmerged) reported 7.30x for a diffusion-LM canvas at 24 queries and 92K KV on B200. That shrank to 2.46x at four sequences “as more sequences fill the grid” [52]. PR #45450 (open, in practice superseded by #56148) reported B300 gemma-4-31B TPOT (time per output token) falling from 13.42 to 3.12 ms at batch 1 [53].

RDNA tuning found the 16-segment constant wrong in both directions [54]. It gives too few programs for one request on a 32-CU part, and too many tiny ones for larger batches. PR #60418 (open) proposes halving the gfx1201 threshold to 64 // num_kv_heads, after a 3,888-batch sweep of forced 2D against forced 3D [54]. PR #56276 raised gfx1151 segments to 32 for MQA (multi-query attention, one KV head). That improved end-to-end latency by 12.7–15.7% at batch 1 with an 8k prompt, while an 8-KV-head control stayed flat [55]. PR #61646 (open, R9700) splits only sliding-window layers [56].

The gate gets the entry condition right. But it is blind to the cost model’s other two axes. It has no KV floor, so it splits short contexts where the reduce launch dominates. And it has no SM scaling, so it probably under-splits large parts. It is a good default for low-batch long-context decode and verify, and a small tax at short context. The IBM authors describe a persistent 3D kernel, with a static grid sized from SMs per KV head and scheduling tensors generated on the CPU [26]. That is the better end state, because real lengths would drive the split [26].

4. FlashAttention and num_splits

FlashAttention exposes split-KV as one integer, num_splits. A value of 1 is single-pass; anything more adds a separate combine kernel. Upstream FA3 picks the value with a host heuristic, then refines it on the device for variable-length batches. vLLM sets a cap and decides when the heuristic may run. On Ampere and Hopper, FLASH_ATTN is first in vLLM’s backend priority, so this code decides on a default H100 deployment [57].

4.1 The upstream heuristic

FA3’s get_num_splits packs GQA into the query dimension. For dynamic-split varlen batches, it computes an upper bound on purpose: We assume the case where there's 1 long sequence and the rest are short, i.e. pretending that batch = 1 [39]. The heuristic returns one split at W ≥ 0.8 [9]. It also returns one split if num_n_blocks <= 4 (we never split for hdim = 128 and seqlen_k = 512) [9]. Otherwise it picks the smallest split count that reaches ≥85% of the best wave efficiency, because extra splits add HBM traffic [9]. The 512-token guard has a small measured cost. On H100 with a Llama-70B shape at batch 1, it leaves 8 CTAs on 132 SMs [20]. Three splits save about 2.5 µs, and the gain shrinks to roughly 1.0–1.05x without precomputed scheduler metadata [20]. It is a minor defect.

4.2 What vLLM overrides, and who actually decides

vLLM’s FA backend (flash_attn.py, main as of 2026-10-25) handles three cases [5]. Eager batches get max_num_splits = 0 (use FA3's heuristics, not CG compatible). Batches inside the full-graph capture range get flash_attn_max_num_splits_for_cuda_graph, default 32 [58]. That way buffers are pre-allocated at capture, along with a persistent scheduler_metadata buffer that is refreshed in place. Under VLLM_BATCH_INVARIANT, max_num_splits = 1, and the AOT (ahead-of-time) schedule is turned off because the schedule varies with max_seqlen_q/k.

The cap is not the split count. At every replay, FA3’s prepare_varlen_num_blocks kernel computes, on the device, blocks_per_sm = ceil(total_blocks * 1.1 * num_head / num_sm) and num_splits_dynamic = min(ceil(num_n_blocks / blocks_per_sm), num_splits_static) [44]. Above batch 992 it falls back to one split [44]. So the live decision belongs to FA3’s device scheduler. It sees actual lengths, bounded by vLLM’s cap. We read this from the code [44, 5]; nobody has checked it at runtime. On that reading, it is the only production design surveyed whose split count stays data-driven inside a captured graph. vLLM turns it off for spec-decode proposers, and under batch invariance too.

Two inferences follow, and neither has been measured. The device path does not reapply the num_n_blocks <= 4 guard. So with 4 KV blocks, 8 heads and 132 SMs it yields four splits, where eager FA3 would run one [44, 9]. And blocks_per_sm sums work across the batch, so the split adapts to batch composition. That is exactly what batch invariance forbids [5].

4.3 Is the cap right?

The original default of 16 came from upstream FlashAttention, when PR #25274 made it configurable. That PR’s DeepSeek-V3 TP8 FLASH_ATTN_MLA run (8 sequences, about 32k-token inputs) showed median TPOT of 34.75, 32.48 and 30.98 ms at caps 16, 32 and 64 (−11%; mean 61.00 → 44.26 ms) [59]. But P99 TPOT rose from 136.90 to 178.50 ms, throughput was non-monotonic, and the 20-request runs generated different token counts [59]. So the evidence for raising the cap points in one direction, but it is noisy.

FA2’s varlen paged path treats split-KV as opt-in. A fix that re-enabled splitting for every paged call was closed, after splits of 2 and 4 ran slower than splits=0 across KV lengths 512–16384 [42]. A vLLM-fork PR that proposed splitting only on explicit request (closed as a duplicate) cited −13.8% to −18.9% verify latency at batch 1 on an RTX 3090 [42].

That happens with MQA, MLA or TP-sharded GQA at batch 1–3 (our inference from [44]). 5. FlashInfer and the TRT-LLM Kernels (XQA, TRT-LLM-gen)

FlashInfer is a kernel library. It has native decode kernels and a planner that runs on the CPU before each launch. It also wraps two NVIDIA TensorRT-LLM kernel families. XQA is a decode kernel specialized for grouped- and multi-query attention. trtllm-gen is TensorRT-LLM’s set of generated attention kernels for Blackwell.

5.1 Routing: vLLM picks the kernel, the kernel picks the split

On Blackwell, FLASHINFER is first in vLLM’s backend priority [57]. Inside it, vLLM picks the decode kernel statically, per the code comment The decode kernel must be selected statically for FULL cudagraph capture [7]. XQA runs on SM90 and SM12x, trtllm-gen on the SM100 family, and FlashInfer’s native kernels on unsupported layouts and pre-SM90 parts [7]. supports_trtllm_attention returns False under VLLM_BATCH_INVARIANT or without NVIDIA artifactory access [60].

5.2 FlashInfer native: two planners

The non-persistent BatchDecode planner (FlashInfer main, October 2026) goes single-pass when batch_size * gdy >= max_grid_size [23]. Otherwise it binary-searches for the smallest page chunk (at least 128 tokens) that keeps CTAs within one wave [23]. Without graphs, it falls back to single-pass when nothing would split. But when using CUDAGraph, we always use partition-kv kernel, padding the batch to max_grid_size / gdy [23].

The persistent scheduler from the MLSys 2025 paper splits only requests “whose KV length exceeds the total KV length divided by the number of CTAs” [16]. Short requests write through without a reduce [16]. Both planners run on the CPU every iteration, outside the captured graph, into a fixed-address, max-size workspace [16]. The paper’s only scheduler ablation (H100, Llama-3.1-8B in SGLang) shows load balancing moving inter-token latency (ITL) from 9.16 to 8.96 ms on ShareGPT, but from 13.89 to 8.63 ms on uniform 4k–16k inputs [16]. That bounds the value of the split logic. It does not compare split with single-pass [16].

5.3 XQA: split-happy, keyed to max length, merged in-kernel

XQA’s split count (TensorRT-LLM main, October 2026) is historyLength / 128, capped at round(sqrt(8n)) [35, 40]. It is reduced only if the grid exceeds 8 waves, and it is bounded by the 6,000-sub-sequence workspace [35, 40]. MLA gets one split. The spec-decode variant skips splitting when batchSize > 32 || historyLength < 2048, and otherwise asserts at most one wave [35, 40]. Each CTA writes row max, row sum and partial output to scratch. And only the CTA that performs the multi-block merge may write the output, so XQA pays for no second launch [15].

historyLength is the batch maximum. So short requests in a mixed batch inherit the long request’s split count. For one KV head per GPU at history 8,192 and batch 1, the code yields n = min(64, round(sqrt(512))) = 23 splits [35]. At batch 128 and history 4,096 it still yields 8 splits with one KV head, and 2 with four [35]. So XQA keeps splitting up to about 4x the SM count (we worked this out from the code) [35]. That goes against TensorRT-LLM’s documented batch × heads < SMs guidance [21]. TensorRT-LLM has had multi-block “turned on by default starting from TRT-LLM 0.13” [21]. NVIDIA claims “up to 3.5x more tokens per second” on HGX H200 at low batch and long sequences, but gives no table [19].

The XQA problem that has actually been measured is under-splitting. FlashInfer PR #4904 (open) replaces the SM90 fp8 launcher’s collapsing rule with a cost model, ceil(waves) * (tiles / split + overhead) + merge * split [4]. On GH200 under CUDA graphs it gains 1.38x at batch 32 and 32,768 KV, and 1.78x with random lengths at batch 64 [4]. Its one regression, 0.92x at batch 128 and KV 512, came from splitting 8-tile sequences three ways [4].

5.4 trtllm-gen: one wave, persistent fallback, opt-in beyond

FlashInfer’s launcher hard-codes multi-CTA-KV mode for generation [61]. The split is min(tunedMax, max(1, SMs / baseNumCtas)) with tunedMax = ceil(window / (2*stepKv)) [11]. At 1 or below, the kernel switches to MultiCtasKvMode::Disabled and a persistent tile scheduler, which is trtllm-gen’s single-pass [11]. The rule sees mMaxSeqLenKv, not per-request lengths. PR #6331 (merged; B200, FP8) added an opt-in 4-wave split for when one wave gives ≤ 2 splits [27]. 4 is a hard cap, because more waves can leave the reduction kernel a zero-size grid. With random lengths it was faster at every batch from 25 to 148 (geomean 1.22x at 64k, 1.27x at 288k). It was neutral with fixed lengths and slower at 8k. Under a graph captured with max_seq_len of 1M, it gave 2.02x at batch 38 with lognormal 288k lengths, but 0.57x at batch 25 with uniform 8k [27]. It stayed opt-in because under CUDA graphs only the maximum length is known, so short requests get too many splits [27].

  • PR #6267 clamped more than 16 splits down to 16 so the CGA reduction still works. That gave 1.33x on SM107 and 1.38x on B200 at batch 1 and 65,536 KV [36].
  • PR #6522 (open) adds a wave-aware split of 2 to 5 when the base grid is 1x–1.5x the SM count and KV is at least 4 MiB per sequence. Results: 1.28x at batch 209 on SM107, 1.02–1.11x on B200, and 0.995–1.017x outside that window [3].

6. ROCm Decode Attention Paths

On AMD GPUs, vLLM tries its attention backends in priority order. The first one that supports the model’s shape wins. In vLLM main, the non-MLA order is ROCM_ATTN → ROCM_AITER_FA → ROCM_AITER_UNIFIED_ATTN → TRITON_ATTN [63]. AITER is AMD’s kernel library. Its decode kernels come in hand-written assembly (ASM), Triton and Gluon (a lower-level Triton dialect), and each one has its own split policy. MLA models use a separate backend family on both vendors (FLASHINFER_MLA first on NVIDIA, AITER MLA here). We cover those only where they reuse XQA, trtllm-gen or SGLang’s AMD MLA kernel. FlashMLA plans num_splits by a rule the sources don’t document [57, 63].

6.1 Four policies on one platform (vLLM and AITER main, October 2026)

  1. HIP custom paged attention (ll4mi, the ROCM_ATTN default): always split. The partition size is fixed at compile time to 256 tokens. The grid is (num_seqs, ceil(max_seq_len/256), num_kv_heads). Workgroups past the end of a sequence exit early. A separate reduce always runs after, and there’s no skip for the single-partition case [46]. Scratch memory is allocated on every call, sized from max_seq_len [41]. The only gate is capability (head size, block size, GQA ratio, context length), not occupancy [63].
  2. AITER FA decode: split below 2 × CUs. paged_attention_common picks the ASM kernel only at head size 128. There, int8 KV or high_precision == 2 forces it, and otherwise num_seqs * num_heads > 2 * cu_num decides. Every other case gets the 256-token HIP split kernel [64, 65]. On a 304-CU MI300X the switch falls at 608, which is about batch 19 with 32 query heads. So at head size 128, the split kernel never sees the large batches where its reduce would cost the most.
  3. AITER Triton unified attention: scaled by CU count. It runs 2D for sliding windows (SWA), for max_seqlen_k <= 512, or when 2D programs exceed 4 × CUs. On gfx1100 the code documents a tighter crossover of cu_count / 4, because segment traffic and the reduce cost more than the extra parallelism buys [24]. The segment count drops to one when each program’s share of CUs is small [45].
  4. AITER Triton pa_decode: V1 vs V2. The legacy dispatch chose single-pass V1 when max_seq_len <= 8192 and either there was one partition or num_seqs * num_q_heads > 512 [29]. That copies vLLM v0.6.0’s CUDA rule, which was itself a workaround for a shared-memory limit [10].

6.2 What the ROCm measurements say

AITER now has measured split wins at W well above 1:

  • PR #5859 (merged 2026-10-07) made gfx950 pick V2 whenever the context spans more than one 1024-token partition. The shapes that switched got 2.00–5.29x faster (geomean 3.13x), and shapes already on V2 stayed at 0.99–1.02x [28].
  • PR #6453 raised the Gluon persistent-split cap from 8 to 32 for small grids. It got 2.25x at batch 1 and 32k, and 1.343x geomean over 72 shapes, with no shape slower [66].
  • PR #6434 (open) sizes splits from kernel occupancy and aligns them to whole 256-token partitions. It got 1.23x geomean on mixed lengths and 1.15x on equal lengths over 2,100 points. It keeps 32 as a correctness cap, because the reduce gives “relative error up to 2.8 at 33 splits” [43].
  • vLLM PR #62476 (closed unmerged, single run) sent gfx950 decode-width batches from AITER’s Gluon kernel to its Triton split-KV kernel, because the Gluon “KV split leaves the launch on too few workgroups”. That raised MiniMax-M3 TP4 EAGLE3 throughput from 720.8 to 985.8 tok/s at about 135K input [67].

There’s only one A/B against the HIP decode kernel. It’s on RDNA, and tile tuning muddies it. In PR #60418 (open), a tuned, occupancy-gated TRITON_ATTN beat the HIP kernel by 1.05x geomean at 1k context, rising to 1.13x at 128k (worst 0.91x). It won by 1.02–1.04x at 1 KV head per GPU and by 1.12–1.17x at 8. That’s the pattern you’d expect if the always-on reduce costs more as the unsplit grid fills [54]. So the tax is real but small there. On CDNA at batch ≥ 256, nothing isolates it. The closest evidence is the MI300 Triton result. There the split kernel lost at short outputs “as the former includes an additional launch of a reduction kernel”, and the static-launch-grid kernel under full HIP graphs removed that loss [51].

The big published ROCm backend gains come more from routing than from split policy. ROCM_AITER_FA roughly halves spec-decode TPOT against ROCM_ATTN (11.10 to 5.62 ms at concurrency 1 on 8×MI300X), while non-spec decode stayed the same within ±1–5% [68]. And the vLLM ROCm blog blames ROCM_ATTN’s 2.7–4.4x lower throughput on Qwen3-235B on unsupported KV head sizes “forcing it to fall back to Triton decode kernels” [69].

7. CUDA-Graph and Batch-Invariance Constraints

A CUDA graph records a sequence of kernel launches once, then replays it with a single CPU call. That removes most launch overhead in decode. vLLM captures one graph per batch size from a configured list. Replay freezes grid dimensions and kernel arguments. So a split decision that depends on live lengths has to be made at capture time, or by a scheduler that writes into fixed, pre-sized buffers. Batch invariance is stronger than determinism. It means a request’s output must be bitwise identical no matter which other requests share its batch.

7.1 CUDA graphs: the decision moves to capture time and can’t see real lengths

The IBM authors spell out what this means. Under graphs “we always launch as many Triton kernels as we would need for the longest request possible”, and the extra waves “outweighs the saving of the launch overhead in nearly all cases” [51]. Their static-grid kernel under full graphs ran about 6% faster than the partial-graph split kernel on H100, and up to 1.99x faster on MI300. That was at batch 1, with grid, graph mode and heuristics all changed together [51].

An H100 report on Qwen3-8B found that under full graphs, the decode launch is fixed at capture with max_seq_len set to max_model_len. So a context-length guard is really a max_model_len guard [71]. The trtllm-gen code says the same about itself: The split only sees max_seq_len, so short or similar KV lengths can be slower [11]. AITER PR #6434 traced 47 of its 57 regressions to 1K–2K contexts, where callers that fix the grid at capture can’t pass max_context_length [43]. And vLLM PR #58650’s gfx950 window-1024 split gain held in eager mode but regressed under CUDA graphs [37].

When real lengths are unknown, most backends split. The cost asymmetry justifies that, until the blind guess goes past one wave. trtllm-gen’s 0.57x at uniform 8k under a 1M-capture graph shows what happens then [27]. FA3’s device scheduler and FlashInfer’s plan keep the decision live and avoid both errors. The price is a scheduler and max-size buffers.

7.2 Batch invariance pushes the boundary to never split

Thinking Machines states the requirement: “the reduction order for each element must be fixed regardless of the batch-size of the kernel” [72]. FlashInfer’s scheduler gives the same result run to run, with no atomics [16]. But its balanced scheduling “chooses the largest split-size that can still saturate all the GPU’s cores”, so the reduction depends on the batch [72]. Every vLLM split rule except HIP’s fixed-size partitions depends on what’s in the batch. And all of vLLM’s invariance overrides land on single-pass:

  • FA sets max_num_splits = 1 and turns off the AOT schedule [5].
  • Triton forces 2D with or is_batch_invariant [6].
  • The TRT-LLM kernels are disabled [60].
  • FlashInfer native sets decode_fixed_split_size = 2048 and disable_split_kv = True [7]. But disable_split_kv wins in the planner (one chunk of numeric_limits<int64_t>::max()), so the 2048 never takes effect [23].

rocm.py adds no attention override under batch invariance. So whether ROCM_ATTN still splits there, and whether it stays invariant, is unverified [63]. PyTorch documents the same contract. Turning off split-KV via num_splits restores batch invariance, because the split decision depends on the longest sequence in the batch [73].

The principled alternative is this: “instead of fixing the # of splits, we fix the size of each split”, so KV 1,000 becomes 256 + 256 + 256 + 232 [72]. On a grid sized by length, it doesn’t survive CUDA graphs, because the CTA count then changes with length. FlashInfer’s code warns that with fixed_split_size compatibility with CUDA graph is NOT guaranteed, while disable_split_kv exists for determinism in CUDA Graph [74]. The PR that added fixed split size concluded “It’s better to disable split-kv for cuda graph” [75]. SGLang’s 2048 decode split is “only effective when cuda graph is not enabled” [76], and its FA3 backend fixes num_splits to 1 [77]. Its Triton backend is the exception. Deterministic mode keeps fixed 256-token splits with per-sequence counts on a (batch, head, MAX_KV_SPLITS) grid [31], and it’s documented as CUDA-graph compatible [78]. But the PR that added it tested only without graphs, and no source reports its cost [79].

7.3 What giving up split-KV costs, and where

Only one source isolates the cost. In high-concurrency offline throughput runs, CoRun reports that turning off split-KV costs 15–41% when prompt lengths vary and 1–9% when they’re similar, because ragged batches give uneven attention work [8]. Whole-mode overheads are bigger and not specific to splitting. SGLang’s deterministic mode averages a 34.35% slowdown, against Thinking Machines’ 61.5% [80]. Thinking Machines’ vLLM run took 26 s by default, 55 s deterministic and 42 s with an improved attention kernel [72]. vLLM’s batch-invariance docs (beta) only warn of a possible performance impact [81]. The measured driver is length variation, not concurrency. Low concurrency with long contexts is a second regime. There the cost model predicts a large tax, but no source has isolated it. RL rollouts and evaluation replays, the workloads that most often want determinism, can hit both [8, 72].

A graph-safe fixed-split design is closer than vLLM’s code suggests. SGLang’s Triton backend ships one. And ROCm’s HIP kernel already uses fixed 256-token partitions on a max_seq_len-sized grid with early exit. So each request’s partition boundaries don’t depend on its neighbors. That’s the Thinking Machines prescription on a grid that works with capture [46]. The catch is that the reduce’s template instance (NPAR_LOOPS) is picked from the batch-maximum partition count. Whether that changes the per-request summation order needs checking [46]. Single-pass under batch invariance is a stopgap, not best practice.

8.3 What the numbers say together

End-to-end gain is roughly attention share × (1 − 1/kernel speedup). That’s Amdahl’s law applied to these measurements. Attention’s share of iteration time is large only when context is long and the batch is small. That’s exactly when the unsplit grid underfills. So ~5–49x kernel wins turn into 1.5–2x at concurrency 1, and 1–3% at concurrency 10 or at short context with similar lengths. Length skew is the second regime where splitting pays at moderate-to-high concurrency (CoRun, FlashInfer’s scheduler ablation, trtllm-gen #6331, #3379) [8, 16, 27, 62].

The model matches the H100 report. A roughly 25% kernel gain on a call of about 14 µs saves about 3.5 µs per layer. Across Qwen3-8B’s 36 layers (we assume this model fact; the source doesn’t state it), that’s about 0.13 ms of a 4.6–4.7 ms ITL, or about 2.7%. The measured gain was +2.61% [71]. The #56148 c10 result has a second limit. On B300, only three dense layers plus the EAGLE3 head use unified_attention. And the PR’s c10 equivalence check failed its ±3% rule at n=1 before passing at n=4. So c10 differences sit near run-to-run noise [2].

The Flash-Decoding headline needs a correction. Its own table shows Flash-Decoding 6.2x faster than FlashAttention 2.0.9 even at batch 256 and sequence length 256, where the grid is already full [82]. So part of the famous 2300.6 → 64.4 µs comes from FA 2.0.9 being slow at query length 1, not from split-KV alone. The original post notes that “all approaches perform similarly for small prompts” [12].

8.4 Gaps in the published evidence

None of the following shows up in the PRs, issues, docs and code of vLLM, FlashAttention, FlashInfer, TensorRT-LLM, AITER and SGLang, or in the arXiv decode-attention literature, through October 2026:

  • a timing of the combine kernel as a function of split count, for FA’s mha_combine, FlashInfer’s merge, trtllm-gen’s reduction or Triton’s reduce_segments (PR #4702 compares two reduction flavours at one shape);
  • a same-GPU comparison of capture-gated vs scheduler-driven splitting on mixed lengths;
  • a kernel benchmark of fixed-size splitting vs num_splits = 1 at batch 1–8 and 32k–128k;
  • an MI300X/MI325X split-vs-single ablation, and a reduce-on/off A/B for HIP paged attention on CDNA at batch ≥ 256 (RDNA has only the muddied #60418 A/B);
  • an official XQA multi-block on/off table;
  • any independent serving reproduction by someone other than the author.

9. Recommendation: When Each Strategy Wins

9.1 The rule

  • Split in four cases. First, when W < ~1 and each sequence has at least ~1–2k tokens of KV. Second, when W is 1–1.5 and KV per sequence is large (≥ ~4 MiB, the #6522 threshold). Third, when skewed lengths make one long request the critical path. Fourth, for spec-decode verify at long context.
  • Size the split to fill about one wave. Deep in underfill, lean toward more splits. Near one wave, both mistakes cost about 1.1–1.4x, so let the wave guard decide. Never take the one extra split that opens a partial wave. Keep each split at ≥ ~64–128 tokens, lined up with page or partition boundaries. Prefer cluster reductions at ≤ 16 splits when each CTA walks ≤ 4,096 tokens.
  • Stay single-pass when W ≥ ~1.5 with moderate KV, when KV ≤ ~512–1k tokens, for legacy CUDA-core kernels on consumer GPUs, and any time batch invariance is on.

So who has to prove their case? Single-pass does, for long-KV, low-batch, TP-sharded, verify and ragged-length workloads. Split-KV does, for homogeneous short-context or full-grid serving.

9.3 Four changes vLLM should make

  1. Replace Triton’s absolute MIN_LAUNCH_GRID_SIZE_2D = 128 with about one wave of 2D programs (SMs × resident CTAs per SM, or AITER’s 4 × CUs). Add a floor of 64–128 KV tokens per segment, checked on each platform. And turn the SM120 64-segment rule into a general segments-per-SM target [25, 24, 37, 23, 54].
  2. Raise flash_attn_max_num_splits_for_cuda_graph toward 64 where batch × KV heads per GPU is below about 4, and watch tail latency. FA3’s device scheduler already backs off at full grids [59, 44].
  3. Build a graph-safe decode path for batch-invariant mode. It would use 256-token, page-aligned splits on a worst-case grid with early exit, as HIP ll4mi already does [46, 72]. Pair it with a batch-free split bucket like the one SGLang’s Triton backend uses for deterministic inference [31].
  4. Measure the ROCM_ATTN reduce tax on CDNA at batch ≥ 256 before keeping the always-split HIP path first in ROCm priority. PR #36702 gave it that spot without a benchmark [47], and open PR #60418 would reverse it on RDNA [46, 54].

9.4 Worked example: Gemma-4-26B-A4B on H100

Gemma-4-26B-A4B mixes two attention shapes. It has 30 layers. 25 of them use a 1,024-token sliding window with head size 256 and 16 query / 8 KV heads. The other 5 are global layers with head size 512 and 16 query / 2 KV heads, over contexts up to 262,144 tokens [83]. At long context the global layers carry most of the attention traffic. So their split decision is the one that matters.

On Hopper, vLLM picks the TRITON_FLASH_ATTN composite for Gemma 4, with FA4 for causal prefill and decode [57]. vLLM passes FA4 num_splits = 0 (meaning: use the kernel’s heuristic) in eager batches. Under full graphs it passes the cap of 32, and under batch invariance it passes 1. On SM90 it precompiles the head-512 kernel with split variants for 1, 32, 64, 128 and 256 splits [5]. FA4’s own heuristic isn’t in the sources. So we use FA3’s device formula as a stand-in [44]. By that formula, one global-layer sequence wants about 132 / (1.1 × 2) ≈ 60 splits, so the cap only binds at concurrency 1. At batch 2 the formula gives about 30. Each sequence has 2 CTAs, so the unsplit global grid fills one wave of a 132-SM H100 at about 66 sequences if one CTA sits on each SM. Under FA3’s 0.8-wave rule it’s about 53 (our own arithmetic).

TRITON_ATTN moves the decision out of the kernel and into vLLM. The rule is simple, and it never looks at sequence length [25, 6].

It starts from the single-pass 2D kernel. That kernel launches one CTA per query block and KV head, so a decode batch gets num_seqs × num_heads_kv CTAs. vLLM treats 128 CTAs (MIN_LAUNCH_GRID_SIZE_2D) as the smallest grid worth running single-pass. At start-up the metadata builder turns that into a batch-size cutoff, seq_threshold_3D = 128 // num_heads_kv. With full decode CUDA graphs it then moves the cutoff to the nearest capture size, so that every captured graph contains only one of the two kernels. At each decode step the launcher compares num_seqs × query blocks against the cutoff. At or below it, the step runs the 3D kernel: 16 segments per sequence on H100, then reduce_segments. Above it, the step runs 2D. A prefill chunk, an image prefix or batch invariance also forces 2D.

The problem with Gemma 4 is which num_heads_kv the builder uses. It calls model_config.get_num_kv_heads(), which returns one number for the whole model, not the number for the layer group the builder is serving [25]. Gemma-4-26B has two: 8 KV heads in the sliding layers and 2 in the global layers [83]. The model-level value is presumably the config’s num_key_value_heads, which is 8. That gives 128 // 8 = 16, and since 16 is one of the default capture sizes, snapping leaves it at 16. Both layer groups split at batch 16 or below and run single-pass above it. This is our reading of the code. We haven’t checked it on a running server.

For the sliding layers, 16 is the right cutoff. At batch 16 their 2D grid is 16 × 8 = 128 CTAs, which is exactly vLLM’s target. The global layers miss. At the same batch they have only 16 × 2 = 32 CTAs, and their grid doesn’t reach 128 until batch 64. A 132-SM H100 fills at about 66 sequences if one CTA fits per SM. So from batch 17 to about 65 the global layers run single-pass on 34 to 130 CTAs, with part of the GPU idle. At long context those are the layers that read the most KV. If the builder used each group’s own count, the global layers would get a cutoff of 128 // 2 = 64.

Below the cutoff the error runs the other way, and it is small. The 3D kernel cuts every sequence into 16 segments, however long it is. A sliding layer reads at most 1,024 tokens, so each segment gets 64 tokens or fewer. That sits at the low end of the 64–128-token floor in §2.4, where the reduce pass costs about as much as the extra parallelism buys. We haven’t measured this for Gemma 4.

Layer group KV heads 2D grid at batch 16 2D grid reaches 128 CTAs at TRITON_ATTN behavior
25 sliding, ≤ 1,024 tokens 8 128 CTAs batch 16 splits at batch ≤ 16, the right cutoff; segments ≤ 64 tokens
5 global, full context 2 32 CTAs batch 64 splits at batch ≤ 16; runs single-pass at 17–65 on 34–130 CTAs, under one wave

On the default backend there’s only one useful knob. Raise flash_attn_max_num_splits_for_cuda_graph to 64 for concurrency-1, long-context serving, and watch tail latency [59]. On TRITON_ATTN, only a code change moves the global layers’ cutoff. A per-group KV-head count would raise it to 128 // 2 = 64.

9.5 Ranking the decision designs, and where this is heading

For mixed-length serving under full graphs:

  1. Data-driven schedulers that write into capture-sized buffers (FA3 device prep, FlashInfer’s CPU plan, the in-progress persistent Triton 3D) rank first.
  2. Host heuristics scaled to occupancy, with KV floors (AITER Triton, trtllm-gen’s one-wave rule), rank second.
  3. Gates that only look at shape (vLLM Triton) rank third.
  4. Unconditional policies (HIP always-split) rank last. But on RDNA a tuned Triton kernel beat it by only 1.05–1.13x geomean [54].

This ranking rests on how the mechanisms work and on NVIDIA’s opt-in experience. No head-to-head measurement exists beyond the IBM authors’ bundled static-grid result [44, 16, 26, 27].

Two trends point the same way. First, every 2026 PR we looked at replaced a constant with occupancy math: XQA’s cost model, AITER’s occupancy-sized splits, trtllm-gen’s wave-aware split, RDNA’s ~128-program target [4, 43, 3, 54]. Second, KV heads per GPU keep shrinking under MQA, MLA, heavy TP, and speculative and diffusion decoding. Each new few-query, long-KV workload of 2026 hit vLLM’s single-pass default. Spec-decode verify showed up as a bug report [1], and the diffusion canvas as an unmerged PR [52].

The likely end state is a persistent kernel with a static grid sized to the SMs. Each CTA takes fixed-size KV tiles from a schedule rebuilt every iteration. Short requests finish in one tile and write straight out. Long ones span several tiles and merge [32, 16, 26]. A deterministic plan would make it batch-invariant by design. And single-pass would live on as the simple one-tile case, decided per request from live lengths.
