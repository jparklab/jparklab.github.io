Neither single-pass nor split-KV decode attention wins in general; every vLLM backend implements the same inequality with different inputs. Split-KV wins when the single-pass launch cannot saturate HBM bandwidth: the unsplit grid (batch × KV heads per GPU × query tiles) falls below about one wave of the GPU, lands in a mostly empty final wave, or gives each thread block a KV walk too long to hide memory latency. Splitting is safe within about one wave of split blocks and at least 64–128 KV tokens per split. Deep in underfill a wrong single-pass has cost 5–49x at kernel level and a wrong split at most 1.21x[1, 2]; near one wave both errors cost about 1.1–1.4x[3, 4, 2]. Serving gains concentrate at low concurrency with long contexts and on ragged lengths. vLLM Triton decides from batch size, FA3 from live lengths on the device, FlashInfer from a CPU plan, XQA and trtllm-gen from max_seq_len; ROCm's HIP default always splits. CUDA graphs push decisions toward a capture-time worst case, and batch invariance forces single-pass in vLLM's FA, Triton and FlashInfer paths[5, 6, 7], costing 15–41% on ragged-length loads[8].

1. Single-Pass vs Split-KV Decode: Mechanics and Why the Choice Exists

1.1 Two decompositions of the same reduction

In the decode phase of LLM inference, each sequence contributes one new query token per iteration, or 1+K tokens when speculative decoding verifies K proposed tokens at once, and that query attends over the sequence's whole key/value (KV) cache. Kernels parallelize the work by handing independent pieces to CTAs (cooperative thread arrays, i.e. thread blocks; AMD calls them workgroups), which the GPU schedules onto its streaming multiprocessors (SMs; compute units, or CUs, on AMD). The two strategies differ only in how many independent pieces they create.

A single-pass kernel assigns one CTA per (sequence, KV head, query tile) and has it walk every KV tile serially with online softmax, keeping a running maximum, exponential sum and accumulator, and writing the normalized output once. vLLM's Triton 2D kernel launches exactly this grid, (total_num_q_blocks, num_kv_heads)[6]; FlashAttention's num_splits = 1, the legacy CUDA PagedAttention V1 and trtllm-gen's persistent fallback are the same design[9, 10, 11].

Flash-Decoding adds a third parallel axis, the KV length. It splits the cache into chunks, computes partial attention per chunk in parallel while writing "1 extra scalar per row and per split: the log-sum-exp", then reduces across splits, using that log-sum-exp (LSE) to rescale each contribution[12]. vLLM's Triton 3D kernel is this design: a grid of (total_num_q_blocks, num_kv_heads, num_par_softmax_segments) followed by a reduce_segments kernel that rescales each segment by exp(segm_max - overall_max)[6]. The second launch exists because "Triton does not provide a global barrier, this reduction requires launching a second kernel, introducing a trade-off between additional parallelism and launch overhead"[13]. The legacy CUDA paged_attention_v2 had the same two-kernel shape[14]; XQA and FlashInfer's persistent kernel fuse the merge instead[15, 16].

The merge is exact in real arithmetic: FlashInfer documents merge_state as producing output "equivalent to attention with merged KV-segment" from two partials and their float32 LSEs[17]. It is not bitwise exact in floating point, because summation order follows the split boundaries. vLLM PRs record greedy outputs diverging into "equally plausible continuations" when only the segment layout changed[18, 1], the root of the batch-invariance constraint.

1.2 Why the choice exists at all

Prefill has thousands of query rows to parallelize over; decode has one per sequence. As the Flash-Decoding authors put it, "if the batch size is smaller than the number of streaming multiprocessors (SMs) on the GPU (108 for an A100), the operation will only use a small part of the GPU"[12]. GQA (grouped-query attention, where several query heads share one KV head) packs a KV head's query heads into one CTA, so the grid scales with KV heads. Tensor parallelism (TP) shards those heads across GPUs, "further reducing the number of SMs activated per GPU during the decode phase"[19]. A Llama-70B-class model at batch 1 runs 8 CTAs on an H100's 132 SMs[20]; at TP8 the unsplit grid equals the batch size. Single-pass also hit walls: legacy vLLM forced V2 above 8,192 tokens to avoid shared memory shortage[10], and TensorRT-LLM forces multi-block mode when its sequence-proportional shared memory runs out[21].

2. The Cost Model: SM Occupancy, Reduction Pass, and Scratch Memory

Split-KV pays three costs for one benefit. The benefit is more CTAs in flight issuing memory loads, drawing more of the GPU's HBM (high-bandwidth memory) bandwidth. The costs are wave quantization (CTAs run in waves that fill every resident slot once, so a grid slightly larger than one wave pays for two), the reduction pass, and scratch memory for partial results.

2.1 One normalized variable

Let C₁ be the unsplit CTA count, batch × KV heads per GPU × ⌈query tokens × GQA ratio / BLOCK_M⌉, and W the unsplit wave fill, C₁ / (SMs × resident CTAs per SM). The production thresholds look unrelated, but each reads W plus a length term. FA3 returns one split at total_mblocks >= 0.8f * num_SMs and otherwise picks the smallest split count reaching 85% of the best wave efficiency[9]; upstream FA2 uses the same rule with the SM count doubled[22]. FlashInfer skips splitting when batch_size * gdy >= max_grid_size, with the grid size taken from measured occupancy[23]; trtllm-gen goes single-pass when oneWaveSplits = SMs / baseNumCtas is 1 or below[11]; AITER's Triton unified attention runs 2D when num_2d_prgms exceeds cu_count * 4[24].

vLLM's own Triton gate is the exception. It sets seq_threshold_3D = MIN_LAUNCH_GRID_SIZE_2D // num_heads_kv with MIN_LAUNCH_GRID_SIZE_2D = 128[25], an absolute CTA count rather than an SM-scaled one. Arithmetic from the constant and published core counts gives W cutoffs of about 0.97 on a 132-SM H100 and 0.42 on a 304-CU MI300X[26], 0.86 on a 148-SM B200[27], and 0.68 on a 188-SM RTX PRO 6000 (SM120, workstation Blackwell)[2]. If one CTA is resident per SM, the Triton default is tuned to H100 scale and switches to single-pass too early on larger parts. That is inference, and the one measured per-platform retune (gfx1201, open PR #60418) moved the threshold down instead.

2.2 The criterion is bandwidth, not idle SMs

W < 1 is a proxy. The criterion is whether the unsplit launch can saturate HBM, and three 2026 measurements show split-KV winning at W ≥ 1:

  • FlashInfer's SM90 fp8 XQA launcher dropped to one split once batch × KV heads exceeded about 50: "One CTA per SM cannot cover HBM latency, so large-batch long-context decode with few KV heads ran at 60-75% of bandwidth" on GH200[4].
  • On MI355X (gfx950, CDNA4) at context 8,192, AITER's partitioned V2 still beat single-pass V1 by 2.00x at batch 128 with 64 query and 8 KV heads at head size 128 (2.92x at head size 64), where V1's grid already holds 8,192 programs[28, 29]. Part of the gap is kernel design rather than split policy: V1 launches one program per query head (num_seqs * num_q_heads), by our reading of the dispatch code[29].
  • On SM107 (a Blackwell variant), growing a batch of 9K-token sequences from 208 to 209 requests made the call 1.39x slower for 0.5% more work, because the 209th CTA opens a nearly empty second wave[3].

Below saturation the speedup tracks parallel CTAs. On SM120 at 131k, 16 and 64 segments beat one 2D CTA by 15x and 48x, about 0.94 and 0.75 parallel efficiency by our arithmetic; at 4k context 16 segments gave only 6.3x (142.9 → 22.6 µs) because a launch-plus-reduce floor of about 22 µs dominates[18, 2].

The counter-case: FlashInfer's 2024 launch post found split-KV gave nothing on RTX 4090 and RTX 6000 Ada, where a fraction of the SMs already saturates GDDR bandwidth for a kernel that is not compute-bound, while it helped on an A100 where the CUDA-core kernel was compute-bound[30]. No source states the general rule, but these measurements jointly imply it: split when C₁ × (bandwidth one CTA can sustain) is below HBM peak. Memory type does not decide it: the 2024 result concerns a CUDA-core, non-GQA kernel. Modern GQA decode kernels on GDDR and LPDDR parts still gain heavily from splits at batch 1 and long context (R9700, RTX PRO 6000, gfx1151 and RTX 3090 results in 4.3 and 8.1)[18, 1].

2.3 Three cost terms, and which one bites

Wave quantization is the largest measured over-split cost. SGLang's AMD MLA (multi-head latent attention, DeepSeek's compressed-KV design) decode code records that crossing the one-wave split budget costs a whole wave: at batch 24 and 68k context, 21 splits (504 blocks) took 358 µs and 22 splits (528 blocks) took 528 µs, +47% for 4.8% more blocks[31]. The 208→209 cliff is the same effect hitting single-pass, and LeanAttention's critique of fixed-split decoding rests on the same partially full waves[32].

The reduction pass is cheap in isolation; what it drags along is not. Two isolated timings exist. A research kernel on an RTX 3060 merged in 0.014 ms against 1.263 ms of decode, about 1.1%, yet the same paper routed contexts below 16k back to FlashInfer because split and merge dominated there[33]. FlashInfer PR #4702 cut a B200 MLA decode call at 4k KV from 12.03 to 11.46 µs median, about 5%, by switching only the reduction from global memory to a thread-block cluster[34].

Production caps treat the reduction as real: XQA caps splits at round(sqrt(8n)) because otherwise the final reduction may dominate[35], and trtllm-gen allows at most ceil(window / (2*stepKv)) splits[11]. In trtllm-gen, 16 splits reduced through a CGA (a thread-block cluster sharing distributed shared memory) "beat 17-32 splits on the GMEM path whenever each CTA walks ≤ 4096 KV tokens"[36]. The reduce turns material when per-split work shrinks toward it: on gfx950 the measured crossover is 64–80 KV tokens per segment, and a gate at 80 had a worst case of −1.0% over 250 configurations against −60.9% for a 256-token gate[37]. FlashDecoding++'s widely quoted 18.8% measures "synchronized partial softmax update" overhead, not the combine pass[38].

Scratch memory is a capacity and CUDA-graph problem more than a time problem.

  • FA3 allocates fp32 out_accum of shape [num_splits, batch, heads, seqlen_q, head_dim] plus softmax_lse_accum, with num_splits ≤ 256[39], which is why vLLM fixes FA's split count under full graphs so the buffers can be allocated at capture[5].
  • FlashInfer's persistent scheduler bounds partials at 2 × #CTA[16].
  • XQA reserves 6,000 sub-sequences, about 12 MB for llama v2 70b[40].
  • vLLM Triton's preallocated partials cost +24 to +42 MiB per rank for MiniMax-M3 TP8[2].
  • ROCm's HIP path allocates per call, sized by the batch's max_seq_len; by our arithmetic from its partial shapes, batch 256 with 32 query heads, head size 128 and 32k context needs about 277 MB per layer call[41].

Capped-split scratch is small next to a multi-gigabyte KV cache, the HIP path's is not; for all of them the binding constraint is that graph-replayed buffers must be sized at capture for the largest split count.

Correctness surface is the cost kernel benchmarks never show. In 2025–2026 the split reduction path produced at least four bugs:

  • FA2's varlen combine wrote every batch to the same output address when a real split occurred[42].
  • vLLM Triton's 3D path corrupted rows whose keys were all masked within a segment, with a maximum absolute error of about 4[1].
  • #56148 fixed the same -inf-clamp hazard for empty segments[2].
  • AITER's HIP persistent-split reduce gives wrong outputs above 32 partitions, with relative error up to 2.8 at 33 splits[43].

Single-pass kernels have no cross-program merge and no equivalent bug class.

2.4 The rule and its two guards

Under-splitting wastes memory parallelism in proportion to how far the grid sits below saturation; over-splitting costs a fraction of a wave plus a cheap merge until one of two guards is violated: about one wave of split CTAs, and a floor of about 64–128 tokens per split. The measured wave cliffs come from opening a partial wave, not from multi-wave grids at long KV.

3. vLLM Triton Unified Attention: 2D vs 3D Kernels

The Triton backend (TRITON_ATTN) is the one place where vLLM itself makes the split decision: a launcher gate picks the 2D (single-pass) or 3D (segmented, plus reduce_segments) kernel per batch. An April 2026 talk calls it the default for AMD deployments[26], but vLLM main ranks it last among ROCm backends, behind ROCM_ATTN, which merged PR #36702 put first[47]; it is chosen when those decline a shape. Nearly every change to its boundary came with a measurement.

3.1 The gate, as of vLLM main (October 2026)

The launcher runs 2D if scratch is missing or undersized; if max_seqlen_q > 1 and the query exceeds MAX_3D_QUERY_LEN or masking is non-causal; if num_seqs * cdiv(max_seqlen_q, BLOCK_Q) > seq_threshold_3D; or if batch invariance is enabled[6]. Because the query test reads the batch maximum, an iteration carrying a chunked-prefill chunk runs all its decodes on 2D, whereas FlashInfer plans decode rows separately[7] and FA3 handles mixed varlen batches in one call[5]; no source measures the serving cost. On main, MAX_3D_QUERY_LEN is 8 for the unified kernel[6, 25] (the DiffKV variant, fixed by #59085, admits verify widths up to 16[48, 1]); PR #56148's final commit text states that admission is "widths 2..5 on every platform; width >= 6 uses 2D", enforced beyond that constant[2].

The threshold is 128 // num_heads_kv. Under full decode graphs it snaps to the CUDA Graph capture size closest to self.seq_threshold_3D, so each captured graph covers one kernel[25]. PR #28306 added the snap with a guard that resets the threshold to 0 (2D only) if snapping would push it above 4x its unsnapped value; a reviewer called 2D-only a safe choice for CUDA graph compatibility[49]. The 3D kernel fixes the segment count per sequence, so short sequences produce empty segments that reduce_segments masks[6]. The count is 16, rising to 64 on SM120 when 16 segments would underfill the GPU[25]. The gate reads batch size, KV heads, query width and capture sizes; it never reads KV length.

3.2 How the boundary moved, PR by PR

PR #19152 (June 2025) introduced 3D with 16 segments and reported "more than a factor of two" end to end at batch 1 with long outputs on H100[50]; the authors' paper confirms 3D was "only launched for decode attention on small batches involving longer sequences"[51]. Until October 2026, however, any max_seqlen_q > 1 forced 2D, so a single-stream verify ran "(1, 4) = 4 CTAs on a 70-SM GPU, each CTA sequentially walking the entire KV history", a 19.6–48.7x kernel penalty at 65–67K KV; on gfx1151 (an RDNA client GPU) a verify iteration took 581 ms against 92 ms without speculation until the 3D fix brought it to 162 ms[1].

PR #56148, merged 2026-10-13, admitted short multi-query batches to 3D through the same shape-only gate. On a width-6 MiniMax-M3 TP8 shape at 128k, measured before admission was narrowed to widths 2..5, the attention kernel ran roughly 10x faster on SM120 and H200, and the worst admitted shape lost 1.21x[2]. PR #58482 (merged 2026-10-01) made SM120's segment count occupancy-adaptive after a constant 64 regressed Llama-3.1-8B with EAGLE3 (a speculative-decoding head) at concurrency 8 and 768-token prompts to 0.962x tokens/s, because "Once the grid fills the GPU, more segments only add partial-result traffic and reducer work"[18]. Over 176 SM120 verify shapes timed for #56148, 64 segments beat 16 by 1.15–3.6x from 8k context and lost only at 2k context, by at most 6%[2].

Two widely cited PRs are not shipped behavior: PR #46724 (unmerged) reported 7.30x for a diffusion-LM canvas at 24 queries and 92K KV on B200, shrinking to 2.46x at four sequences "as more sequences fill the grid"[52]; PR #45450 (open, superseded in practice by #56148) reported B300 gemma-4-31B TPOT (time per output token) falling from 13.42 to 3.12 ms at batch 1[53].

RDNA tuning found the 16-segment constant wrong in both directions, too few programs for one request on a 32-CU part and too many tiny ones for larger batches; PR #60418 (open) proposes halving the gfx1201 threshold to 64 // num_kv_heads after a 3,888-batch forced-2D/forced-3D sweep[54]. PR #56276 raised gfx1151 segments to 32 for MQA (multi-query attention, one KV head), improving end-to-end latency 12.7–15.7% at batch 1 with an 8k prompt while an 8-KV-head control stayed flat[55]. PR #61646 (open, R9700) splits only sliding-window layers[56].

The gate is right about the entry condition and blind to the cost model's other two axes: with no KV floor it splits short contexts where the reduce launch dominates, and with no SM scaling it probably under-splits large parts. It is a good default for low-batch long-context decode and verify and a small tax at short context. The persistent 3D kernel the IBM authors describe, with a static grid sized from SMs per KV head and CPU-generated scheduling tensors, is the better end state because real lengths would drive the split[26].

4. FlashAttention and num_splits

FlashAttention exposes split-KV as one integer, num_splits: 1 is single-pass, more adds a separate combine kernel. Upstream FA3 picks the value with a host heuristic and refines it on the device for variable-length batches; vLLM sets a cap and decides when the heuristic may run. On Ampere and Hopper FLASH_ATTN is first in vLLM's backend priority, so this code decides on a default H100 deployment[57].

4.1 The upstream heuristic

FA3's get_num_splits packs GQA into the query dimension and, for dynamic-split varlen batches, deliberately computes an upper bound: We assume the case where there's 1 long sequence and the rest are short, i.e. pretending that batch = 1[39]. The heuristic returns one split at W ≥ 0.8, one split if num_n_blocks <= 4 (we never split for hdim = 128 and seqlen_k = 512), and otherwise the smallest split count at ≥85% of the best wave efficiency, on the grounds that excess splits add HBM traffic[9]. The 512-token guard has a small measured price: on H100 with a Llama-70B shape at batch 1 it leaves 8 CTAs on 132 SMs, and three splits save about 2.5 µs, shrinking to roughly 1.0–1.05x without precomputed scheduler metadata[20], a minor defect.

4.2 What vLLM overrides, and who actually decides

vLLM's FA backend (flash_attn.py, main as of 2026-10-25) handles three cases[5]. Eager batches get max_num_splits = 0, use FA3's heuristics, not CG compatible. Batches within the full-graph capture range get flash_attn_max_num_splits_for_cuda_graph, default 32[58], so buffers are pre-allocated at capture, plus a persistent scheduler_metadata buffer refreshed in place. Under VLLM_BATCH_INVARIANT, max_num_splits = 1 and the AOT (ahead-of-time) schedule is disabled because the schedule varies with max_seqlen_q/k.

The cap is not the split count. FA3's prepare_varlen_num_blocks kernel computes, on the device at every replay, blocks_per_sm = ceil(total_blocks * 1.1 * num_head / num_sm) and num_splits_dynamic = min(ceil(num_n_blocks / blocks_per_sm), num_splits_static), falling back to one split above batch 992[44]. The live decision belongs to FA3's device scheduler, which sees actual lengths bounded by vLLM's cap. Read from the code[44, 5] and unverified at runtime, it is the only production design surveyed whose split count stays data-driven inside a captured graph. vLLM turns it off for spec-decode proposers as well as under batch invariance.

Two unmeasured inferences follow. The device path does not reapply the num_n_blocks <= 4 guard, so with 4 KV blocks, 8 heads and 132 SMs it yields four splits where eager FA3 would run one[44, 9]. And because blocks_per_sm sums work across the batch, the split adapts to batch composition, which is exactly what batch invariance forbids[5].

4.3 Is the cap right?

The original default of 16 came from upstream FlashAttention when PR #25274 made it configurable. Its DeepSeek-V3 TP8 FLASH_ATTN_MLA run (8 sequences, about 32k-token inputs) showed median TPOT of 34.75, 32.48 and 30.98 ms at caps 16, 32 and 64 (−11%; mean 61.00 → 44.26 ms), but P99 TPOT rose from 136.90 to 178.50 ms, throughput was non-monotonic, and the 20-request runs generated different token counts[59]. The evidence for raising the cap is directional and noisy.

FA2's varlen paged path treats split-KV as opt-in: a fix that re-enabled splitting for every paged call was closed after splits of 2 and 4 ran slower than splits=0 across KV lengths 512–16384, and a vLLM-fork PR proposing splits only on explicit request (closed as a duplicate) cited −13.8% to −18.9% verify latency at batch 1 on an RTX 3090[42].

The cap rarely binds: by the device formula, one 32k sequence with 8 KV heads on 132 SMs gets about 15 splits. A cap of 32 therefore binds only when batch × KV heads per GPU is below about 4, as with MQA, MLA or TP-sharded GQA at batch 1–3 (our inference from[44]). Raising it toward 64 is justified there, with tail latency monitored, on the strength of one noisy MLA run[59].

5. FlashInfer and the TRT-LLM Kernels (XQA, TRT-LLM-gen)

FlashInfer is a kernel library with native decode kernels and a planner that runs on the CPU before each launch. It also wraps two NVIDIA TensorRT-LLM families: XQA, a decode kernel specialized for grouped- and multi-query attention, and trtllm-gen, TensorRT-LLM's generated attention kernels for Blackwell.

5.1 Routing: vLLM picks the kernel, the kernel picks the split

On Blackwell FLASHINFER is first in vLLM's backend priority[57]. Inside it vLLM selects the decode kernel statically, per the code comment The decode kernel must be selected statically for FULL cudagraph capture: XQA on SM90 and SM12x, trtllm-gen on the SM100 family, and FlashInfer's native kernels for unsupported layouts and pre-SM90 parts[7]. supports_trtllm_attention returns False under VLLM_BATCH_INVARIANT or without NVIDIA artifactory access[60].

5.2 FlashInfer native: two planners

The non-persistent BatchDecode planner (FlashInfer main, October 2026) goes single-pass when batch_size * gdy >= max_grid_size and otherwise binary-searches the smallest page chunk (at least 128 tokens) that keeps CTAs within one wave; without graphs it falls back to single-pass when nothing would split, but when using CUDAGraph, we always use partition-kv kernel, padding the batch to max_grid_size / gdy[23].

The persistent scheduler from the MLSys 2025 paper splits only requests "whose KV length exceeds the total KV length divided by the number of CTAs" and lets short requests write through without a reduce; both planners run on the CPU every iteration, outside the captured graph, into fixed-address, max-size workspace[16]. The paper's only scheduler ablation (H100, Llama-3.1-8B in SGLang) shows load balancing moving inter-token latency (ITL) from 9.16 to 8.96 ms on ShareGPT but from 13.89 to 8.63 ms on uniform 4k–16k inputs, bounding the value of the split logic rather than comparing split with single-pass[16].

5.3 XQA: split-happy, keyed to max length, merged in-kernel

XQA's split count (TensorRT-LLM main, October 2026) is historyLength / 128, capped at round(sqrt(8n)), reduced only if the grid exceeds 8 waves, and bounded by the 6,000-sub-sequence workspace. MLA gets one split, and the spec-decode variant skips splitting when batchSize > 32 || historyLength < 2048 and otherwise asserts at most one wave[35, 40]. Each CTA writes row max, row sum and partial output to scratch, and only the CTA that performs the multi-block merge may write the output, so XQA pays no second launch[15].

Because historyLength is the batch maximum, short requests in a mixed batch inherit the long request's split count; for one KV head per GPU at history 8,192 and batch 1, the code yields n = min(64, round(sqrt(512))) = 23 splits[35]. At batch 128 and history 4,096 it still yields 8 splits with one KV head and 2 with four, so XQA keeps splitting up to about 4x the SM count, against TensorRT-LLM's documented batch × heads < SMs guidance (derived from the code)[35, 21]. TensorRT-LLM has had multi-block "turned on by default starting from TRT-LLM 0.13"[21], and NVIDIA claims "up to 3.5x more tokens per second" on HGX H200 at low batch and long sequences, without a table[19].

The XQA problem actually measured is under-splitting. FlashInfer PR #4904 (open) replaces the SM90 fp8 launcher's collapsing rule with a cost model, ceil(waves) * (tiles / split + overhead) + merge * split, gaining 1.38x at batch 32 and 32,768 KV and 1.78x with random lengths at batch 64 on GH200 under CUDA graphs; its one regression, 0.92x at batch 128 and KV 512, came from splitting 8-tile sequences three ways[4].

5.4 trtllm-gen: one wave, persistent fallback, opt-in beyond

FlashInfer's launcher hard-codes multi-CTA-KV mode for generation[61]. The split is min(tunedMax, max(1, SMs / baseNumCtas)) with tunedMax = ceil(window / (2*stepKv)); at 1 or below the kernel switches to MultiCtasKvMode::Disabled and a persistent tile scheduler, trtllm-gen's single-pass[11]. The rule sees mMaxSeqLenKv, not per-request lengths. 6. ROCm Decode Attention Paths

On AMD GPUs vLLM tries its attention backends in priority order, and the first that supports the model's shape wins; in vLLM main the non-MLA order is ROCM_ATTN → ROCM_AITER_FA → ROCM_AITER_UNIFIED_ATTN → TRITON_ATTN[63]. AITER is AMD's kernel library, with decode kernels in hand-written assembly (ASM), Triton and Gluon (a lower-level Triton dialect), each encoding its own split policy. MLA models use a separate backend family on both vendors (FLASHINFER_MLA first on NVIDIA, AITER MLA here), covered only where it reuses XQA, trtllm-gen or SGLang's AMD MLA kernel. FlashMLA plans num_splits by a rule the sources do not document[57, 63].

6.1 Four policies behind one platform (vLLM and AITER main, October 2026)

  1. HIP custom paged attention (ll4mi, the ROCM_ATTN default): always split. The partition is a compile-time 256 tokens, the grid is (num_seqs, ceil(max_seq_len/256), num_kv_heads), workgroups past a sequence's end exit early, and a separate reduce always follows with no single-partition skip[46]. Scratch is allocated per call from max_seq_len[41], and the only gate is capability (head size, block size, GQA ratio, context length), not occupancy[63].
  2. AITER FA decode: split below 2 × CUs. paged_attention_common picks the ASM kernel only at head size 128, where int8 KV or high_precision == 2 force it and otherwise num_seqs * num_heads > 2 * cu_num decides; every other case gets the 256-token HIP split kernel[64, 65]. On a 304-CU MI300X the switch falls at 608, about batch 19 for 32 query heads, so at head size 128 the split kernel never meets the large batches where its reduce would cost most.
  3. AITER Triton unified attention: CU-scaled. It runs 2D for sliding windows (SWA), for max_seqlen_k <= 512, or when 2D programs exceed 4 × CUs; on gfx1100 the code documents a tighter crossover of cu_count / 4 because segment traffic and the reduce cost more than the added parallelism[24]. The segment count collapses to one when each program's share of CUs is small[45].
  4. AITER Triton pa_decode: V1 vs V2. Legacy dispatch chose single-pass V1 when max_seq_len <= 8192 and (one partition, or num_seqs * num_q_heads > 512)[29], copying vLLM v0.6.0's CUDA rule, itself a shared-memory workaround[10].

6.2 What the ROCm measurements say

AITER now has measured split wins at W well above 1:

  • PR #5859 (merged 2026-10-07) made gfx950 select V2 whenever the context spans more than one 1024-token partition, for 2.00–5.29x on the shapes that switched (geomean 3.13x) while shapes already on V2 stayed at 0.99–1.02x[28].
  • PR #6453 raised the Gluon persistent-split cap from 8 to 32 for small grids: 2.25x at batch 1 and 32k, 1.343x geomean over 72 shapes, with no shape slower[66].
  • PR #6434 (open) sizes splits from kernel occupancy and aligns them to whole 256-token partitions: 1.23x geomean on mixed lengths and 1.15x on equal lengths over 2,100 points, with 32 kept as a correctness cap because the reduce gives "relative error up to 2.8 at 33 splits"[43].
  • vLLM PR #62476 (closed unmerged, single run) routed gfx950 decode-width batches from AITER's Gluon kernel to its Triton split-KV kernel because the Gluon "KV split leaves the launch on too few workgroups", raising MiniMax-M3 TP4 EAGLE3 throughput from 720.8 to 985.8 tok/s at about 135K input[67].

The only A/B against the HIP decode kernel is on RDNA and confounded by tile tuning: in PR #60418 (open), a tuned, occupancy-gated TRITON_ATTN beat it by 1.05x geomean at 1k context rising to 1.13x at 128k (worst 0.91x), and by 1.02–1.04x at 1 KV head per GPU against 1.12–1.17x at 8, the gradient expected if the unconditional reduce costs more as the unsplit grid fills[54]. The tax is real but small there; on CDNA at batch ≥ 256 nothing isolates it, and the closest evidence is the MI300 Triton result, where the split kernel lost at short outputs "as the former includes an additional launch of a reduction kernel", a loss the static-launch-grid kernel under full HIP graphs removed[51].

The large published ROCm backend gains reflect routing more than split policy: ROCM_AITER_FA roughly halves spec-decode TPOT against ROCM_ATTN (11.10 to 5.62 ms at concurrency 1 on 8×MI300X) while non-spec decode was unchanged within ±1–5%[68], and the vLLM ROCm blog attributes ROCM_ATTN's 2.7–4.4x lower throughput on Qwen3-235B to unsupported KV head sizes "forcing it to fall back to Triton decode kernels"[69].

7. CUDA-Graph and Batch-Invariance Constraints

A CUDA graph records a sequence of kernel launches once and replays it with a single CPU call, removing most launch overhead in decode; vLLM captures one graph per batch size from a configured list. Replay freezes grid dimensions and kernel arguments, so a split decision that depends on live lengths must be made at capture or by a scheduler that writes into fixed, pre-sized buffers. Batch invariance is stronger than determinism: a request's output must be bitwise identical regardless of which other requests share its batch.

7.1 CUDA graphs: the decision moves to capture time and goes blind

The IBM authors spell out the consequence: under graphs "we always launch as many Triton kernels as we would need for the longest request possible", and the surplus waves "outweighs the saving of the launch overhead in nearly all cases"[51]. Their static-grid kernel under full graphs ran about 6% faster than the partial-graph split kernel on H100 and up to 1.99x faster on MI300, at batch 1 with grid, graph mode and heuristics bundled[51].

An H100 report on Qwen3-8B found that under full graphs the decode launch is fixed at capture with max_seq_len set to max_model_len, so a context-length guard is in effect a max_model_len guard[71]. The trtllm-gen code says the same of itself: The split only sees max_seq_len, so short or similar KV lengths can be slower[11]. AITER PR #6434 traced 47 of its 57 regressions to 1K–2K contexts, where callers that fix the grid at capture cannot pass max_context_length[43], and vLLM PR #58650's gfx950 window-1024 split gain held in eager mode but regressed under CUDA graphs[37].

Under uncertainty about real lengths most backends split, which the cost asymmetry justifies until the blind guess goes past one wave, as trtllm-gen's 0.57x at uniform 8k under a 1M-capture graph shows[27]. FA3's device scheduler and FlashInfer's plan keep the decision live and avoid both errors, at the price of a scheduler and max-size buffers.

7.2 Batch invariance collapses the boundary to never split

Thinking Machines states the requirement: "the reduction order for each element must be fixed regardless of the batch-size of the kernel"[72]. FlashInfer's scheduler is deterministic run to run, with no atomics[16], yet its balanced scheduling "chooses the largest split-size that can still saturate all the GPU's cores", so the reduction depends on the batch[72]. Every vLLM split rule except HIP's fixed-size partitions depends on batch composition, and all of vLLM's invariance overrides land on single-pass:

  • FA sets max_num_splits = 1 and turns off the AOT schedule[5].
  • Triton forces 2D with or is_batch_invariant[6].
  • The TRT-LLM kernels are disabled[60].
  • FlashInfer native sets decode_fixed_split_size = 2048 and disable_split_kv = True[7], but disable_split_kv takes precedence in the planner (one chunk of numeric_limits<int64_t>::max()), so the 2048 never takes effect[23].

rocm.py adds no attention override under batch invariance, so whether ROCM_ATTN still splits there, and stays invariant, is unverified[63]. PyTorch documents the same contract: disabling split-KV via num_splits restores batch invariance because the split decision depends on the longest sequence in the batch[73].

The principled alternative: "instead of fixing the # of splits, we fix the size of each split", so KV 1,000 becomes 256 + 256 + 256 + 232[72]. On a length-sized grid it does not survive CUDA graphs, because the CTA count then varies with length; FlashInfer's code warns that with fixed_split_size compatibility with CUDA graph is NOT guaranteed, while disable_split_kv exists for determinism in CUDA Graph[74]. The PR that introduced fixed split size concluded "It's better to disable split-kv for cuda graph"[75]. SGLang's 2048 decode split is "only effective when cuda graph is not enabled"[76], and its FA3 backend fixes num_splits to 1[77]. Its Triton backend is the exception: deterministic mode keeps fixed 256-token splits with per-sequence counts on a (batch, head, MAX_KV_SPLITS) grid[31], documented as CUDA-graph compatible[78]. The introducing PR, however, tested only without graphs and no source reports its cost[79].

7.3 What giving up split-KV costs, and where

Only one source isolates the cost: in high-concurrency offline throughput runs, CoRun reports that disabling split-KV costs 15–41% when prompt lengths vary and 1–9% when they are similar, because ragged batches offer uneven attention work[8]. Whole-mode overheads are larger and not split-specific: SGLang's deterministic mode averages a 34.35% slowdown against Thinking Machines' 61.5%[80], and Thinking Machines' vLLM run took 26 s by default, 55 s deterministic and 42 s with an improved attention kernel[72]. vLLM's batch-invariance documentation (beta) warns only of a possible performance impact[81]. The measured driver is length heterogeneity, not concurrency. Low concurrency with long contexts is a second regime where the cost model predicts a large tax that no source has isolated. RL rollouts and evaluation replays, the workloads that most often want determinism, can hit both[8, 72].

A graph-safe fixed-split design is closer than vLLM's code suggests: SGLang's Triton backend ships one, and ROCm's HIP kernel already uses fixed 256-token partitions on a max_seq_len-sized grid with early exit. Each request's partition boundaries are therefore independent of its neighbors, which is the Thinking Machines prescription on a capture-compatible grid[46]. The caveat is that the reduce's template instance (NPAR_LOOPS) is chosen from the batch-maximum partition count, and whether that changes per-request summation order needs checking[46]. Single-pass under batch invariance is a stopgap, not best practice.

8.3 What the numbers jointly say

End-to-end gain is approximately attention share × (1 − 1/kernel speedup), Amdahl's law applied to these measurements. Attention's share of iteration time is large only when context is long and the batch small, exactly when the unsplit grid underfills. That is why ~5–49x kernel wins become 1.5–2x at concurrency 1 and 1–3% at concurrency 10 or short context with homogeneous lengths. Length skew is the second regime where splitting pays at moderate-to-high concurrency (CoRun, FlashInfer's scheduler ablation, trtllm-gen #6331, #3379)[8, 16, 27, 62].

The model reproduces the H100 report: a roughly 25% kernel gain on a call of about 14 µs saves about 3.5 µs per layer. Across Qwen3-8B's 36 layers (a model fact assumed here, not stated in the source), that is about 0.13 ms of a 4.6–4.7 ms ITL, or about 2.7%, against a measured +2.61%[71]. The #56148 c10 result has a second limiter: on B300 only three dense layers plus the EAGLE3 head use unified_attention, and the PR's c10 equivalence check failed its ±3% rule at n=1 before passing at n=4, so c10 differences sit near run-to-run noise[2].

The Flash-Decoding headline needs a correction. Its own table shows Flash-Decoding 6.2x faster than FlashAttention 2.0.9 even at batch 256 and sequence length 256, where the grid is already full[82]. Part of the famous 2300.6 → 64.4 µs therefore reflects FA 2.0.9's inefficiency at query length 1, not split-KV alone; the original post notes that "all approaches perform similarly for small prompts"[12].

  • any independent, non-author serving reproduction.

9. Recommendation: When Each Strategy Wins

9.1 The rule

  • Split when W < ~1 and per-sequence KV is at least ~1–2k tokens; when W is 1–1.5 and KV per sequence is large (≥ ~4 MiB, the #6522 threshold); when skewed lengths make one long request the critical path; and for spec-decode verify at long context.
  • Size the split to fill about one wave. Deep in underfill, err toward more splits; near one wave, where both errors cost about 1.1–1.4x, let the wave guard decide. Never take the one extra split that opens a partial wave; keep each split at ≥ ~64–128 tokens, aligned to page or partition boundaries; prefer cluster reductions at ≤ 16 splits when each CTA walks ≤ 4,096 tokens.
  • Stay single-pass when W ≥ ~1.5 with moderate KV, when KV ≤ ~512–1k tokens, for legacy CUDA-core kernels on consumer GPUs, and whenever batch invariance is on.

The burden of proof sits on single-pass for long-KV, low-batch, TP-sharded, verify and ragged-length workloads, and on split-KV for homogeneous short-context or full-grid serving.

9.3 Four changes vLLM should make

  1. Replace Triton's absolute MIN_LAUNCH_GRID_SIZE_2D = 128 with about one wave of 2D programs (SMs × resident CTAs per SM, or AITER's 4 × CUs) plus a floor of 64–128 KV tokens per segment, validated per platform, and generalize the SM120 64-segment rule into a segments-per-SM target[25, 24, 37, 23, 54].
  2. Raise flash_attn_max_num_splits_for_cuda_graph toward 64 where batch × KV heads per GPU is below about 4, with tail-latency monitoring; FA3's device scheduler already backs off at full grids[59, 44].
  3. Build a graph-safe decode path for batch-invariant mode with 256-token, page-aligned splits on a worst-case grid with early exit, as HIP ll4mi already does[46, 72], alongside a batch-free split bucket like the one SGLang's Triton backend uses for deterministic inference[31].
  4. Measure the ROCM_ATTN reduce tax on CDNA at batch ≥ 256 before keeping the always-split HIP path first in ROCm priority, a place PR #36702 granted without a benchmark[47] and open PR #60418 would reverse on RDNA[46, 54].

9.4 Worked example: Gemma-4-26B-A4B on H100

Gemma-4-26B-A4B mixes two attention shapes. Of its 30 layers, 25 use a 1,024-token sliding window with head size 256 and 16 query / 8 KV heads; 5 are global layers with head size 512 and 16 query / 2 KV heads, over contexts up to 262,144 tokens[83]. At long context the global layers carry most of the attention traffic, so their split decision is the one that matters.

On Hopper, vLLM selects the TRITON_FLASH_ATTN composite for Gemma 4, with FA4 for causal prefill and decode[57]. vLLM passes FA4 num_splits = 0 (the kernel's heuristic) in eager batches, the cap of 32 under full graphs, and 1 under batch invariance; on SM90 it precompiles the head-512 kernel with split variants for 1, 32, 64, 128 and 256 splits[5]. FA4's own heuristic is not in the sources. Using FA3's device formula as a proxy[44], one global-layer sequence wants about 132 / (1.1 × 2) ≈ 60 splits, so the cap binds only at concurrency 1; at batch 2 the formula gives about 30. With 2 CTAs per sequence, the unsplit global grid fills one wave of a 132-SM H100 at about 66 sequences if one CTA is resident per SM, or about 53 under FA3's 0.8-wave rule (our arithmetic).

Forcing TRITON_ATTN changes the picture. The builder computes seq_threshold_3D = 128 // num_heads_kv from the model-level get_num_kv_heads(), not per layer group[25]. For Gemma 4 that is presumably the sliding layers' 8 KV heads, giving 16, which the default capture sizes keep at 16; H100 uses 16 segments[25, 6]. That model-level value is our reading of the code, unverified at runtime.

Layer group FA4 (default) TRITON_ATTN

9.5 Ranking the decision architectures, and where this is heading

For mixed-length serving under full graphs:

  1. Data-driven schedulers writing into capture-sized buffers (FA3 device prep, FlashInfer's CPU plan, the in-progress persistent Triton 3D) rank first.
  2. Occupancy-scaled host heuristics with KV floors (AITER Triton, trtllm-gen's one-wave rule) rank second.
  3. Shape-only gates (vLLM Triton) rank third.
  4. Unconditional policies (HIP always-split) rank last, though on RDNA a tuned Triton kernel beat it by only 1.05–1.13x geomean[54].

The ranking rests on mechanism and on NVIDIA's opt-in experience; no head-to-head measurement exists beyond the IBM authors' bundled static-grid result[44, 16, 26, 27].

Two trends point the same way. Every 2026 PR surveyed replaced a constant with occupancy arithmetic: XQA's cost model, AITER's occupancy-sized splits, trtllm-gen's wave-aware split, RDNA's ~128-program target[4, 43, 3, 54]. KV heads per GPU keep shrinking under MQA, MLA, heavy TP, and speculative and diffusion decoding, and each new few-query, long-KV workload of 2026 reached vLLM against a single-pass default, spec-decode verify as a bug report[1] and the diffusion canvas as an unmerged PR[52].

The likely end state is a persistent kernel with an SM-sized static grid in which each CTA takes fixed-size KV tiles from a schedule rebuilt every iteration: short requests finish in one tile and write through, long ones span several and merge[32, 16, 26]. A deterministic plan would make it batch-invariant by construction, and single-pass would survive as the degenerate one-tile case, decided per request from live lengths.
