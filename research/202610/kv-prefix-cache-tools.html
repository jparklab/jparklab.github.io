The open-source KV cache stack has five layers, joined by the engine’s connector API and its KV-event streams: engine prefix caches (vLLM Automatic Prefix Caching, SGLang RadixAttention, TensorRT-LLM block reuse); offload and shared stores (vLLM’s OffloadingConnector, SGLang HiCache, LMCache, Mooncake Store, NVIDIA Dynamo KVBM, AIBrix, FlexKV, DeepSeek 3FS); transfer libraries (NIXL, Mooncake Transfer Engine); cache-aware routers (llm-d with the Gateway API Inference Extension, the Dynamo KV router, the SGLang Model Gateway, Ray Serve); and platforms that package them (KServe, llm-d, Dynamo, vLLM production-stack). Teams usually build in the same order: engine cache, then a per-replica CPU tier, then cache-aware routing blended with load, then a shared pool or peer fetch. Each step pays only when the prefill it avoids costs more than fetching the KV or queueing behind a busy replica. Most headline multiples come from the projects or vendors themselves. Independent 2026 studies find SSD and remote-tier restores losing to recompute below roughly 8K-17K tokens, while PCIe 5 CPU tiers clear the bar; no one has independently replicated the routing or pool claims.

1. The KV and Prefix Cache Problem in LLM Serving

1.1 What the cache holds

During prefill (the compute-bound pass over the prompt), each layer computes key and value tensors for every token; decode reads them back for each new token. PagedAttention (2023) found about 30% of an A100’s memory holding KV for a 13B model and, by managing it in fixed-size blocks like operating-system pages, gained 2-4x throughput [1]. SGLang’s RadixAttention made reuse across requests automatic with an LRU-managed radix tree of KV [2].

Prefix caching reuses KV computed for an identical leading token sequence instead of recomputing it [4]. Attention is causal, so a block is reusable only if every earlier block is present; llm-d’s indexer scores a pod holding B3 and B4 without B0-B2 at zero [3]. Engines therefore key blocks by a hash chained to the preceding prefix, and only exact token-prefix matches hit [3, 4, 5]. Where it applies the gains are large: DeepSeek’s API bills a hit at $0.014 per million tokens against $0.14 for a miss [6].

1.2 How much reuse real traffic offers

Alibaba Bailian traffic has an ideal (infinite-capacity) hit rate of 62% and 54% on two traces [7]. Alibaba coding-agent traces reuse more than 80% of KV blocks, about 90% of them within roughly 100 s [8], and a one-year Chutes trace finds about 80% of repeat arrivals from a user-model pair within 10 seconds [9]. The reuse is fragile: in XPerf, mini-SWE-agent’s hit rate fell from 91% to below 4% as load rose and eviction dropped idle context [10], and context truncation halved one LMCache customer’s hit ratio [11]. Capacity bites too: 100K tokens of Kimi-2.5 FP8 context take about 3.8 GB of KV [12], a 128K-token Qwen3-32B request about 32 GB [8].

1.3 The five-layer stack

Beyond one replica, or once the working set outgrows HBM (GPU high-bandwidth memory), three problems appear: capacity (idle conversations are evicted), locality (a cache-blind balancer scatters related requests) and movement (KV must cross PCIe, NVLink, RDMA or storage links for offload, sharing, and prefill/decode (P/D) disaggregation, which runs the two phases on separate instances). The tools meet at two seams: vLLM’s KV connector interface, which hosts LMCache, Mooncake, NIXL, FlexKV and the native offloader [13], and engine events announcing stored and removed blocks, which routers index [3].

2. Engine-Level Prefix Caching

An engine prefix cache lives inside one serving process: it hashes each fixed-size token block with its prefix, attaches matching blocks to new requests, and keeps unreferenced blocks in an eviction queue. All three major engines enable it by default and differ in index, eviction, hybrid-model handling, isolation and exported events.

2.1 vLLM Automatic Prefix Caching

APC has been on by default since the V1 engine (January 2025), costing under 1% throughput even at a 0% hit rate [14]. Blocks are keyed by a chained hash of parent hash, block tokens and extras such as LoRA ID, multimodal hash and cache salt; only full blocks are cached [4]. The xxhash seed is randomised per process, so cross-instance sharing needs a common PYTHONHASHSEED [15]. For hybrid models, which mix sliding-window, state-space or linear-attention layers with full attention, the Hybrid KV Cache Manager keys blocks by (block_hash, group_id) and intersects per-group hits, so a sliding-window (SWA) group needs only its last window; the docs call it early-stage [16]. The per-request cache_salt, added after CVE-2025-46570 showed prefixes leaking through timing, is the isolation primitive the rest of the stack inherits [17].

2.2 SGLang RadixAttention and the Unified Radix Cache

SGLang schedules longest-shared-prefix first over its radix tree, reporting up to 6.4x throughput over contemporary systems [2]. Its August 2026 Unified Radix Cache is one token-keyed tree whose FULL, SWA and MAMBA components each check their own reuse boundary. With HiCache and a 500 GiB Mooncake L3, the project reports about 98% hit rate and 145.5K input tokens/s on DeepSeek-V4-Flash, against 9.4K GPU-only and 14.3K with host memory [18].

2.3 TensorRT-LLM KV cache reuse

TensorRT-LLM keeps blocks in a radix search tree with prioritized LRU (priorities 0-100); evicted blocks can spill to host memory and stay searchable [5]. KV becomes reusable only after the producing request finishes, so a batch sharing a system prompt gets no first-pass reuse, and the 128-token default block suits kernels but reduces reuse [19]. The 1.4.0rc docs add a V2 manager for hybrid models, cache_salt enforced through cryptographic block hashes, and KV events for routers such as Dynamo [5].

3. KV Cache Offloading, Tiering and Shared Stores

An offload layer catches blocks the engine is about to evict, writes them to a cheaper tier, and copies them back on a later match instead of recomputing. The tools share one hierarchy: GPU HBM, pinned CPU DRAM, local NVMe or shared filesystem, then remote or object storage [20, 21, 22]. Engine-native tiers run in the serving process; out-of-tree layers keep their own indexing and storage behind the connector API, trading deployment complexity for cross-replica sharing and backend choice [23].

3.1 Engine-native tiers

vLLM’s OffloadingConnector (0.11.0, reworked in 0.12.0) copies completed blocks to pinned host memory by asynchronous DMA [24]. TieringOffloadingSpec adds ordered fs, obj (S3 via NIXL) and p2p (peer CPU) tiers with lru, arc or custom eviction, and self_describing_kv_events lets routers index offloaded blocks [15]. The vLLM team reports 2-22x lower TTFT (time to first token) on CPU hits (project-authored) [24]. SGLang HiCache uses GPU as L1, host memory as a per-instance L2 and a storage backend as L3, shared only if the backend supports it [21]; backends implement just get, exist and set, and project benchmarks report up to 6x throughput [25].

3.2 Out-of-process layers

LMCache (Tensormesh and the University of Chicago) is the most widely integrated third-party layer, with 256-token chunks, layer-pipelined transfers and a controller API (lookup, move, pin, compress) for routers; its paper’s up-to-15x throughput is vendor-authored, against GPU-only vLLM [11]. Its multiprocess (MP) mode runs a standalone server, keeps L1 in DRAM or a GPUDirect Storage (GDS) slab, pushes to and prefetches from L2 adapters (NIXL, filesystems, Mooncake Store, S3), and can load CacheBlend modules [26, 22]. Keys carry the cache_salt [22], with per-salt quotas [79]. Hybrid models work with caveats: output is not bit-exact, unified blocks reach 784 tokens on Qwen3.6-27B, only text KV is validated, and opaque pages rule out CacheBlend [27].

Mooncake Store is a distributed KV object store: a master owns placement, leases and approximate-LRU eviction, and clients contribute memory, issue Put/Get and can spill to SSD [28]. vLLM ranks contribute DRAM directly (embedded) or call an external DRAM-plus-SSD pool (standalone-store) [29]. cache_salt marks request-group boundaries, and an opt-in tenant_id namespace adds quotas but is not authentication [30, 80]. MooncakeStoreConnector pools and MooncakeConnector handles P/D, combined through MultiConnector [23].

  • Dynamo KVBM is a Rust block manager with tiers G1 (GPU), G2 (CPU), G3 (NVMe) and G4 (remote storage reached through NIXL), deduplicating by sequence hash [20]; a CPU cache smaller than the GPU cache churns [31].
  • AIBrix (ByteDance) v0.3.0 adds an L1 DRAM cache with S3FIFO eviction and pluggable L2 backends such as InfiniStore [32].
  • FlexKV (Tencent Cloud) serves vLLM, SGLang and TensorRT-LLM with SSD, GDS and Mooncake paths [33] and is experimental in Dynamo [34].
  • 3FS (DeepSeek) is a distributed filesystem positioned as a cheaper, larger alternative to DRAM caching, reporting up to 40 GiB/s per KVCache client [35]; NIXL ships an HF3FS backend [48].

3.3 Platform wrappers and non-prefix reuse

KServe declares tiering in spec.workload.kvCacheOffloading [36]. llm-d offers native, LMCache, Mooncake and KVBM connectors, and ships a PVC evictor because its filesystem tier does not evict [23, 37]. CacheBlend (EuroSys’25) reuses non-prefix chunks for retrieval-augmented generation (RAG), recomputing a small fraction of tokens to restore cross-attention, with 2.2-3.3x lower TTFT in its authors’ benchmark [38].

3.4 Contested point: restore versus recompute

Results on whether loading KV from a slower tier beats recomputing it sort by who ran the test. Cloudian reports P95 TTFT of 7.59 s against 158.86 s for recompute at 120K tokens with KVBM over RDMA, from a test repeating one request [39]. VAST and Lablup (vLLM 0.20, LMCache with GDS, 140K-token contexts) report 2.09x lower average TTFT, with cold first turns about 4 s slower, and concede plain NFS can lose to recompute [40]. The LMCache paper finds that at 32 Gbps loading beats prefill only above about 256K tokens [11].

Three independent 2026 studies test the other corner:

  • py-kvcache (VU Amsterdam and IBM) derives the rule load if g(P) + f(D−P) < f(D), where g is hit-path TTFT for reused prefix P and f cold TTFT for prompt length D. On H100 the bandwidth needed falls from 23.2 GB/s at 1K tokens to 3.5 GB/s at 80K, so a PCIe 5 CPU tier always clears it, but the measured ~13.5 GB/s SSD falls short somewhere below 8K tokens [41].
  • Multiverse Computing ran LMCache with a Valkey L2 on 8x B300: a 16K-token hit took 0.88 s to load against 0.31 s to recompute, p99 rose from 3.96 s to 17.3 s, and the deployment was rolled back. A hit pays only above bandwidth B* = bytes per token × prefill rate (2.53 GB/s here) and after about 0.33 s fixed cost, so prompts under about 17K tokens cannot win; sharding and asynchronous loading later cut hit-heavy p99 from 83.32 s to 0.67 s [42].
  • EfficientAgent (HKUST and Huawei) found 79.2% of chunks written to a host tier evicted before reuse; offload paid only when working set over host capacity fell below 1 (2.3, 1.1, 0.57 at 5, 10, 20 GiB), and a tier so sized cut recomputed tokens by 93% [43].

The camps measure different cells of one cost model: reuse pays when fixed per-hit cost plus bytes over bandwidth is below the reused prefix’s prefill time, and only when the tier holds the working set; some losses reflect connector maturity, not physics [41, 42].

3.5 Contested point: native offload versus a plugin layer

LMCache’s paper reports 400 Gbps loading against 88 Gbps for vLLM native offload, a comparison predating the 0.12 rework [11, 24]. Third-party tests (a storage vendor and an IBM-coauthored study) point the other way: py-kvcache found native CPU-plus-disk offload ahead of LMCache (8.02 s against 13.48 s TTFT at 40K tokens) [41], and NetApp, testing LMCache v0.5.3, found that “vLLM’s native offloading connector delivered the best performance overall”, with LMCache in-process ahead of MP mode on longer prompts [44].

Defaults are set per stack: KServe exposes only the native connector [36], llm-d calls it simplest [23], Dynamo’s router-visible offload uses it [45], and vLLM production-stack’s older docs still enable LMCache in-process through lmcacheConfig, a mode LMCache now marks deprecated [46, 75]. The plugin case rests on pooling, durable L2, backend breadth, the controller API and CacheBlend [11, 26].

3.6 Contested point: eviction policy

TensorRT-LLM adds priorities [5], AIBrix defaults to S3FIFO [32], and Bailian-trace research proposes workload-aware eviction [7]. A study of 14 policies on more than 20B production tokens found plain LRU robust [47], and the Chutes trace found sophisticated policies can underperform FIFO and LRU [9]. Both sides agree capacity matters more: Bailian traffic nears its ideal hit rate at about 2x per-GPU HBM under LRU [7].

4. KV Transfer Libraries and Disaggregated Serving

A transfer library hides the mechanics of moving KV between memory types and machines behind one asynchronous API and picks the fastest transport. NIXL (NVIDIA Inference Xfer Library) runs a transfer agent per process over VRAM, DRAM, file, object and block memory, with backends such as UCX, GDS, POSIX, S3 over RDMA, Mooncake and HF3FS [48]. It sits under vLLM’s NixlConnector and obj/p2p tiers [13, 15], LMCache L2, KVBM G4 and HiCache L3 [22, 20, 21], and TensorRT-LLM’s transceiver [5].

The Mooncake Transfer Engine moves batches between registered memory segments over TCP, multi-NIC RDMA, EFA, NVMe-oF and NVLink [49], and its GPUDirect RDMA path uses no GPU streaming multiprocessors [12]. It came from Moonshot AI’s KV-centric architecture for Kimi, which reported 75% more requests under SLOs on real workloads [50].

vLLM’s documentation states that “Disaggregated prefill DOES NOT improve throughput”; the gain is separate tuning of TTFT and inter-token latency (ITL) [13]. The p2p tier doubles as a P/D path [15], MultiConnector chains Mooncake handoff with pool lookups [29], and SGLang pairs --disaggregation-transfer-backend mooncake with HiCache [51]. In the vLLM-Mooncake design only prefill instances read the pool, and both phases must share namespace values [12, 30]. LMCache claims 1.53-1.84x lower TTFT than vLLM’s native NIXL P/D path (vendor benchmark) [11], and AWS SageMaker HyperPod runs llm-d with NIXL over EFA for up to 70% more tokens/s [52].

5. Cache-Aware Routing and Global KV Indexing

A cache-aware router estimates how much of each prompt’s prefix every replica holds and weighs that against load. Routers differ on two axes: the signal, approximate (from the router’s own past decisions) or precise (from KV events that vLLM, SGLang and TensorRT-LLM publish over ZMQ or NATS) [3, 53, 5]; and the blend, how strongly that signal is traded against load.

5.1 llm-d and the Gateway API Inference Extension

llm-d’s Endpoint Picker (EPP) ships both signals. The approximate scorer hashes fixed-size blocks estimated from characters and remembers where it sent each prefix; it needs no engine integration but drifts when pods evict [54]. The precise path tokenizes through vLLM and indexes KV events in memory or Redis/Valkey, weighting GPU hits 1.0 and CPU hits 0.8 [3]. Its guide lists the costs: a single router replica, a 10,000-batch replay buffer that hides pre-window shared system prompts after a restart, matched 64-token block sizes, and a missing --enable-scale-out on vLLM 0.30 that disables cache-aware routing [55].

The Gateway API Inference Extension (GIE), the Kubernetes standard beneath llm-d and GKE Inference Gateway, composes weighted queue, KV-utilization and prefix scorers; a second prefix scorer with autoTune: false can model a CPU tier [56, 37].

llm-d’s benchmark (16 H100s, 6K-token contexts, KV demand at 73% of capacity) reports p90 TTFT of 0.542 s precise, 31.08 s approximate and 92.6 s random, and 8,730 against 6,944 output tokens/s [57].

5.2 NVIDIA Dynamo KV router

Dynamo keeps a global radix tree from worker events. It scores workers by prefill_load_scale × adjusted_prefill_blocks + potential_decode_blocks + active_request_blocks, minus overlap credits for device, host, disk and fetchable shared blocks. Higher credits favour reuse and TTFT, lower credits even load and ITL, and fetchable blocks get smaller credit because a fetch can miss [53]. Without events it predicts residency from its own decisions with a 120 s TTL [58]. With vLLM 0.24+ and Dynamo 1.3+, CPU-tier blocks are routable at a host-hit weight of 0.75; storage-tier events drop the salt, costing hits but not correctness, and shared-pool routing is planned [45].

5.4 Contested points: signal quality and affinity versus load

On signal quality the only controlled comparison is llm-d’s own: its 57x headline compares p90 tails on a workload built to stress staleness, where approximate routing’s mean queue was 8.1 against 0.1; the baseline was llm-d’s own history scorer, not SGLang’s tree, and the throughput gap is about 25% [57]. The approximate camp offers operating evidence instead: Character.AI’s sticky sessions without a global index [64], Ray’s caution about overhead [62], and the history-based modes Dynamo and SGLang retain [58, 60].

On affinity versus load, most findings favour blending, though the answer depends on workload. Anyscale and NVIDIA found pure affinity piling RL rollouts onto the replica holding a shared system prompt, while a token-load router had the best p99 despite a lower hit rate [65]. Meta’s CacheRoute preprint found affinity alone raised hit rate from 56% to 88% but imbalance to 3.46x, leaving capacity flat until balanced placement doubled it. Where only about 15% of the prompt was reusable, affinity fell to 0.50-0.67x a flat balancer’s capacity. It advises gating rollout on a shadow replay [66]. DualMap (ICLR 2026) switches to load-aware routing when TTFT exceeds the SLO, reporting up to 2.25x capacity [67]. Vertex AI moved its prefix:queue:KV-utilization weights from 3:3:2 to 3:5:2 to skip hot nodes [68].

Every production router surveyed includes a load term, yet sticky or affinity routing won in AgentX [71] and in llm-d’s uniform shared-prefix run (p50 TTFT 0.48 s against 0.73 s) [72]. Lodestar’s learned router replaces fixed weights with an online predictor, cutting mean TTFT 1.41x against AIBrix’s heuristic (authors’ benchmark) [77].

6. How Teams Build the Cache Layer: Reference Architectures and Production Accounts

Four packaged stacks recur, and published deployments fit a four-rung ladder.

6.1 Reference stacks

  • KServe, llm-d and vLLM put GIE/EPP routing in front of vLLM APC, with native CPU and volume tiers declared in an LLMInferenceService [36, 23, 69].
  • NVIDIA Dynamo runs its KV router over vLLM, SGLang or TensorRT-LLM workers with one offload backend per worker and NIXL for P/D [34, 45, 20].
  • SGLang-native deployments pair the Model Gateway with HiCache and a Mooncake or 3FS L3 [59, 21, 18].
  • vLLM production-stack combines prefix-aware routing with LMCache sharing and launched claiming 3-10x lower delay (project-authored) [70, 46].

6.2 The build ladder in practice

Rung 1, the engine cache alone, is often enough: APC costs almost nothing on misses [14], and VAST and Lablup treat single-shared-prefix RAG as a case GPU-only caching handles [40]; Bailian’s trace study finds a small GPU cache suffices for API-dominated business traffic [7].

Rung 2 adds a per-replica CPU tier, usually with sticky sessions. Character.AI built it before open tools existed, keeping host-memory KV between turns in an LRU tree with sticky sessions and a model that shrinks KV more than 20x, for a 95% cache rate [64]. Open stacks now expose it as configuration: KServe’s cpu: "10Gi" [36], llm-d’s native, lmcache-connector or mooncake-store connector choice [37], Dynamo’s OffloadingConnector [45], production-stack’s cpuOffloadingBufferSize [46] and SGLang’s --enable-hierarchical-cache [51].

Rung 3 adds cache-aware routing and has the most accounts. Tesla, with Red Hat, replaced round-robin behind NGINX with KServe, llm-d and GIE, reporting 3x output tokens/s and 2x lower TTFT for Llama 3.1 70B on MI300X (one deployment, before/after) [69]. Vertex AI reports its hit rate doubling from 35% to 70% behind GKE Inference Gateway, with P95 TTFT 52% lower for DeepSeek V3.1 (vendor blog, no ablation) [68]. The llm-d v1.0 post reports IBM Research serving up to 3,000 concurrent coding agents at about 98% hit rate [52].

Rung 4 adds a shared pool or peer fetch once sessions outgrow local DRAM or move between replicas. Mooncake’s Conductor picks a prefill/decode pair by prefix match and queue time; growing the pool from 1,000 to 50,000 blocks raised the hit ratio from 30% to 50% [50]. The vLLM-Mooncake team, running embedded mode over RDMA [29], reports 3.8x throughput and 46x lower P50 TTFT on 12 GB200 GPUs as hit rate rose from 1.7% to 92.2%, holding above 95% out to 60 GPUs (synthetic data, deliberate round-robin, project and partner authors) [12].

vLLM AgentX runs a standalone Mooncake pool behind Dynamo and llm-d routers and found load-balancing policies all did worse than session-aware sticky routing [71]. llm-d’s P2P test found pure affinity worst (2.75 req/s), against 4.4 for load-aware and 6.3 req/s for token-aware placement with pulls gated by minCachedTokenDelta [72]. Novita AI reports hit rate rising from 40% to 80% with HiCache on 3FS [25].

DeepSeek’s DeepInfer keeps block KV on about 100 PiB of 3FS SSD with 3-day (agent) and 7-day (chat) TTLs so any prefill machine can hit any prefix, removing the conflict between affinity and load balancing. It still matches hit length before routing, buckets load by context length and keeps sliding-window KV local [73].

6.3 Contested point: route to the cache or make the cache global

At the top rung the field holds three positions. Mooncake’s Conductor, Dynamo and llm-d keep a router and price a pool fetch as a score discount [50, 53, 72]. DeepSeek replaces affinity routing with a dedicated pool plus a pre-routing hit-length lookup [73]. AgentX keeps the pool but returns to sticky routing for short-gap sessions [71]. Academic work brackets the choice: the Chutes simulation finds cache-first routing turns larger caches into higher hit ratios with modest imbalance [9], while SMetric argues a global tier lets load balancing coexist with reuse if the slower tier is used carefully [8]. No source compares pool hardware cost with the recompute GPU-hours it saves.

7. Choosing and Combining Tools: Trade-offs and Recommendations

7.1 One inequality behind every knob

Every setting asks whether the prefill avoided is worth more than getting the KV to the GPU.

  • Offload admission compares against tier bandwidth, giving the independent break-even points of about 8K tokens (H100, NVMe) and 17K tokens (B300, remote tier, before connector fixes) [41, 42].
  • Routing compares against queueing delay through Dynamo’s overlap credits, GIE scorer weights and Ray’s imbalanced_threshold [53, 56, 61].
  • Pool fetches compare against fabric cost through Dynamo’s shared-cache credit and llm-d’s minCachedTokenDelta [53, 72].

One shared system prompt Engine cache only Near-zero cost [14]; TRT-LLM reuse waits for first request [19]
Multi-turn chat by session Sticky routing with load spill, CPU tier Character.AI [64]; reuse within ~100 s [8]
Cross-session prefixes under KV pressure Precise routing plus CPU tier Project benchmark only [57]
Long-context agents, minute-scale gaps CPU tier sized to working set, then pool Misses start past 5-minute gaps [78]; pool results project-authored [12, 43]
Short prompts on fast GPUs GPU cache plus routing; gate storage tiers SSD/remote restores lose below ~8K-17K tokens [41, 42]
RAG with reordered chunks CacheBlend via LMCache, dense models Authors’ benchmark [38]; not hybrid pages [27]
Very large fleet, multi-day retention Dedicated pool, load-based routing DeepSeek only [73]
P/D-disaggregated serving NIXL or Mooncake connector No throughput gain from P/D [13]

7.3 Composition rules, isolation and hybrid models

  • Use one offload backend per worker; Dynamo calls LMCache, FlexKV and HiCache “alternatives, not cache layers to stack together” [34]. Backends are engine-bound: HiCache is SGLang-only, the OffloadingConnector vLLM-only [23].
  • Pin versions, since router-visible offload needs vLLM 0.24 and Dynamo 1.3 and precise routing fails on vLLM 0.30 without the scale-out flag [45, 55].
  • Set PYTHONHASHSEED consistently and match block sizes across engine, connector and router [15, 55].
  • Verify each tier with metrics such as vllm:external_prefix_cache_hits_total [37], size the CPU tier above the GPU cache [31], and gate affinity changes on a shadow replay [66].

Shared prefixes leak through timing: KVGov measured a cold-to-cached TTFT ratio of 0.22 on vLLM 0.26 and proposes HMAC-derived per-principal salts [74], and CacheSolidarity keeps up to 70% more reuse than per-user isolation by isolating selectively (research prototype) [17]. vLLM, TensorRT-LLM, LMCache MP and Mooncake carry salts [4, 5, 22]; the gaps are Dynamo’s unsalted storage-tier index [45] and undocumented per-request salts in the llm-d indexer and HiCache L3. Since most reuse stays within a session or user [8, 9], per-tenant salting costs little in those traces, though system prompts supply 18-20% of reuses [8], exactly the cross-principal hits salting removes.

Hybrid models follow the same pattern: engines, LMCache and HiCache handle them on validated recipes, but the llm-d and Dynamo routers model only full-attention groups [3, 45, 27], so hybrid fleets pin one validated engine-and-connector pair.

7.4 Outlook and evidence gaps

Engine-native tiering is absorbing the per-replica job because its events are router-visible, while third-party layers concentrate on pooling, durable L2, non-prefix reuse and vendor storage [36, 37, 44]. Routing and pooling are converging on discounted-fetch scoring: Dynamo plans shared-pool routing, the vLLM-Mooncake team plans cache-aware routing over the pool, and llm-d v1.0 adds session-aware routing [45, 12, 52]. vLLM also plans programmable pinning and inter-turn prefetch [71].

Hybrid and compressed-KV models (DeepSeek-V4, Qwen3.5, gpt-oss) shrink bytes per token but multiply cache groups, pushing per-group semantics into router indexes, salts and offload events where support lags the engines [18, 3]. Each GPU generation makes recompute cheaper and moves the restore break-even toward longer prompts, even as connector fixes pull it back [42]. Offload now has independent bounds; routing signal quality and shared pools do not, so a team’s own shadow replay is the deciding measurement [41, 66].
