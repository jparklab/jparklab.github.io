How Kubernetes Manages the Lifecycle of Pods and ReplicaSets

Kubernetes splits lifecycle management between two layers that never do each other’s job. On the node, the kubelet drives a single Pod through its phases: it starts containers, restarts them according to restartPolicy, runs probes, and shuts them down gracefully when the Pod is deleted. In the control plane, the ReplicaSet controller never restarts or moves anything. It counts the Pods that match its selector, compares that count with spec.replicas, and creates or deletes whole Pods to close the gap. A Pod is bound to one node for life and is never rescheduled; healing means a controller creates a new Pod with a new UID. Owner references tie each Pod to its ReplicaSet and each ReplicaSet to its Deployment, so the garbage collector can cascade deletions, and a Deployment rollout is nothing more than a controlled scale-up of a new ReplicaSet and scale-down of the old one.

1. The Control Loop Model: Who Manages Pods and ReplicaSets

Every lifecycle behavior below comes from the same pattern: a controller is a control loop that watches the cluster’s state and makes or requests changes to move the current state toward the desired state [1]. The Kubernetes API-machinery guidelines describe a controller as “an active reconciliation process” that watches both the desired state and the actual state of the world [2]. Two design rules from those guidelines explain much of the behavior covered below. Controllers are level-driven rather than edge-driven: they act on the current state of an object, not on the sequence of events that produced it, so a missed event is corrected on the next pass [2, 3]. And controllers react to changes in related objects by mapping them back to the owner: the ReplicaSet controller reacts to a Pod being deleted “by finding the related ReplicaSets and queuing references to those” [2].

The machinery behind this is shared informers plus a work queue. Informers keep a local cache of watched objects and deliver add, update and delete notifications; the work queue guarantees that no two worker goroutines process the same key at the same time and supports rate-limited requeueing with backoff; informers can also resync periodically as a safety net [2, 3]. The ReplicaSet controller in pkg/controller/replicaset is built exactly this way: Pod and ReplicaSet events enqueue a ReplicaSet key, and syncReplicaSet reconciles that one key [4].

Pods themselves are not meant to be managed by hand. The Pods documentation states that you will rarely create individual Pods directly, “even singleton Pods”, because Pods are “relatively ephemeral, disposable entities”; workload resources such as Deployments create them from a Pod template and manage them for you [5].

Actor Runs where What it owns in the lifecycle What it never does
API server Control plane Stores Pod and ReplicaSet objects, records deletion timestamps and grace periods Run containers
Scheduler Control plane Binds a Pending Pod to a node Move a bound Pod
kubelet Each node Container start, restart, probes, graceful shutdown, Pod phase and conditions Create replacement Pods
ReplicaSet controller kube-controller-manager Keeps the count of matching Pods equal to spec.replicas Restart a container

2. Pod Lifecycle: Phases, Conditions and Container States

2.1 Phases

A Pod’s status.phase is a coarse summary with five values. Pods start in Pending, move to Running once at least one primary container starts, and end in Succeeded or Failed depending on whether any container terminated in failure [6]. Pending covers both the time spent waiting to be scheduled and the time spent pulling images; Running means the Pod is bound to a node, all containers have been created and at least one is running, starting or restarting; Unknown usually means the control plane cannot reach the node [6]. CrashLoopBackOff and Terminating are not phases: they are display strings that kubectl shows in its STATUS column, and the documentation warns explicitly against confusing that column with the phase in the API [6]. Since Kubernetes 1.27 the kubelet moves a deleted Pod to a terminal phase (Failed or Succeeded) before removing it from the API server, with exceptions for static Pods and force-deleted Pods [6].

The single most important lifecycle fact is that a Pod is bound to one node for life. Once scheduled, the Pod runs on that node until it stops or is terminated; if the node fails before the Pod starts, that Pod never starts [6]. “A given Pod (as defined by a UID) is never ‘rescheduled’ to a different node; instead, that Pod can be replaced by a new, near-identical Pod”, which may reuse the name but always gets a new .metadata.uid [6]. Anything with “the same lifetime as a Pod”, such as an emptyDir volume, dies with that UID even if an identical replacement appears [6].

Phase Meaning Typical next step
Pending Accepted; waiting for scheduling, image pulls or sandbox setup Running
Running Bound to a node; at least one container running, starting or restarting Succeeded, Failed, or stays Running
Succeeded All containers exited 0 and will not restart Kept until garbage-collected
Failed All containers terminated, at least one in failure, and no restart is configured Kept until garbage-collected
Unknown Node unreachable, state cannot be obtained Resolved when the node reports again, or the Pod is deleted

2.2 Conditions

Conditions give finer-grained, independently timestamped facts. The kubelet manages the following conditions [6]:

  • PodScheduled
  • PodReadyToStartContainers: the sandbox exists, networking is configured, volumes are mounted and any dynamic resources are allocated
  • Initialized: all init containers completed
  • ContainersReady
  • Ready: the Pod can serve and should be added to the load-balancing pools of matching Services

DisruptionTarget marks a Pod about to be terminated by preemption, eviction or garbage collection [6, 7]. Each condition carries status, lastTransitionTime, reason and message [6]. PodReadyToStartContainers was called PodHasNetwork during its early development; the current documentation lists it as stable [6].

2.3 Container states and the startup sequence

Each container has one of three states. Waiting covers everything before execution, such as pulling an image or applying Secret data, and carries a reason. Running means the container is executing and any postStart hook has finished. Terminated records an exit code, reason and start and finish times; any preStop hook runs before a container enters this state [6].

Inside a Pod, startup is ordered. Init containers run sequentially, each to completion, and the main containers do not start until all of them succeed [8]. Sidecar containers are init containers declared with restartPolicy: Always: they start in init order but keep running for the Pod’s whole life, and they can be started, stopped and restarted independently of the app containers [9]. The sidecar documentation describes the feature as stable since v1.33, first available in v1.28 and enabled by default since v1.29 [9].

3. Restarts and Probes: How Pods Stay Healthy

3.1 Restart policy and backoff

Restarts are a node-local behavior. The Pod’s restartPolicy is Always (the default), OnFailure or Never, and it governs the app containers; sidecars always restart [6]. When a container exits and policy allows a restart, the kubelet restarts it in place, in the same Pod, with an exponential backoff of 10s, 20s, 40s and so on, capped at 300 seconds [6]. The kubelet resets the backoff once a container has run for 10 minutes without problems [6]. A Pod that keeps failing this way shows CrashLoopBackOff in kubectl, but its phase is still Running [6]. The design point is that none of this involves the ReplicaSet controller. A crash-looping Pod still matches its selector and still exists, so from the ReplicaSet’s point of view the replica count is satisfied [6, 10].

Recent releases add knobs to this loop: a per-node maxContainerRestartPeriod (feature KubeletCrashLoopBackOffMax, beta in v1.35) can lower the 300-second cap, and the alpha ReduceDefaultCrashLoopBackOffDecay gate starts at 1s and caps at 60s [6]. Container-level restartPolicyRules can restart on specific exit codes, and the RestartAllContainers action can restart the entire Pod in place while keeping its UID, IP, sandbox and volumes [6].

3.2 Probes

The kubelet runs three kinds of probes using exec, httpGet, tcpSocket or grpc checks; gRPC probes have been stable since v1.27 [6, 11]. Each kind of probe triggers a different consequence:

Probe Question it answers On failure Who acts
Startup Has the app finished starting? Container is killed and handled by its restart policy; liveness and readiness are held off until it succeeds kubelet
Liveness Is the process stuck (for example, deadlocked)? Container is restarted after exceeding the failure tolerance kubelet
Readiness Can it take traffic right now? Pod IP is removed from the EndpointSlices of matching Services; no restart EndpointSlice controller

Readiness probes run for the container’s whole lifetime, so a Pod can drop out of Service traffic during overload and return without being restarted [6, 11]. Startup probes exist for slow starters: the documented pattern sets failureThreshold * periodSeconds long enough to cover the worst-case startup time, after which the container is killed if it never succeeds [11]. Default probe timing is an initial delay of 0, a period of 10s, a timeout of 1s and a failure threshold of 3 [12].

Liveness probes are where practitioners most often hurt themselves. If a liveness endpoint checks external dependencies such as a database, a slow dependency triggers restarts across every replica at once, and the restarted Pods then pile reconnects onto the already-struggling dependency: a cascading failure [12]. A slow cache warm-up that trips liveness produces an endless restart loop. Readiness, not liveness, is the right tool for a Pod that is temporarily unable to serve [6, 12].

4. Pod Termination and Graceful Shutdown

4.1 The termination sequence

Deleting a Pod does not kill it. The API server records a deletion timestamp and a grace period, 30 seconds by default via terminationGracePeriodSeconds, and kubectl shows the Pod as Terminating [6]. From there, two independent tracks run in parallel:

Step Node (kubelet) Control plane
1 Sees the Pod marked terminating and starts local shutdown Pod has a deletion timestamp and grace period
2 Runs each container’s preStop hook, if defined EndpointSlice controller marks the endpoint terminating (ready: false, serving still reported)
3 Sends SIGTERM (or the image’s STOPSIGNAL) to PID 1 in each container, in no guaranteed order ReplicaSets stop counting the Pod as a valid in-service replica
4 When the grace period expires, sends SIGKILL to remaining processes (plus a one-off 2s extension if preStop is still running) —
5 Moves the Pod to Failed or Succeeded, then force-removes it with grace period 0 API object disappears

All of the above is taken from the Pod lifecycle documentation [6]. Two details matter in practice. First, sidecars shut down last: the kubelet delays SIGTERM to sidecar containers until the last main container has terminated, then stops them in reverse order of definition, so a slow main container also delays the sidecars [6]. Second, preStop hooks run inside the grace period, not before it; if the hook needs longer than the grace period, you must raise terminationGracePeriodSeconds [6, 13]. Hooks are delivered at least once, and a failing PostStart or PreStop hook kills the container [13].

Force deletion (--grace-period=0 --force) removes the API object immediately without waiting for the kubelet to confirm, which is why a new Pod with the same name can be created at once; the documentation warns that the old process “may continue to run on the cluster indefinitely” [6].

4.2 The endpoint race

Because endpoint removal and SIGTERM begin at the same moment, a Pod can receive SIGTERM while load balancers, ingress controllers or kube-proxy rules on other nodes still route new connections to it. Skipper’s documentation states the problem plainly: endpoint updates are asynchronous, and “reducing this interval or implementing watch will only reduce the timeframe, but not fix the underlying race condition” [14]. The standard mitigations are a preStop hook that sleeps a few seconds before SIGTERM, or an application that, on SIGTERM, fails its readiness check and keeps serving briefly before exiting [14]. The upstream documentation addresses the same gap from the other side: terminating endpoints stay in EndpointSlices with ready: false and a separate serving condition, so a proxy that wants to drain connections can still see them [6]. This is the main place where the documented behavior and real-world behavior diverge: Kubernetes guarantees ordering on the node, not across the network.

4.3 Involuntary termination: eviction, node loss and Pod GC

Not every termination starts with kubectl delete. Four other paths end a Pod:

  • API-initiated eviction (for example, kubectl drain) is graceful, honors terminationGracePeriodSeconds, and respects PodDisruptionBudgets [7].
  • Node-pressure eviction is harsher: the kubelet watches signals such as memory.available, disk and inode availability and PID counts; soft thresholds wait out a grace period capped by eviction-max-pod-grace-period, while hard thresholds kill Pods immediately, and evicted Pods end in Failed for their controller to replace [15].
  • Node failure. When a node fails, Kubernetes treats its Pods as unhealthy and eventually deletes them [6].
  • Pod garbage collection. The Pod garbage collector (PodGC) deletes terminated Pods once their number exceeds terminated-pod-gc-threshold, removes orphan Pods bound to nodes that no longer exist and unscheduled terminating Pods, and marks any non-terminal Pod it cleans up as Failed [6, 7].

5. The ReplicaSet Controller: Reconciling Replica Count

5.1 What a ReplicaSet is

A ReplicaSet has three parts: a selector that identifies the Pods it may own, a replica count, and a Pod template for new Pods; it “fulfills its purpose by creating and deleting Pods as needed to reach the desired number” [10]. It does not care how a Pod came to exist. The ReplicaSet identifies Pods by selector, not by template, which has two consequences. Changing the template has no effect on running Pods; only newly created Pods use the new template, which is why ReplicaSets cannot do rolling updates and the docs recommend Deployments instead [10]. And a ReplicaSet will adopt bare Pods that happen to match its selector [10].

5.2 One sync pass

Each sync of a ReplicaSet key in the controller does roughly the following [4, 16]:

  1. Check expectations. The controller keeps per-ReplicaSet ControllerExpectations: counters of creates and deletes it has issued but not yet seen in its informer cache. syncReplicaSet calls manageReplicas only when expectations are satisfied, so it never acts on a stale cache and double-creates Pods. Expectations expire after 5 minutes, a safety valve the source says exists because “without it the controller could stay asleep forever”.
  2. Claim Pods. claimPods lists Pods matching the selector and calls PodControllerRefManager.ClaimPods, which adopts matching orphans and releases owned Pods whose labels no longer match.
  3. Filter to active Pods (excluding terminal and terminating ones) and compute diff = len(active) - spec.replicas.
  4. Create or delete, capped per sync at BurstReplicas = 500, a constant the source ties to performance requirements for Kubernetes 1.0.
  5. Update status (replicas, ready, available and, where enabled, terminating replicas).

Creation uses slow-start batching. Batches start at SlowStartInitialBatchSize = 1 and double after each fully successful batch; “If there are any failures in a batch, all remaining batches are skipped”, and the expectations for the skipped creates are decremented [4, 16]. This keeps a ReplicaSet whose Pods are rejected (for example by quota or admission) from flooding the API server with hundreds of doomed requests.

Deletion records deletion expectations first, then deletes the Pods chosen by getPodsToDelete [4]. Because terminating Pods are excluded from the active count, the total number of Pods can briefly exceed spec.replicas while old Pods drain; the .status.terminatingReplicas field (feature DeploymentReplicaSetTerminatingReplicas, beta and on by default since v1.35) makes that visible [10].

5.3 Which Pods die first on scale-down

The documentation summarizes the scale-down order as: pending and unschedulable Pods first, then lower pod-deletion-cost, then Pods on nodes that run more replicas, then newer Pods, then random [10]. The source code is more precise. ActivePodsWithRanks sorts by eight rules in order [16]:

# Rule (earlier = deleted first)
1 Unassigned to a node before assigned
2 Pending before Unknown before Running
3 Not ready before ready
4 Lower controller.kubernetes.io/pod-deletion-cost before higher
5 Higher rank (more related Pods on the same node) before lower
6 Ready for less time before ready for longer (log scale)
7 More container restarts before fewer
8 Newer creation time before older (log scale)

Rules 6 and 8 compare timestamps on a logarithmic scale and break ties by UID, giving a pseudorandom choice among Pods of similar age [16]. That is the LogarithmicScaleDown behavior from KEP-2185, which went stable in v1.31. It exists because the old rule, always kill the newest Pod, tended to preserve imbalance across failure domains after repeated scale-ups and scale-downs [17].

pod-deletion-cost (KEP-2255) lets an application bias the choice, for example by marking idle replicas cheap before a scale-down [10, 18]. Two cautions apply. It is explicitly best-effort and “does not offer any guarantees on pod deletion order” [10], and its maturity label is inconsistent: the KEP page lists v1.24 as its stable milestone, while the current ReplicaSet documentation still marks the feature beta since v1.22 [10, 18].

6. Ownership, Adoption and Garbage Collection

6.1 Owner references

The link between a ReplicaSet and its Pods is not the selector alone; it is metadata.ownerReferences. A ReplicaSet is the owner of its Pods, which are its dependents, and controllers set owner references automatically [19]. A Pod created by a Deployment’s ReplicaSet carries an owner reference of kind: ReplicaSet with controller: true and blockOwnerDeletion: true [20], and blockOwnerDeletion is set automatically whenever a controller sets the reference [19]. Owner references hold a name and a UID and must stay within one namespace; cross-namespace owners are disallowed by design [19].

6.2 Adoption, release and isolation

Because the controller reconciles by selector and controller reference together, ownership can move. A Pod with no owner reference, or one whose owner is not a controller, is “immediately acquired” by any ReplicaSet whose selector it matches, even if it was created by hand from a different template [10]. In the other direction, changing a Pod’s labels so it no longer matches releases it: the ReplicaSet drops the owner reference and, seeing one replica fewer, creates a replacement. This is the documented way to pull a misbehaving Pod out for debugging without losing capacity [4, 10]. The documentation warns against creating bare Pods whose labels overlap a ReplicaSet’s selector, and against overlapping selectors between controllers, for exactly this reason [10].

6.3 Cascading deletion

Deleting an owner deletes its dependents through the garbage collector, in one of three modes [10, 20, 21]:

Mode How to request it What happens
Background (default) kubectl delete rs x Owner is deleted immediately; GC deletes Pods afterward
Foreground --cascade=foreground or propagationPolicy: Foreground Owner gets a deletionTimestamp and a foregroundDeletion finalizer; it stays visible until dependents with blockOwnerDeletion: true are gone
Orphan --cascade=orphan Owner is deleted; Pods keep running with their owner reference removed

Kubernetes uses background deletion unless told otherwise [21]. The orphan mode is how you replace a ReplicaSet without downtime: delete it with --cascade=orphan, create a new ReplicaSet with the same selector, and the new one adopts the existing Pods [10]. Adopted Pods keep their old template; a new template takes effect only as Pods are replaced [10].

7. Deployments, Rollouts and ReplicaSet Lifecycle

In practice most ReplicaSets are created and managed by a Deployment, and the documentation says not to manage Deployment-owned ReplicaSets directly [22]. The Deployment controller adds a pod-template-hash label to every ReplicaSet it creates or adopts; the label “ensures that child ReplicaSets of a Deployment do not overlap”, which is what keeps two ReplicaSets with otherwise identical selectors from fighting over Pods [22].

A rollout is a change to the Pod template, and only that: scaling a Deployment does not trigger one [22]. On a template change, the Deployment controller creates a new ReplicaSet and then scales the new one up and the old ones down. Each step is just a change to spec.replicas that the ReplicaSet controller reconciles. With the default RollingUpdate strategy, maxUnavailable and maxSurge both default to 25%, so at least 75% and at most 125% of the desired Pods are up during the rollout [22]. Terminating Pods do not count as available, so the actual Pod count can exceed replicas + maxSurge while old Pods drain [22]. If the template changes again mid-rollout, the controller creates yet another ReplicaSet and treats the one it was scaling up as old [22]. The Recreate strategy instead kills all existing Pods before creating new ones [22].

Deployment action Effect on ReplicaSets Effect on Pods
Scale (replicas: 3 → 5) Current ReplicaSet scaled (proportionally across ReplicaSets mid-rollout) Two new Pods from the current template
Template change New ReplicaSet created with a new pod-template-hash; old ones scaled toward 0 Pods replaced within maxSurge/maxUnavailable
kubectl rollout undo An older ReplicaSet is scaled back up Pods from the older template return
Revision cleanup ReplicaSets beyond revisionHistoryLimit are deleted Already at 0 replicas

Old ReplicaSets are kept at zero replicas as rollout history, which is what kubectl rollout undo scales back up, and .spec.revisionHistoryLimit controls how many are retained [22]. When a rollout is scaled mid-flight, the Deployment controller spreads the extra replicas across the new and old ReplicaSets in proportion to their size, a behavior the docs call proportional scaling [22]. progressDeadlineSeconds sets how long the controller waits before reporting the rollout as stalled in the Deployment status [22].

Taken together, the lifecycle is a hierarchy of loops, each with one job. The Deployment loop decides how many Pods each template version should have. The ReplicaSet loop makes the count of matching Pods equal that number. The kubelet loop keeps each Pod’s containers running and shuts them down cleanly. The garbage collector cleans up whatever loses its owner. Most surprising behaviors follow directly from which loop owns which decision. Examples include a crash-looping Pod that never gets replaced, Pod counts that briefly exceed replicas, a stray Pod that suddenly belongs to a ReplicaSet, and 502 errors during rollouts.
