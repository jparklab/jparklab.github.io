Source: Prefill-as-a-Service: KVCache of Next-Generation Models Could Go Cross-Datacenter (Qin et al., Moonshot AI + Tsinghua, arXiv 2604.15039v1, April 2026) Reviewed: 2026-10-31 · Sheet: PrfaaS summary sheet

Overview

The paper proposes Prefill-as-a-Service (PrfaaS). Long prefills run in a standalone, compute-dense “PrfaaS cluster”. The resulting KV cache travels over ordinary Ethernet (VPC peering or a dedicated line) to a separate, conventional PD-disaggregated cluster, which does the decoding [1]. The authors are the Mooncake team. Their premise: PD disaggregation is stuck inside one RDMA fabric today because dense-attention models emit KV cache faster than any slower link can carry it. Hybrid-attention models interleave a few full-attention layers with linear-attention or sliding-window layers. That cuts the KV emission rate by roughly 4–13×, enough to make a cross-datacenter link plausible for some requests [1].

The authors call smaller KV “necessary but not sufficient”. The system contribution has four parts [1]:

  1. A length threshold, so only long, uncached prefills cross the link.
  2. A hybrid prefix-cache pool that holds both recurrent state and block-level KV.
  3. A transport layer: layer-wise pipelining, multi-connection TCP, congestion signals.
  4. An analytical throughput model (Eqs. 3–8) and a two-timescale scheduler built on it.

The case study runs an internal 1T model with the Kimi Linear architecture. It uses 32 H200 for PrfaaS and 64 H20 for local PD, connected by a ~100 Gbps VPC. The paper reports 1.54× throughput over a 96-H20 homogeneous PD cluster and 1.32× over naive heterogeneous PD, with only 13 Gbps of cross-cluster egress [1]. These numbers come from profiled latencies fed into the model, not from a live end-to-end run.

Key concepts

  • Φkv, KV throughput (§2.1, Eq. 1). Φkv(l) = S_kv(l) / T_prefill(l). This is the rate at which one model instance produces KV cache during prefill, and so the egress bandwidth that instance needs to avoid stalling [1]. Prefill time grows almost quadratically with l. KV size grows linearly, or stays flat for recurrent state. So for hybrid models Φkv flattens or falls at long lengths.
  • PD disaggregation. Prefill (compute-bound) and decode (memory-bandwidth-bound) run on separate instances, and KV moves P→D once per request. The paper argues that this per-request transfer, not the scheduler, is what keeps PD inside one RDMA domain [1].
  • Hybrid attention (§2.2, Table 1). “Type A” linear-complexity layers (KDA, SWA, GDN, Lightning) are interleaved with “Type B” full-attention layers (MLA or GQA). Example ratios: 3:1 for Kimi Linear and Qwen3.5-397B, 5:1 for MiMo-V2-Flash, 7:1 for Ring-2.5-1T [1]. Only Type B layers produce KV that grows with length.
  • PrfaaS cluster vs local PD cluster (§3.1). Each cluster has one hardware type. The local PD cluster can serve a request end to end. The PrfaaS cluster only prefills the requests routed to it, as a “stateless KVCache producer” [1].
  • PD-P / PD-D (§3.4). The prefill and decode nodes inside the local PD cluster. PrfaaS and PD-P are parallel producers; PD-D is the single consumer [1].
  • Routing threshold t (§3.3). l is the incremental (uncached) length. If l > t the request goes to PrfaaS, otherwise to PD-P. Short prefills under-use compute-dense chips and have no better Φkv [1].
  • Hybrid prefix cache pool (§3.2, Fig. 4). Built on vLLM’s hybrid KV cache manager [1]. Linear-attention state and full-attention KV live in separate groups with aligned block sizes, drawn from one shared block pool across host memory and SSD.
  • Prefix-cache vs transfer-cache blocks. Prefix-cache blocks are full, block-aligned, reusable and stay inside the cluster. Transfer-cache blocks hold the tail KV of a prefill, can be any length, exist only to be shipped P→D, and are freed after the send [1].

How it works

1. The bandwidth wall (§2.1–2.3)

The asynchronous KV push never stalls the GPU only if cluster egress B_out exceeds the aggregate KV production rate. For an N-GPU prefill cluster with P GPUs per instance (Eq. 2) [1]:

B_out = (N/P) · E[S_kv] / E[T_prefill]  ≈  (N/P) · Φkv(L_avg)

L_avg is the mean uncached length of the requests actually offloaded. Model architecture sets Φkv. Length distribution, prefix-hit rate and routing policy set L_avg. That is why the paper needs both a model-side and a system-side lever.

2. Architecture (§3.1, Fig. 3)

A request router sits in front of two clusters, each with intra-cluster RDMA and its own hybrid prefix cache pool. Cross-cluster Ethernet connects them. A Global KVCache Manager holds KV metadata for all clusters, and a global scheduler routes each request to a cluster and then to a cache-affine node [1].

request (l_total)

   ▼
Global KVCache Manager ── prefix match per cluster → l_prfaas, l_pd

                         layer-wise pipelined, multi-conn TCP

For agentic traffic, most requests are incremental prefills on a cached prefix. The manager knows where every cached entry lives, so only the incremental part crosses clusters [1].

3. Hybrid prefix cache pool (§3.2)

The two kinds of state reuse differently [1]. Linear-attention or SWA state is request-level: constant size, and reusable only on an exact length match. Full-attention KV is block-level: it grows linearly and supports partial prefix matches. A one-format cache does not fit both. The design:

  • Separate groups per state type, with aligned block sizes so all groups allocate from one pool (vLLM’s hybrid manager design).
  • Each block is tagged prefix-cache or transfer-cache. The partial last block of a prefill stays out of the reusable cache while it is in flight.
  • The manager rebalances cache to relieve hotspots, and transfers cache across clusters when bandwidth allows (§3.4.3).

4. Transport (§3.3)

The paper gives one paragraph and no measurements [1]:

  • Layer-wise prefill pipelining sends each layer’s KV as soon as it is computed, so transfer overlaps compute. This justifies the min(compute, bandwidth) form of Eq. 3.
  • Multi-connection TCP fills a long-haul link that one TCP flow would not saturate.
  • Congestion monitoring tied to the scheduler: loss and retransmission signals trigger routing changes before queues build.

5. Throughput model (§3.4.1–3.4.2, Eqs. 3–8)

Simplifications: every PrfaaS request has length l_long = E[L | L > t], every PD-P request has l_short = E[L | L ≤ t], arrivals are uniform at rate Λ, and a fraction p = P(L > t) goes to PrfaaS [1].

Eq. 3  Θ_prfaas = min( N_prfaas / T_prefill(l_long),  B_out / S_kv(l_long) )
Eq. 4  Θ_pd-p   = N_p / T_prefill(l_short)                  (RDMA never binds)
Eq. 5  Θ_pd-d   = N_d · BS_max / (T_decode · L_out)          (SLO-fixed constants)
Eq. 6  Λ_max    = min( Θ_prfaas / p,  Θ_pd-p / (1−p),  Θ_pd-d )
Eq. 7  Θ_prfaas / p = Θ_pd-p / (1−p)                         (both producers saturate together)
Eq. 8  Θ_prfaas + Θ_pd-p = Θ_pd-d                            (producers match consumer)

Each producer sees only its share of traffic, so its capacity is divided by that share. Raising t sends fewer, longer requests to PrfaaS. For those, T_prefill grows faster than S_kv, so Φkv falls and bandwidth pressure eases, while PD-P takes more work. Θ_prfaas/p falls as p grows and Θ_pd-p/(1−p) rises, so a 2-D grid search over t and N_p/N_d finds the optimum [1].

6. Dual-timescale scheduling (§3.4.3)

Short term: bandwidth- and cache-aware routing [1].

  • The PrfaaS ceiling is B_out / S_kv(l_long) req/s. The scheduler watches egress utilization and queue depth. Near a threshold, it re-profiles and searches t again over the post-prefix-match length distribution.
  • Bandwidth scarce: caches are judged per cluster. If l_total − l_pd ≤ t, run in PD-P; otherwise PrfaaS. No cache shipping.
  • Bandwidth abundant (compute is scarce): l_prefix = max(l_prfaas, l_pd). If l_total − l_prefix ≤ t, run in PD-P; otherwise PrfaaS. If the longer prefix sits in the other cluster, ship it instead of recomputing it.

Long term: traffic-driven re-allocation [1]. If Θ_prfaas + Θ_pd-p ≪ Θ_pd-d, prefill binds; if ≫, decode binds. The scheduler reads which from per-stage queue depth and utilization. It then converts nodes between P and D roles inside the PD cluster and re-optimizes t. PrfaaS size stays fixed.

7. Case study (§4)

Setup [1]:

  • Two clusters over a VPC with ~100 Gbps aggregate.
  • PrfaaS: 32 H200 (4 instances of 8 GPUs). Local PD: 64 H20 (8 instances), 800 Gbps RDMA per node. Baseline: 96 H20 homogeneous PD.
  • Model: internal 1T hybrid, Kimi Linear architecture, KDA:MLA = 3:1, profiled with in-house vLLM.
  • Workload: truncated log-normal input lengths (μ = 9.90, σ = 1.00, range [128, 128K]), mean ≈ 27K. The median e^9.9 ≈ 20K explains why t ≈ 19.4K splits traffic ~50/50 (derived). Output fixed at 1024 tokens; SLO 40 tok/s.

Worked check: ship vs recompute

Transfer time / prefill time = Φkv / link bandwidth (derived from Eq. 1). For the 1T model at 128K (2.43 GB, 7.40 s prefill), transfer takes ~1.9 s at 10 Gbps and ~0.19 s at 100 Gbps. Shipping wins. For a dense model at 32K (Φkv ≈ 60 Gbps), shipping over 10 Gbps takes 6× longer than prefill.

Relation to known

Internet for the KV Cache (LMCache). Both argue that KV should cross datacenter boundaries when moving it beats making it again, under a global control plane [1, 2]. PrfaaS’s Φkv is the break-even test that vision needs: ship when Φkv(l) < link bandwidth. The differences:

  • Per-request P→D transfer vs cross-request reuse. PrfaaS mostly ships transfer-cache blocks: produced once, consumed once, freed. KV must reach decode anyway, so the question is where prefill runs, not whether to recompute. Cross-request reuse appears only in the “bandwidth abundant” branch, as a binary regime switch.
  • Tiers. The PrfaaS pool spans DRAM and SSD inside each cluster. There is no hot/warm/cold hierarchy across clouds and no replication [1, 3].
  • Numbers. The vision’s example (1 GB, 0.8 s at 10 Gbps vs ~15 s recompute) implies Φkv ≈ 0.53 Gbps, below every entry in Tables 3 and 5 [1, 3]. With the 1T model at 128K, shipping still wins, by ~4× rather than ~19× (derived). For dense models the vision’s argument mostly fails over 10 Gbps.
  • Evidence. Neither paper has a measured end-to-end deployment. PrfaaS is closer, with a concrete model, profiles and a workload.

llm-d planner. Both size a deployment from SLOs and per-replica capacity. The planner’s ceil(peak × 1.2 / rps_per_replica) is the one-stage form of Eqs. 4–5, and its GQA-vs-MLA KV-per-token term is the S_kv(l) input [4]. To model PrfaaS it would need:

  1. A hybrid KV model: fixed recurrent state plus per-token KV from Type B layers only. Table 5 shows 190.8 MiB already at 1K.
  2. A length distribution (P(L > t), E[L | L > t], E[L | L ≤ t]) instead of one peak RPS.
  3. Three roles on possibly different hardware, combined with Eqs. 3–6 and solved by grid search over t and N_p/N_d.
  4. A link check: B_out ≥ Θ_prfaas · S_kv(l_long).
  5. Superlinear T_prefill(l), plus T_decode and BS_max from the TPOT SLO.
  6. Headroom per stage (PrfaaS runs at Λ_max with none) and integer effects.
  7. Output of P/D role counts, a routing threshold and multi-cluster placement. Today the planner emits KServe + vLLM with no P/D config [4].

Caveats

  • Results are model output. “All throughput and bandwidth results reported below are derived by feeding the measured profiling data into the throughput model” (§4.1) [1]. There is no live cross-datacenter run, no measured transfer latency and no burst behaviour.
  • TTFT method is unstated. Table 6 gives mean and P90 TTFT, but the paper does not say how the model produces latency distributions.
  • 1.54× compares unequal costs (32 H200 + 64 H20 vs 96 H20). The same-hardware number is 1.32× over naive; the paper’s equal-cost figure is ~15%, with no pricing given [1].
  • Naive heterogeneous has better mean TTFT (1.74 s vs 2.22 s) and equal P90. PrfaaS-PD wins on throughput, not latency, against it.
  • Representative-length approximation. T_prefill(E[L | L > t]) underestimates E[T_prefill(L)] because prefill is convex in l and the distribution is wide. This overstates producer throughput; the error between configurations is unknown.
  • Uniform arrivals and steady state are assumed, yet bursts and fluctuating bandwidth are the stated motivation. The short-term scheduler, congestion monitoring and multi-connection TCP get no evaluation.
  • The link never binds (13% use), so the bandwidth-aware branches are never exercised.
  • No prefix hits in the workload. The hybrid pool and cache-aware routing have no quantitative result.
  • Decode is an SLO constant: per-decode-instance throughput is ~0.78 req/s in all three configurations, and output is fixed at 1024 tokens.
  • Internal model and engine. Table 5 uses in-house vLLM; Table 3 uses SGLang. The internal model’s Φkv trend runs opposite to public Kimi Linear’s.
  • No distance given. The link is “a VPC network” of ~100 Gbps. RTT and loss are not reported.
  • Cache-transfer tension. Fig. 4 says prefix-cache blocks stay in-cluster, while §3.4.3 ships prefix cache across clusters when bandwidth is abundant. The paper does not say which block type carries it or how it counts against B_out.
  • H20/H200 pairing. H20 has low compute and full HBM bandwidth, which favours offloading prefill. A less lopsided pair would likely give smaller gains.
  • No code release is mentioned.
