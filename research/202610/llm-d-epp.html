The Endpoint Picker (EPP) is the part of llm-d that decides which model-server replica handles each inference request. It is not a proxy. It is a service the proxy calls on every request. The proxy handles connections, TLS and forwarding. The EPP looks at live model-server state and returns the address of one pod: the one that already holds the most relevant KV-cache, has the shortest queue, or best meets a latency target. The llm-d docs call it the "brains" of an llm-d deployment [1].

The project moves fast, and the sources describe llm-d around release v0.9 and the dev branch of mid-to-late 2026.

01What EPP Is and Where It Sits

A short primer. A large language model (LLM) server such as vLLM keeps a KV-cache in GPU memory. The KV-cache holds the attention keys and values already computed for a prompt. When a later request starts with the same text (the same prefix), the server can reuse those values and skip the expensive prefill step. That only works if the request reaches the same replica that holds the cache. An ordinary load balancer, using round-robin or least-connections, cannot see any of this. It spreads related requests across pods and throws away the cache benefit [2]. The EPP exists to make this routing decision with that information in hand.

The llm-d Router = Proxy + EPP. llm-d calls its request entry point the llm-d Router. The Router has two parts [3]:

  • Proxy: "Any conformant industry-grade L7 proxy". Examples are Istio, agentgateway, Envoy AI Gateway, or a cloud load balancer such as Google Cloud's Application Load Balancer. It owns the data plane.
  • Endpoint Picker (EPP): "A specialized service that the proxy consults for every request". It holds the routing logic.

The docs fix the terms [3]:

  • llm-d Router: the whole entry point.
  • EPP: the component that makes routing decisions.
  • Inference Gateway: a synonym for the Router when it runs in Gateway Mode.
  • Request Scheduler: a sub-component inside the EPP.

Older material calls the whole thing the "inference scheduler", and Red Hat's container image is still named odh-llm-d-inference-scheduler [4].

What the EPP is responsible for. The docs give it two jobs [1]:

  1. Intelligent routing: choosing which model-server pod in an InferencePool serves a request, based on "KV-cache utilization, prefix cache locality, request queue depth, and active request counts".
  2. Fairness and prioritization: choosing which requests run at any given moment, so workloads with different priorities can share one set of model servers.

The request lifecycle. A request passes through six stages [1]:

Step Stage What happens
1 Request arrival Client request hits the proxy (gateway).
2 External processing Proxy calls the EPP over Envoy's ext-proc protocol, passing headers and body.
3 Request handling A Parser plugin converts the request (OpenAI HTTP, vLLM gRPC, or a custom format) into the EPP's internal structure.
4 Flow control If enabled, the request is queued by priority and tenant, and held while the pool is saturated.
5 Scheduling The Request Scheduler filters and scores candidate endpoints and picks one.
6 Proxying The EPP returns the chosen address. The proxy forwards the original request there.

A Data Layer runs alongside this pipeline, asynchronously. It watches the Kubernetes API for InferencePool and Pod changes, scrapes model-server metrics, and maintains in-memory structures such as a prefix-cache tree. It also talks to "consultant" sidecars: a latency predictor, a KV-cache indexer, or a tokenizer [1]. The other stages read this pre-built state. They do not query servers while a request is waiting.

A concrete deployment. Red Hat's walkthrough of llm-d on Amazon EKS shows the EPP running as a scheduler pod with two containers. The main container runs the EPP, serves gRPC on port 9002, and uses queue-scorer, prefix-cache-scorer and max-score-picker. A second container tracks prefix-cache state across vLLM replicas and shares it with the main container over ZeroMQ [4].

02Relationship to Gateway API Inference Extension and Envoy

The EPP did not begin in llm-d. Its history explains why the APIs live in one place and the code in another.

Gateway API Inference Extension (GIE). GIE is a Kubernetes SIG project that extends the standard Gateway API (Gateways and HTTPRoutes) for inference traffic. It adds an inference-aware step between matching a route and sending to a pod [5]. Its core API object is the InferencePool, which became GA (v1) in v1.0.0. An InferencePool is a group of pods that share "the same compute configuration, accelerator type, base language model, and model server". You can think of it as a Kubernetes Service built for model serving [6].

The spec has three parts: a selector for the pods, targetPorts, and an endpointPickerRef that points at the EPP service. One EPP serves exactly one InferencePool, but an HTTPRoute can reference several pools [6]. Since GIE v1.5.0, endpointPickerRef is optional, so a pool can be used without a user-managed EPP if the gateway implementation supports that [6].

The Endpoint Picker Protocol. GIE proposal 004 defines how a proxy talks to an EPP. The EPP "MUST implement the Envoy external processing service protocol" and "MUST support streaming mode", so tokens can stream back through the gateway [7]. The protocol has been versioned since February 2025:

  • v0.3.0 added subsetting and fallback.
  • v0.4.0 added multiple fallback endpoints.
  • v1.0.0 (July 2025) added a status metadata field for picked endpoints.

A data plane can also restrict the EPP to a subset of endpoints through filter metadata (x-gateway-destination-endpoint-subset). If none of those endpoints is eligible, the EPP must return an immediate error response rather than pick outside the subset [7]. llm-d's docs add one practical constraint: the only supported Envoy request_body_mode / response_body_mode is FULL_DUPLEX_STREAMED [1].

What ext-proc means. External processing is an Envoy filter that pauses a request and sends it to an outside gRPC service, which can inspect it and return instructions. llm-d describes the result as the proxy parking the request while it calls back to the EPP [3]. Because of this split, llm-d does not have to build its own proxy. Any gateway that speaks the protocol can use the EPP. At the time of the 2026 move proposal, conformant gateways included GKE Gateway, Istio, kGateway and NGINX Gateway Fabric [8].

The 2026 move of EPP code into llm-d. Until early 2026 there were two EPP images. GIE shipped a reference EPP, and llm-d's llm-d-inference-scheduler used that EPP as a library and added plugins. In February 2026, GIE maintainers proposed moving the EPP implementation into llm-d. Their reason was that advanced plugins, "like P/D and precise kv-cache aware scheduling", were mostly being built in llm-d, which led to "fragmented code and duplicate maintenance" [8].

Under the proposal, the InferencePool API, the EPP protocol and the conformance tests stay in Kubernetes, and a lightweight EPP is kept there for conformance testing. The full EPP moves to llm-d [8]. The EPP code now lives in the llm-d/llm-d-router repository under pkg/epp/ [9]. The split works like Gateway API itself: Kubernetes defines the standard and its conformance tests, and implementations such as the llm-d EPP compete on top of it.

03Scheduling Architecture: Profiles, Filters, Scorers, Pickers

The Request Scheduler is the EPP's decision engine. Each part of it is a plugin, so you can change the routing policy without changing EPP code.

The basic loop: Filter → Score → Pick. For each request, a scheduling profile runs three stages [10]:

  1. Filters run in sequence and remove ineligible endpoints. Examples: keep only pods with a given label, or keep only prefill-role pods.
  2. Scorers give each remaining endpoint a score from 0.0 to 1.0. Each scorer has a weight. The endpoint's final score is the weighted sum.
  3. A Picker chooses the final endpoint or endpoints from the scored list.

The docs give a worked example. If Scorer A (weight 2.0) returns 0.8 and Scorer B (weight 1.0) returns 0.5, the endpoint scores (0.8 × 2.0) + (0.5 × 1.0) = 2.1 [10]. Weights are how an operator trades off goals. Red Hat OpenShift AI's default, for example, weights prefix-cache hits at 3 and queue depth at 2, which "prioritizes KV cache reuse over even load distribution" [11].

Profiles and profile handlers. A request may need more than one Filter → Score → Pick pass. The ProfileHandler plugin first decides which profiles to run (Pick), then merges their results (ProcessResults) [10]. The default single-profile-handler runs one profile. The disagg-profile-handler runs separate prefill and decode profiles (see Section 4). Its predecessor, pd-profile-handler, still appears in older write-ups, and the deprecated data-parallel-profile-handler should be replaced with single-profile-handler [10] [12].

The built-in plugin catalog. Not every plugin is enabled by default. The catalog in the current docs [10] includes:

Stage Plugin What it does
Filter prefix-cache-affinity-filter Probabilistically narrows candidates to "sticky" pods with high prefix-cache scores. A TTFT load gate breaks stickiness if those pods are much slower.
Filter label-selector / prefill-endpoints-filter / decode filter Keep endpoints matching a label, or only prefill-role or decode-role pods.
Filter SLO headroom filter Keeps endpoints by SLO headroom tier.
Scorer prefix-cache-scorer Scores by length of prefix-cache match. Reads data from an approximate or precise producer.
Scorer queue-scorer Prefers shorter request queues.
Scorer kv-cache-utilization-scorer Prefers lower KV-cache utilization.
Scorer running-requests-size-scorer Scores by number of active requests.
Scorer token-load scorer Scores by total input+output tokens in flight.
Scorer LoRA affinity scorer Prefers pods with the requested LoRA adapter already loaded, or room to load it.
Scorer latency scorer Scores by predicted latency headroom against the user's SLO.
Scorer session-affinity scorer Max score to the pod that served the session's previous requests.
Scorer no-hit LRU scorer For cold requests, spreads prefill load to pods that have never, or least recently, served one.
Picker max-score-picker Highest score wins. Default, auto-injected when a profile names no picker.
Picker random picker Uniform random choice.
Picker weighted-random picker Random choice with scores as probabilities ("lottery scheduling").

Request-control plugins outside the scheduler. Some plugins run before or after scheduling, not inside a profile. DataProducers prepare per-endpoint data before the scheduler runs. For example, the approximate and precise prefix producers attach a PrefixCacheMatchInfo attribute to every candidate pod, which prefix-cache-scorer then reads [13]. PreRequest hooks run after a pick. The prefix producers use one to record that the chosen pod now holds the prefix [14]. This separation keeps scorers simple. A scorer reads attributes, and the work of maintaining indexes lives in the producers.

Flow control. Flow control comes before scheduling, as an admission layer. It holds requests in an in-memory queue when a saturation detector reports the pool is full. It groups traffic into priority bands, for example chat ahead of batch summarization. Within a band, it shares dispatch turns among tenants using a pluggable FairnessPolicy (such as round-robin) and orders requests within a flow using an OrderingPolicy (such as FIFO or SLO-based) [1]. Red Hat describes the order of operations: when pool saturation is at or above a band's configured ceiling, the dispatch gate "keeps requests in that band queued in the Endpoint Picker" until the band may dispatch, and only then does scheduling choose a pod [15]. Red Hat reports this feature as GA in Red Hat AI Inference 3.5 (a vendor product claim) [15]. In short, flow control decides when a request is sent and scheduling decides where it goes.

04Routing Signals: Prefix-Cache, Load, LoRA, and Disaggregation

Load signals

The basic signals come from model-server metrics scraped by the Data Layer: queue depth, KV-cache utilization and running-request count [1]. GIE defines a model-server protocol that pods must follow to join an InferencePool, so the EPP can get these numbers in a consistent form [6]. Load-only scheduling avoids hot spots. It does not see the cache.

Prefix-cache affinity: approximate vs precise

This is the EPP's main feature, and it comes in two versions [16]:

  • Approximate (approx-prefix-cache-producer): the EPP keeps its own record of where it sent which prefixes. It hashes the prompt's tokens into fixed-size blocks and keeps an in-memory LRU index of which pods recently served which block hashes [13]. It needs no model-server integration. If no tokenizer is configured, the framework auto-creates a tokenizer-free estimate backend, so it "works without extra setup" [13]. The cost is drift: the index is a guess about cache contents and can diverge from reality once pods evict blocks [16].
  • Precise (precise-prefix-cache-producer): the model servers report what they cache. vLLM (and SGLang) emit KV-events over ZeroMQ when blocks are added or evicted. A KV-block index in the EPP's Data Layer turns these events into a cluster-wide block-to-pod map [16] [14]. On each request, the producer hashes the tokenized prompt into block keys, looks them up, and writes per-pod match info. Optionally, it adds speculative entries for the chosen pod right away, with a TTL, so a burst of follow-ups does not wait for the real event [14].

The costs are more moving parts: a tokenization endpoint (vLLM's render endpoint), ZMQ connectivity, and engine support for KV-events [16]. Engine support is uneven. vLLM emits the extra_keys needed for multimodal and cache_salt correlation, but SGLang does not, so salted SGLang requests are precise-cache misses [14].

Both producers feed the same prefix-cache-scorer. You choose one by setting the scorer's prefixMatchInfoProducerName. If it is unset, the scorer falls back to the approximate producer, and the older single-plugin precise-prefix-cache-scorer is deprecated [10].

What difference does it make? The llm-d project's own benchmark compares four schedulers on a prefix-heavy workload whose total cache demand was sized at about six times a single pod's capacity [2]:

Scheduler Output tok/s TTFT p90 (s) TTFT mean (s)
precise prefix + load 8,730 0.542 0.298
approximate prefix + load 6,944 31.08 13.32
load only (queue + KV util) 4,429 94.87 46.99
random 4,429 92.55 45.28

The project summarizes this as precise scheduling being "57x faster" in p90 TTFT than approximate, with about 25% more throughput [2]. Two cautions apply. This is the project measuring itself, and the workload was built to stress cache placement. The upstream GIE launch blog is more modest. Compared with a plain Kubernetes Service on 10 Llama2 replicas, it found "roughly on par" throughput and "significantly lower" p90 latency only above about 400–500 QPS [5]. Both results point the same way: the EPP helps most when the cache is under pressure and the workload shares prefixes, as in multi-turn chat or agent loops, and helps less otherwise.

LoRA adapters

When many fine-tuned LoRA adapters share a base model, a LoRA affinity scorer prefers pods that already have the requested adapter loaded, or have room to load it [10]. Adapter-aware routing was one of GIE's original goals [5].

Predicted latency

For workloads where prompt and output lengths vary widely, queue depth is a poor stand-in for load. llm-d offers a path where an XGBoost model, trained online on observed traffic, predicts each pod's TTFT and TPOT. A latency-scorer then picks the pod with the most headroom against a per-request SLO. The training and prediction servers run as EPP sidecars [17]. The docs warn that this path does not suit heterogeneous pools (mixed GPUs, or prefill and decode pods in one pool), "because the predictor assumes a single pod shape" [17].

Prefill/decode disaggregation

Disaggregated serving runs prefill (compute-bound) and decode (memory-bandwidth-bound) on different pods, so long prefills do not stall ongoing decodes. Each side can then be tuned separately, for example with a different tensor-parallel size [18]. The EPP coordinates this through the disagg-profile-handler [18]:

  1. Run the decode profile (filter → score → pick) to choose a decode pod.
  2. Ask a decider whether, given how much of the prompt is already cached on that decode pod, disaggregation is worthwhile.
  3. If not, return only the decode pod. If so (a large uncached suffix), also run the prefill profile to choose a prefill pod.
  4. Return the decode pod as the primary destination and put the prefill pod's address in a request header [10].

A routing sidecar next to the decode worker reads that header. It sends the prompt to the prefill worker with max_tokens=1, gets back KV-transfer parameters, and the decode worker pulls the KV-cache over NIXL (RDMA) [18]. Without RDMA, NIXL falls back to TCP, which the docs call suitable only for testing [18]. Prefill/decode roles are assigned by pod label, and dedicated filters keep each profile on the right pods [10]. In Red Hat's OpenShift AI example, the prefill profile used only a queue scorer, while the decode profile added a cache scorer [12].

05Configuration, Deployment, and Reported Results

The EndpointPickerConfig file. The EPP is configured with one YAML document whose apiVersion is llm-d.ai/v1alpha1 and whose kind is EndpointPickerConfig. It is passed with --config-file (usually a mounted ConfigMap) or --config-text [19]. It looks like a Kubernetes custom resource but is not a CRD. No controller reconciles it, and it is "only read on startup", so any change needs an EPP restart [19].

The docs suggest reading the config as a graph [19]:

  • Nodes: the top-level plugins: list creates named plugin instances with their parameters.
  • Edges: sections such as schedulingProfiles: and flowControl: refer to those plugins by name and give them a role.
  • Auto-wiring: plugins that implement certain interfaces (DataProducer, PreRequest, response processors, Admitter) are bound to their role automatically, without an explicit edge.
  • Validation: every reference must resolve, profile names must be unique, and metric extractors must form a DAG with no cycles.

Other top-level sections are featureGates (for example, enabling flow control), requestHandler, flowControl, and dataLayer [19]. A minimal aggregated-serving config combines these pieces. In the sketch below, plugin type names come from the docs, and the weights are illustrative, matching the OpenShift AI default described above:

apiVersion: llm-d.ai/v1alpha1
kind: EndpointPickerConfig
plugins:
  - type: approx-prefix-cache-producer
  - type: prefix-cache-scorer
  - type: queue-scorer
  - type: max-score-picker
schedulingProfiles:
  - name: default
    plugins:
      - pluginRef: prefix-cache-scorer
        weight: 3
      - pluginRef: queue-scorer
        weight: 2
      - pluginRef: max-score-picker

You can declare a plugin more than once with different names. For example, two approximate prefix producers with different block sizes can model GPU and CPU cache tiers, each feeding its own scorer [13].

Plugin maturity. Each in-tree plugin has a stability level:

  • Alpha plugins need the --allow-experimental-plugins flag and carry no compatibility guarantee.
  • Beta plugins are on by default, with a two-minor-release deprecation policy.
  • Stable is reserved for later: "all in-tree plugins are classified as Alpha or Beta" until the project nears 1.0 [9].

Some plugins also have multicluster variants, where a cluster-scoped EPP treats whole clusters as its candidate endpoints and scores them on pool-aggregate metrics [9].

Deployment surfaces. The EPP is deployed differently on each platform:

  • Plain Kubernetes: the EPP runs as a Deployment that an InferencePool's endpointPickerRef points to [6].
  • Red Hat OpenShift AI: KServe's LLMInferenceService resource generates the EPP. Scheduler settings can be inline or in a ConfigMap (the two are mutually exclusive) [11].
  • AKS: Microsoft's reference design uses the GIE Endpoint Picker as the third of three routing decisions. The semantic router decides which model, the AI gateway enforces policy, and the EPP decides only "which replica" [20].

Observability. The EPP exports pool-level Prometheus metrics, including llm_d_epp_ready_endpoints, llm_d_epp_average_kv_cache_utilization, llm_d_epp_average_queue_size, and the standard deviations of KV utilization and queue size [10]. The standard deviations are a direct way to check whether load is actually balanced across the pool.

06Limitations and Open Questions

Bursty load can herd onto one pod. An llm-d contributor found a case where the EPP did worse than Knative's simple request-count balancing. Eight Llama-3.3-70B replicas received concurrency-mode traffic with fixed 1,000/1,000-token requests, scored only with queue and KV-utilization scorers. The result was slightly lower throughput and "significantly worse TTFT", because "when many requests arrive simultaneously they get routed to the same Pod" [21]. A maintainer attributed this to metric staleness. Metrics refresh about every 50 ms, so a burst all sees the same best pod until its numbers update [21].

The reporter called it a corner case chosen to favor Knative and said llm-d "significantly outperforms" Knative when lengths vary or prefix caching applies. The discussion produced a weighted-random picker, which adds randomness in proportion to score [21]. The underlying point holds for any picker that scores on lagging metrics: the default max-score-picker is deterministic, and that becomes a weakness when the data is stale.

Approximate vs precise is a real trade-off. Approximate routing is free to deploy but can drift from the true cache contents [16]. Precise routing is accurate but depends on the engine (KV-events, extra_keys support) and adds a tokenizer and a ZMQ event stream, whose events "arrive at many times the inference request rate" [14]. Long prompts also raise EPP CPU usage when the match caps are lifted [13].

Operational rough edges. Several practical issues remain:

  • Config reloads: config changes need a restart, because the config is read once at startup [19].
  • Maturity: no plugin is yet Stable [9].
  • Naming churn: names change often. pd-profile-handler became disagg-profile-handler, and precise-prefix-cache-scorer became a producer + scorer pair [10]. Microsoft's AKS guide warns that field names "drift between releases" and tells readers to pin versions [20].
  • Hardware and topology fit: predicted-latency routing does not suit mixed-hardware or mixed-role pools [17], and disaggregation needs RDMA to be worthwhile [18].

Governance: whose EPP is it? Moving the EPP into llm-d was contested. One GIE contributor argued that GIE's value was "neutral governance". Other frameworks, such as NVIDIA Dynamo (which already had an EPP derived from the GIE library) or Ray Serve, would now have to import "a competitor's (i.e llm-d's) EPP" [8]. The proposers answered that the standard is the InferencePool API and the protocol, not the implementation: "why should k8s pick a winning EPP?" They committed to keeping a lightweight conformance EPP in Kubernetes [8].

The evidence favors the proposers' framing. Gateway API itself standardizes interfaces and leaves implementations to others, and the EPP protocol is open to any implementer. Whether other EPP implementations actually emerge is still an open question.

Open questions worth watching:

  • Independent benchmarks. The large published gains come from the project or its sponsors. No third-party comparison of EPP scheduling against least-request balancing on realistic mixed traffic turned up in this research.
  • How the deterministic default picker and the weighted-random picker compare across workloads, given the herding issue.
  • Whether the predicted-latency path can handle heterogeneous pools, which disaggregated deployments create by design.
  • How the EPP protocol evolves now that its main implementation sits outside the standards body.
