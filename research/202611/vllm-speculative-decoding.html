Speculative decoding takes one JSON flag to enable, --speculative-config on the CLI or speculative_config in Python [1]. No configuration is best in general. Claims here apply to vLLM 0.32.0, the latest release (2026-10-18), unless marked as main [2]. Try a native multi-token prediction (MTP) head first, then an EAGLE-3, DFlash or DSpark checkpoint matched to your exact target, and reserve ngram_gpu or suffix for copy-heavy traffic. Keep a setting only if it beats a no-speculation run at your real concurrency and objective. Load is only one way to lose: fixed 7-token DSpark fell about 26 to 33% below no speculation at concurrency 256 (main 32881ec177, four-GPU B300) [3], and n-gram lost at a single request (vLLM 0.19.1, one A30) [4]. At high load, test speculation only with a budgeted or short draft, and keep it only if it wins at your latency target and survives an overload test.

1. How Speculative Decoding Works in vLLM

1.1 The trade

Ordinary decoding produces one token per forward pass. Speculative decoding adds a fast predictor, the drafter, which guesses the next k tokens (num_speculative_tokens). The target model checks all k in one pass, keeps the accepted prefix and adds one token of its own [5]. With the standard verifier, the output distribution is preserved up to numerical limits [1]. You pay for drafting and for verification slots spent on rejected guesses.

With per-token acceptance a, and c as the cost of a draft step relative to a target step, tokens per step are L = (1 − a^(k+1)) / (1 − a), and speedup is S = L / (kc + 1) [6]. This assumes verifying k+1 tokens costs about the same as verifying one. That holds while the GPU is memory-bound, waiting on memory bandwidth with compute to spare, and can fail once it is compute-bound [6, 7]. The docs therefore scope the feature to medium-to-low queries per second (QPS) on memory-bound workloads [1]. The same page’s qualitative table still rates every method medium gain or better at high QPS, without numbers. The long fixed-draft losses in Section 5.1 contradict it [1, 3]. By this report’s calculation, at a = 0.5 the model gives 1.63x for k=3 and c=0.05 but 0.98x for k=5 and c=0.20.

1.2 Three ways to lose

Saturation happens when the verification batch uses up the available compute. The docs frame that batch as batch size times k [8]; this report counts k+1 to include the extra token the target adds. A load policy fixes it, and PR #47808 is the measured case [3].

Cost loss happens when the drafter, per-step overhead or a badly chosen k returns less than it costs, even with no queue. Only a different method, k or setup helps. Alauda’s n-gram test is one example: 0.98x on code refactoring and 0.85x on chat (Qwen3-8B BF16, vLLM 0.19.1 V1 engine, one A30 24 GB, temperature (T) 0, k=5, one concurrent request, median of 3 runs) [4]. Alauda blames proposer work, verification and disabled async scheduling together, and calls it a reminder to measure, not a verdict on n-gram. ngram_gpu keeps async but has no such test.

Memory pressure is the third: draft weights and KV compete with the target’s KV cache, so fewer requests fit. Neither a k schedule nor a verification budget frees that memory. Nightjar offloads the draft [9]; no such vLLM mechanism was found.

Method Proposer GPU memory cost Drafting share of step time
mtp Heads inside the target; Gemma 4 adds an assistant checkpoint [10] Low per NVIDIA, no figure [11] Not measured on current vLLM
eagle, eagle3 Small trained head fed by target hidden states +1.4 to 5.3% of weights [6] 12 to 20% at batch 1 [6]
dflash, dspark Matched block drafters emitting many tokens per pass [12] No figure published Not measured
draft_model Separate small LLM +1.8% (1B on 70B), +7.3% (0.6B on 8B) [6] 21% and about 47% at batch 1 [6]
ngram, ngram_gpu Prompt lookup Zero for CPU ngram [6]; negligible per NVIDIA [11] Under 2% for CPU ngram [6]
suffix CPU suffix trees over prompt and past outputs [13] CPU side About 10% total overhead at concurrency 64, version unstated [14]

The study figures are from vLLM v0.10.1.1 on H100 with greedy sampling, and memory numbers are analytical. Verification took 42 to 95% of runtime there, so tuning mainly aims to avoid verifying tokens that will be rejected [6].

2. Running Speculative Decoding

No command in this report has been run. Each is composed from v0.32.0 code and current docs, so check --help on your build.

2.1 Pin the version and take a baseline

pip install "vllm==0.32.0"
vllm serve "$TARGET" --tensor-parallel-size "$TP" --max-model-len "$MML" --max-num-seqs 256

Pin because the docs site follows main (Section 3.2). Tensor parallelism (TP) splits one model across GPUs. The --max-num-seqs default of 128 caps the batch below the top of a high-concurrency sweep [15]. Save output throughput and time per output token (TPOT) at each concurrency.

2.2 Launch the first drafter that fits

# Native MTP head: no draft weights.
vllm serve XiaomiMiMo/MiMo-7B-Base --tensor-parallel-size 1 \
  --speculative-config '{"method":"mtp","num_speculative_tokens":1}'

# Gemma 4: MTP with an assistant checkpoint
vllm serve google/gemma-4-26B-A4B-it --max-model-len 8192 --language-model-only \
  --speculative-config '{"method":"mtp","model":"google/gemma-4-26B-A4B-it-assistant","num_speculative_tokens":1}'

# EAGLE-3 with a released head
vllm serve Qwen/Qwen3-8B --tensor-parallel-size 1 \
  --speculative-config '{"method":"eagle3","model":"RedHatAI/Qwen3-8B-speculator.eagle3","num_speculative_tokens":3}'

# Block drafter (DSpark example in the load policy below)
vllm serve Qwen/Qwen3-8B \
  --speculative-config '{"method":"dflash","model":"z-lab/Qwen3-8B-DFlash-b16","num_speculative_tokens":7}'

# Separate draft on a large same-vocabulary target. Untested; the draft is gated and needs approval.
vllm serve "$TARGET" --tensor-parallel-size "$TP" --gpu-memory-utilization 0.8 \
  --speculative-config '{"method":"draft_model","model":"meta-llama/Llama-3.2-1B-Instruct","num_speculative_tokens":3}'

# Copy-heavy traffic. This ngram_gpu window is an untested combination.
vllm serve "$TARGET" \
  --speculative-config '{"method":"ngram_gpu","num_speculative_tokens":5,"prompt_lookup_min":3,"prompt_lookup_max":5}'

# Suffix, after: pip install arctic-inference==0.1.1
vllm serve "$TARGET" --speculative-config '{"method":"suffix"}'

If the Gemma startup log shows SpeculativeConfig(method='draft_model', ...), your vLLM is too old for this path [1, 10]. The long EAGLE-3 form lets you change k or pair the head with a quantized target [16], while vllm serve RedHatAI/Qwen3-8B-speculator.eagle3 reads the target from the checkpoint’s speculators_config [17]. Block-drafter settings follow AMD’s runs [12]. The docs’ draft_model examples pair Qwen/Qwen3-0.6B with 4B or 8B targets at k=5 [18]. Do not copy them, since that draft costs about 37.5% of an 8B step [6].

2.3 Run offline

from vllm import LLM
llm = LLM(model="Qwen/Qwen3-8B", tensor_parallel_size=1, disable_log_stats=False,
          speculative_config={"method": "eagle3", "num_speculative_tokens": 3,
                              "model": "RedHatAI/Qwen3-8B-speculator.eagle3"})

The keys match the CLI, and disable_log_stats=False lets llm.get_metrics() report acceptance [19].

2.4 Check what actually ran

The startup log should show your method. vLLM warns when it falls back to the older V1 runner, and logs when a method turns async scheduling off [20]. Then read the counters:

curl -s localhost:8000/metrics | grep spec_decode
# mean acceptance length = 1 + _num_accepted_tokens_total / _num_drafts_total

A mean acceptance length of 1 means nothing is accepted, which usually points to a mismatched drafter [5, 21]. --speculative-model is deprecated [18]. --speculative-disable-by-batch-size has no matching field in v0.32.0’s config. The gauge vllm:spec_decode_draft_acceptance_rate is absent from main’s metrics code, so ignore guides built on them [22, 23]. Allow for slow startup in readiness probes: about 5 minutes for an EAGLE-3 head on one A30 (vLLM 0.19.1) [4].

2.5 Sweep on your own prompts

Run once per arm. Repeating vllm bench serve on one server can reuse prefix-cached prompts and inflate throughput, so restart the server before every level of every arm [3, 24]:

for conc in 1 4 16 32 64 128 256; do
  restart_server_and_warm_up  # your own step; warm up on other prompts
  vllm bench serve --backend openai-chat --endpoint /v1/chat/completions \
    --base-url http://127.0.0.1:8000 --model "$MODEL" --tokenizer "$MODEL" \
    --dataset-name custom --dataset-path prompts.jsonl --skip-chat-template \
    --custom-output-len "$PROD_OUTPUT_LEN" --num-prompts 256 \
    --max-concurrency "$conc" --request-rate inf --disable-shuffle \
    --temperature "$PROD_TEMP" --seed 0 \
    --save-result --result-filename "${ARM}_c${conc}.json"
done

vllm bench sweep serve resets caches between runs; check --help for these flags [24]. Without a prompt log, use --dataset-name speed_bench with --speed-bench-dataset-subset (qualitative for acceptance, throughput_1k through throughput_32k for speed) [24]. Add --speed-bench-output-len as in PR #47808’s harness [3]. This sweep is closed-loop, meaning each client waits for its last response, so it cannot show queueing. Repeat the winner and the baseline with a finite --request-rate and --burstiness 1.0 (Poisson arrivals) at and above your traffic rate [24].

3. Configuration Reference

Everything lives in one object: a JSON string on the CLI, a dict in Python, or a nested mapping in YAML [1]. The keys also select a runner, vLLM’s internal execution path: V2 is modern, and V1 is the older path some methods force.

3.1 Keys that affect performance (v0.32.0)

3.3 How the runner is chosen

On main, VLLM_USE_V2_MODEL_RUNNER defaults to None [27]. With it unset, the v0.32.0 code path uses V2 unless the config has an unsupported feature, then warns and falls back to V1 [20]. On v0.32.0, the Section 6 matrix shows which methods force V1 or lose async scheduling. Async scheduling lets the engine prepare the next step while the current one runs [20].

Leave the variable unset, because setting it skips the fallback logic [20]. The Dynamic Speculative Decoding page’s examples set it to 0, yet on V1 that feature gets only piecewise and not full CUDA graphs. Do not copy that prefix [8].

4. Which Configuration to Use

CoreWeave and NVIDIA both order methods as MTP, then EAGLE-3, then n-gram as a fallback [5, 11]. That order follows effort and is not a ranking, because no source compares these methods on one build, GPU and load.

4.1 Starting points

On AMD’s sweep native MTP beat DFlash on Qwen3.5-27B, Qwen3.5-122B-A10B and Qwen3.6-27B, while DFlash won on Qwen3.6-35B-A3B, 1.77 to 2.06x against 1.28 to 1.49x [12]. The docs suggest starting MTP at k=1 [10], but on that model it gave 0.87 to 0.89x at k=1 and 1.49x at k=6 [12]. amd/PARD-Qwen3-0.6B with parallel_drafting falls back to V1 on v0.32.0, and no benchmark on a current release was found [29, 20].

Small dense targets such as Qwen3-8B are the danger zone, and the table’s figures for them are per-workload peaks. On AMD’s sweep a Thinking EAGLE-3 head gave 0.71, 0.91 and 0.99x on GSM8K at k=1, 2 and 3, rising with k, so shorter is not safer there. DSpark gave 0.73x at k=3 on MATH500 [12]. The 2.2 Qwen3-8B commands show syntax, not a recommended pairing.

4.2 Matched drafters, and when a draft model pays

A matched drafter was trained against your exact target; one from another base model can fail to load or give near-zero acceptance [5]. Look for drafters here [12]:

  • Red Hat AI (-speculator.eagle3, .dflash, .dspark)
  • Z-Lab (<target>-DFlash)
  • DeepSeek DeepSpec
  • LightSeek (Kimi)
  • Inferact (MiniMax, Kimi)
  • Google (Gemma 4)

Quantization is less clear-cut: CoreWeave warns a different quantization can fail to load [5]. Yet Speculators documents pairing a head with a quantized target [16], and AMD ran BF16 and FP8 drafts against an MXFP4 target [28]. Test the pair and read the logs. LiLiCorr, a variant run through method: dflash, strongly recommends k at exactly block size minus 1 [30].

A separate draft model costs about 12.5% of a target step for 1B on 70B and an estimated 37.5% for 0.6B on 8B. That explains why it wins on the first and trails on the second despite higher acceptance there (about 81% against 76% on GSM8K) [6]. A draft about 8x cheaper than the target is a rough guide inferred from those two ratios, never a measured threshold. CoreWeave’s view that draft_model is rarely the better choice [5] fits 8B-class targets and is too broad for 70B-class ones.

4.3 Copy-heavy traffic: n-gram or suffix

Above about 0.6 BLEU-4 (a text-similarity score) between prompt and output, n-gram beat EAGLE and EAGLE-3 by up to 53% at k=3 on Llama3.1-8B; at low overlap it lost 10 to 17% at small batch (v0.10.1.1, H100, T=0) [6]. Overlap alone is not sufficient: CoreWeave saw ngram slow a mixture-of-experts model below no speculation, without publishing numbers [5].

vLLM’s merge benchmark (PR #25784, H200, SpecBench, version not stated, C for concurrency) gives the window evidence. At k=5, lookup 3 to 5 beat 5 to 5 at every concurrency, and suffix with its cache led both:

Arm TPOT at C=1 TPOT at C=64
Lookup 3 to 5 5.21 ms 10.66 ms
Lookup 5 to 5 5.6 ms 11.07 ms
Suffix with cache 4.4 ms 10.55 ms

Keep n-gram k low: at k=32 and C=64, 3-to-5 reached 13.37 ms against 11.83 ms for 5-to-5, a k effect and not a load flip [31]. That table has no no-speculation arm. Against vanilla decoding, Snowflake reports 1.96 to 3.12x on BlazeEdit and 1.0 to 1.28x on SpecBench, a vendor figure with no stated vLLM version [14].

Start with ngram_gpu on v0.32.0 as the lower-risk arm, not the expected winner, and choose suffix when outputs repeat across requests [13]. Suffix forces V1 and turns async off [20], while async added 20.6 to 39.4% over sync ngram_gpu (PR #29184, H20, Qwen3-1.7B, CMU-DoG, k=3, 2 to 16 prompts, late 2025 build) [32]. Snowflake reports suffix 1.11 to 1.17x over best n-gram on SpecBench and 1.02 to 1.31x on BlazeEdit, vendor-run [14]. Nobody has measured suffix against ngram_gpu directly, so A/B them. Snowflake’s cap of 16 or 32 assumes its depth of 64 [14]. With vLLM’s 24, leave the cap at its default, which logs a warning, or no higher than the depth [22].

4.4 Train last

No controlled trained-versus-released head comparison was found. NVIDIA says a head tuned to your traffic “will usually beat the default”, without numbers [11]. DeepSpec’s default Qwen3-4B setup needs roughly 38 TB of target cache and assumes one 8-GPU node [33]. Try EAGLE 3.1 first: it loads through method: eagle3, and its authors claim up to 2x longer acceptance length on long context [34]. Train when no head exists for your target, or when acceptance falls short on your domain or in thinking mode [33]. Use the Speculators library [17] and select checkpoints by served acceptance length [28].

5. Getting the Best Performance

5.1 What the load evidence supports

Setup Version, hardware Load Result
EAGLE, Llama3.1-8B, GSM8K, k=3 v0.10.1.1, H100, greedy Closed loop, batch 1 to 128 1.73x falling to 1.21x [6]
EAGLE 3.1, Kimi-K2.6-NVFP4, k=3 Main before v0.22.0, GB200, TP=4 C=1, 4, 16, coding 2.03x, 1.71x, 1.66x per user [34]
Fixed DSpark, V4-Flash, k=7 Main 32881ec177, B300, TP=4, T=1.0 Closed loop, C up to 256 About 26% (chart) to 33% (text) below no speculation at C=256 [3]
Adaptive DSpark, same model Same Same Above no speculation at C=256; within 3% of fixed k at C≤64 [3]

The rule that speculation loses at high load has real support, but older evidence is dated. Nightjar’s open-loop loss of up to 30.25% used a 7B target with a 0.5B draft (vLLM 0.8.2, RTX 4090, high load) [9]. vLLM’s 2024 V0-engine post reported 1.4x and 1.8x slowdowns on Llama3-70B (4x H100, high QPS, value not given) [35]. The MLSys study cannot refute the rule: it shows no vLLM result below 1x at k=3 up to batch 128, but with a closed loop, greedy decoding and one k. Its statement about slowing under load is background from the goodput paper [6, 36].

PR #47808 is the strongest modern evidence, because its chart varies k. Approximate readings by eye at C=256: adaptive 11,500 tok/s, k=1 10,000, k=2 8,850, no speculation 7,850, k=3 6,450, k=7 5,800. Among fixed arms only k=1 and k=2 beat no speculation. At C=128, k=7 already lost, 4,700 against 5,750. The PR is inconsistent: text says 33% and 256 prompts, chart about 26% and 880. Its no-speculation arm shared a node and was modestly depressed, so the true fixed-k deficit is probably larger and adaptive’s margin smaller [3].

On the docs’ batch-size-times-k framing [8], this report’s arithmetic with k+1 gives 512 tokens per step for the MLSys study and 2,048 for the PR [6, 3]. That helps explain how the results coexist. By this report’s arithmetic, every losing arm has C times (k+1) of at least 1,024, the run’s CUDA graph capture size. Cost jumps past captured graphs [3, 15]. That may contribute, but k=3 at C=256 and k=7 at C=128 sit exactly at the limit, so leaving captured graphs cannot explain those two. The default --max-num-seqs of 128 is no protection, since k=7 already lost at C=128 [15, 3].

The crossover also depends on the drafter. In SGLang, not vLLM, original EAGLE fell to 0.93x at batch 24 while EAGLE-3 gave 1.38x at batch 64 (v0.4.4, H100, Llama-3.1-8B, MT-Bench, chain of 3) [37]. No current source gives a crossover for a given model and GPU.

5.2 State your objective first

A high-load loss is a matched-concurrency claim. A service targeting, say, 60 tokens per second per user runs each configuration at whatever load still meets the target. A faster per-user configuration reaches it at higher load. By this report’s inference, a loss at C=256 matters only if you would run at C=256.

On InferenceX, DeepSeek R1 on B200 FP4 gives 8906.5 tok/s/chip with MTP against 1518.4 with it off, at a matched 62 tok/s/user, about 5.9x [38]. The engine is not stated and values are interpolated, so it is not a vLLM result. vLLM’s own post plots adaptive DSpark well outside no speculation on the best-trade-off curve, as a figure with no table (DeepSeek-V4-Pro-0813, TP=8, 8x B300, T=1.0, C=1 to 256, main 73b8394) [15].

Sizes do not transfer, because ratios at matched speed inflate when the baseline nears its limit. DSpark’s authors report nominal +661% and +406% at their strictest target for that reason. They treat their 60 to 85% and 57 to 78% per-user gains at matched throughput as more stable. Those are DeepSeek’s own serving system against MTP-1 and need kernel changes the paper describes, so they are not vLLM results [39]. Batch jobs have no speed target, so peak throughput decides, and under overload queues grow however good the curve looks.

5.3 Adaptive verification

Adaptive verification scores each draft slot by survival probability and admits the best slots until a budget from a startup cost profile is spent [7]. On DeepSeek-V4-Pro-0813 the last of 7 drafted tokens survives under 10% of the time against over 70% for the first (main 73b8394, TP=8, 8x B300) [15]. In PR #47808, accepted length fell only from about 3.9 to 3.5, and GSM8K accuracy held at 0.945 to 0.951 (256 prompts, 512 output tokens) [3].

That test is closed-loop, capped at C=256, and on main. A user comment on the PR, with no numbers, reports minimal gain with long contexts and mixed prefill (prompt processing) and decode batches. An open issue (#54046) says the profiler measures a batch shape the scheduler cannot produce [3]. Neither is a measurement.

The v0.32.0 docstring and the docs’ method table say DSpark only, and they appear stale [22, 1]. In the code, BaseSpeculator assigns the flag for all speculators. Drafters with no confidence head use an online acceptance estimator, and validators do not check the method [40, 41, 20]. Benchmarks exist only for DSpark. SmartSpec, an earlier goodput policy, claims up to 3.2x lower latency at low rates and only maintained performance at high rates [36]. This report reads that as the ceiling for a costly drafter: a budget can stop a loss without producing a win.

  1. --data-parallel-size above 1 (several engine replicas, or ranks). vLLM disables the schedule, because ranks could pick different k and deadlock [8].   2. N-gram and suffix. No load mechanism is documented or tested [7, 8]. If peak load puts them below baseline, route peak traffic to a pool without speculation, which is this report’s suggestion and not a tested design.

5.5 Use acceptance to diagnose and to choose k

vLLM’s acceptance rate is accepted over drafted tokens, so it falls mechanically as k grows [21]. By this report’s calculation, independent per-token acceptance of 0.8 reads as 0.65, 0.54 and 0.45 at k=3, 5 and 7. Break-even runs from 0.13 (c=0.05, k=3) to 0.75 (c=0.375, k=7), so fixed cut-offs such as disabling below 0.5 do not transfer. This report’s calculation, no queueing:

Best k c=0.05 c=0.10 c=0.20
a=0.8 8 6 4
a=0.5 3 2 1

Overshoot is cheap for a good cheap drafter (a=0.8, c=0.1: k=5 2.46x, k=7 2.45x) and costly otherwise (a=0.5, c=0.2: k=1 1.25x, k=5 0.98x).

Divide mean acceptance length by measured speedup to get R, the real cost of a speculative step relative to a plain step. By definition, speculation wins only while acceptance length exceeds R. MiniMax-M3 EAGLE-3 on MBPP (0.23.1rc1.dev1120, MI355X, load unstated) gives 3.82 tokens at 1.97x with k=4, so R = 1.94, and 4.18 tokens at 1.93x with k=5, so R = 2.17 [12]. Position 5 returned 0.36 tokens and cost 0.23 of a plain step.

A position pays only if its survival probability exceeds its cost times the current speedup. Here 0.23 × 1.97 = 0.45, above the 0.36 returned, and throughput did fall. With a cheap head (c=0.1) at 2x, keep positions above about 0.2; with an expensive draft (c=0.375) at 1.5x, only those above about 0.56. R and this rule are this report’s derivation. The MiniMax check cannot fail, because R comes from the measured speedup: the rule is an identity on that example. The 0.2 and 0.56 thresholds are untested and assume flat verification cost, so the throughput A/B decides. The rule fits autoregressive drafters best, since block drafters spend little more as k grows. Read survival from _num_accepted_tokens_per_pos divided by _num_drafts [19]. DFlash at k=15 on Qwen3.5-122B fell to 0.94 to 0.95x with about 1% acceptance at the last slot, against 1.66x at k=7 on HumanEval (AMD sweep) [12].

A Qwen3-8B EAGLE-3 Thinking head gave 0.44x at k=1 on MATH500 and never passed 0.88x there (AMD sweep) [12]. The source does not identify the cause. The MLSys study measured EAGLE-3 at 1.64 to 1.80x on Qwen3-8B-Thinking (v0.10.1.1, H100, GPQA and AIME, medium batch) [6], so the conflict is unresolved. Head cost alone cannot explain it: by this report’s arithmetic, 0.44x at k=1 needs c of at least 1.27, while EAGLE-family drafting took 12 to 20% of step time in the MLSys study [6]. If k=1 runs far below 1x, check the runner and async logs before blaming the drafter.

5.6 Measure so the number means something

Lab numbers are not forecasts. DFlash’s 5.1x in SGLang (Qwen3-8B Math500, C=1, single B200) compares with 1.08 to 1.27x on AMD’s vLLM sweep [42, 12], though GPU, backend, checkpoint and load all differ. One EAGLE-3 head on Llama-3.1-8B gave 1.84x on code (mean acceptance length 2.54) and 0.99x on chat (1.19) on vLLM 0.19.1, one A30, T=0, one concurrent request [4]. Temperature matters less than domain: EAGLE-3 accepted length falls about 4 to 21% from T=0 to T=1 at the method level, not in vLLM [37], while Qwen3-8B Eagle3 at T=1.0 ranges from 5.30 on GSM8K to 2.54 on Alpaca in DSpark’s method-level table [39].

Compare output_throughput and TPOT against a baseline with identical prompts, order and temperature, on equal nodes [3]. Prefer TPOT to inter-token latency, because one streamed chunk can hold several tokens [24]. Keep the server’s --enable-per-request-metrics off in timed runs, since it adds server CPU overhead [24]. --per-request-spec-decode-metrics is experimental [21], so do the same as a precaution. Use four arms: no speculation, best fixed k, k one step shorter, and adaptive or a schedule where supported. Judge time to first token separately: on vLLM Neuron it rose from 51.07 to 63.65 ms while TPOT fell from 10.52 to 6.41 ms (Trn2, Llama-3.1-8B, k=3, concurrency 2, version unstated) [43].

5.7 Memory and graphs

Reserve headroom. AMD ran draft-weight methods at --gpu-memory-utilization 0.8 to 0.85 [12]. On computed v0.10.1.1 figures, a 0.6B draft on Qwen3-8B raises KV cache from 144 to 256 KiB per token [6]. On out-of-memory errors, shorten the max model length, lower concurrency, adjust utilization or pick a lighter method [11].

Keep verification batches inside captured CUDA graphs (pre-recorded execution paths for given batch sizes). Set the limit with --compilation-config '{"max_cudagraph_capture_size":N}'. The DSpark authors set max_cudagraph_capture_size to (k+1) times --max-num-seqs. That ran out of memory at default utilization, so they used 0.8 (DeepSeek-V4-Pro-0813, TP=8, 8x B300, main 73b8394) [15]. Sources conflict: that formula gives 2,048 for k=7 and 256 sequences, the blog’s run used 4,096, and the PR 1,024 [15, 3]. For long contexts with adaptive verification, raise VLLM_ADAPTIVE_VERIFICATION_PROFILE_CONTEXT_LEN from its 8192 default [7]. Above T=0, A/B draft_sample_method: neither mode is universally faster per LiLiCorr’s docs [30], and DSpark’s runs used probabilistic [3, 15].

6. Limitations and Compatibility

Compatibility is decided by explicit allowlists in the code, so anything unlisted falls back or fails at startup. The matrix was read from v0.32.0 code and not run, so confirm it on your platform [20, 8, 7].

Method Runner Async Dynamic k Adaptive verification
eagle, eagle3 V2 Yes Tested Online estimator, no benchmark
mtp V2 Yes Not listed as tested Online estimator, no benchmark
dflash V2 Yes Tested Online estimator, no benchmark
dspark V2 only Yes Not listed as tested Benchmarked
draft_model V2; V1 with parallel_drafting or heterogeneous vocabulary Yes Not listed as tested Online estimator, no benchmark
ngram_gpu V2 Yes Not listed as tested Not listed
ngram V2 Off; error if forced Not listed as tested Not listed
suffix V1 Off; error if forced Not listed as tested Not listed
medusa, mlp_speculator, custom_class V1 Off Not listed as tested Not listed

Adaptive verification rejects --enforce-eager and output logprobs, and does not support LoRA adapters or pipeline parallelism (splitting model layers across nodes) [7, 15]. Sources disagree on unsupported backends: the PR describes a piecewise fallback, the later blog says rejection at startup. A startup failure on FA2 GPUs (#62094) was still open in October 2026 [3, 15]. Test startup on your exact GPU. LiLiCorr with adaptive verification is not validated end to end [30].

Draft pipeline parallelism is fixed at 1, while target pipeline parallelism works with static speculation on V2. The docs’ incompatibility note covers only vllm<=0.15.0 [20, 1]. Structured output with speculation and async scheduling landed in PR #29821, merged 2026-01-06, so older warnings are out of date. However, nobody has benchmarked the scheduler CPU its grammar checks add [44]. min_p and logit_bias were ignored with a warning on vLLM 0.19.1 [4]. Per-request metrics report only when n == 1 [21]. FLy, main only, is lossy: its docs report 1.04 to 1.31x over standard speculation (V2, MI355X and B300, batch 1 to 64, version not stated) with accuracy retention down to 96.3%. Avoid it where output fidelity matters [26].

The evidence has gaps: no same-build comparison of methods, no open-loop EAGLE-3 curve on a current release, and no V1-against-V2 comparison for one configuration. Most figures come from main or development builds, not v0.32.0.

Turning speculation off at high load will likely look dated within a year for checkpoints with good confidence signals. It will likely stay correct for costly drafters on small targets and memory-limited deployments. An open-loop sweep on a current release with a clean no-speculation arm and a non-DSpark drafter would settle it. Until then, rerun your sweep on every upgrade.
