Building the SQL Server Proxy as an Envoy Dynamic Module

Research report · 6 cited sources · reviewed 2026-11-14

Summary. An Envoy dynamic module can carry a SQL Server (TDS) proxy in which each client session keeps its own server connection. Place the module as a network filter in front of Envoy’s built-in tcp_proxy. The module reads and rewrites TDS traffic, picks the backend cluster, and can delay the server connection. tcp_proxy opens and owns the server connection. Every callback this needs exists in Envoy v1.40.2, the current release.

Connection sharing is different. The module interface has no way to borrow a connection from Envoy’s connection pool and return it later, and that borrow-and-return is the core of sharing. A module can share connections only by opening and managing its own server sockets. That means rebuilding the pool, health checks and upstream TLS that a compiled C++ filter gets from Envoy. So build the no-sharing proxy as a module, and build sharing, if measurement justifies it, as the C++ filter from the earlier report. The TDS parsing code carries over unchanged.

This report rests on reading Envoy source: abi.h on main (commit 3500543, 2026-11-13), abi.h at v1.40.2, and tcp_proxy’s config and source. No module was built or run. All code below is an unbuilt illustration.

1. What a Dynamic Module Can Do

A dynamic module is a shared library that Envoy loads at runtime. It implements the C interface in abi.h, and official SDKs exist for C++, Go and Rust (docs). No custom Envoy build is needed. The project’s stated goal is that modules can do “any functionality that can be implemented by the built-in C++ extensions”, and it adds: “This is work in progress and many features are not yet available.”

1.1 The network filter callbacks that matter here

The set_filter_state_typed documentation names this use directly: it exists “for interoperability with built-in Envoy filters that read filter state as typed objects (e.g., tcp_proxy reads PerConnectionCluster via the key "envoy.tcp_proxy.cluster")”.

1.2 What is missing

There is no callback that opens, borrows or returns a raw TCP connection from an Envoy cluster. A search of the main header for tcp_conn, conn_pool, connection_pool, raw_socket and tcp_callout finds nothing. The only module-initiated upstream call is an HTTP callout. Sections 3 and 4 follow from this gap.

1.3 Version stability

The interface follows a no-breaking-change policy: “Released ABI is frozen. Once a function, type or struct in the ABI has shipped in an Envoy release, it never changes.” Superseded entries stay “for at least four Envoy release cycles, roughly one year”. The flip side is that “it must be ABI-compatible with the Envoy binary that loads it.” Build against a pinned Envoy release with the matching SDK, and treat main-only callbacks as unavailable until they ship.

2. Case A: A Proxy Without Sharing

2.1 Layout

client ──TLS──▶ [listener: TLS termination]
                  └─ module network filter  (parse TDS, decide, rewrite, count)
                  └─ tcp_proxy               (owns the one server connection)
                                   ──TLS──▶ SQL Server

tcp_proxy provides the standard parts: connect timeouts, cluster load balancing, health checks, outlier detection, circuit breakers, upstream TLS through the cluster’s transport socket, and access logs. The module adds TDS awareness.

Illustrative listener configuration, with field names checked against the main protos:

filter_chains:
- transport_socket: { ... downstream TLS, for TDS 8.0 clients ... }
  filters:
  - name: tds
    typed_config:
      "@type": type.googleapis.com/envoy.extensions.filters.network.dynamic_modules.v3.DynamicModuleNetworkFilter
      dynamic_module_config: { name: tds_proxy }      # loads libtds_proxy.so
      filter_name: tds
      filter_config:
        "@type": type.googleapis.com/google.protobuf.StringValue
        value: '{"route_by":"database"}'
  - name: tcp
    typed_config:
      "@type": type.googleapis.com/envoy.extensions.filters.network.tcp_proxy.v3.TcpProxy
      stat_prefix: mssql
      cluster: mssql_default
      upstream_connect_mode: ON_DOWNSTREAM_DATA       # see 2.4
      max_early_data_bytes: 65536

# bootstrap: needed so the module's cluster choice is read at connect time (2.4)
layered_runtime:
  layers:
  - name: static
    static_layer:
      envoy.reloadable_features.tcp_proxy_delay_route_selection: true

2.2 What the module does with the bytes

TDS framing is cheap. Each packet starts with an 8-byte header: Type, Status, big-endian Length, SPID, PacketID and Window. A message ends at the packet whose Status has the EOM bit set. The module keeps a small per-connection reassembly buffer, because a read can end mid-header or mid-packet. Dispatch on Type: PRELOGIN 0x12, LOGIN7 0x10, SQLBatch 0x01, RPC 0x03, Attention 0x06, Transaction Manager 0x0E, and server responses 0x04.

What this enables, in rising order of cost:

  1. Observe: count logins by user and database, sessions that never send a query, batch and RPC rates, and Attention messages. This needs only framing and a LOGIN7 parse.
  2. Route: after parsing LOGIN7, set envoy.tcp_proxy.cluster, for example by database or application name.
  3. Allow or block: inspect SQLBatch text or RPC procedure names. To refuse a request, drop it and write a TDS ERROR and DONE token back to the client. That requires generating server-style tokens correctly.
  4. Rewrite: change request bytes, fixing up packet Length and splitting across packets. Any rewrite of server responses needs a token walker, which the earlier report calls the expensive part.

Each step needs only the callbacks in section 1.1.

2.3 Encryption decides what the module can see

This limit applies to C++ as well:

  • TDS 8.0 (strict): TLS comes first on the connection, so Envoy’s normal TLS listener terminates it. The module sees plain TDS, and the cluster’s TLS socket re-encrypts toward the server.
  • TDS 7.x with full encryption: the TLS handshake travels “encapsulated in TDS packet(s) of type PRELOGIN (0x12)” (MS-TDS). Envoy’s stock TLS socket can’t unwrap that, so without extra work the module sees PRELOGIN and then ciphertext.
  • TDS 7.x with only the login encrypted: traffic after login is plain, but the module can’t read the login, so it can’t route by user or database.

There is a new option here. A module can now implement a transport socket (on_transport_socket_do_read and do_write, with an is_upstream flag). A module transport socket using its own TLS library could, in principle, wrap and unwrap the PRELOGIN-framed handshake. The earlier report identified that custom socket as the largest encryption unknown, and it no longer requires C++. It remains inference: nobody has built one, and it is a project of its own. Ship TDS 8.0 first. JDBC’s default is encrypt=true, not strict, so this means reconfiguring clients.

2.4 Choosing the backend after reading the login

By default tcp_proxy connects as soon as the client connects, before any TDS arrives. With upstream_connect_mode: ON_DOWNSTREAM_DATA and max_early_data_bytes set, it connects when the first client data reaches it.

Delaying the connection is not enough on its own. tcp_proxy also has to choose its route late, and by default it doesn’t: it picks the route when the client connects. It picks the route just before connecting only when the runtime flag envoy.reloadable_features.tcp_proxy_delay_route_selection is on. That flag is a FALSE_RUNTIME_GUARD, off by default in both v1.40.2 and main. Turn it on in the bootstrap’s runtime layer. With it on, a cluster the module puts in filter state before passing data on is the one tcp_proxy uses. Without it, the filter-state cluster is read before the module has seen any TDS. Runtime guards are usually removed once a behaviour becomes the default, so check the flag at your pinned release.

The tcp_proxy documentation warns that this mode “is not suitable for server-first protocols (e.g., SMTP, MySQL, POP3)”. TDS is client-first: the client sends PRELOGIN before the server says anything. So the mode fits, but only for PRELOGIN. To route on the user or database, the module needs LOGIN7, and the client won’t send LOGIN7 until it has a PRELOGIN response. Two choices follow:

  • Route by listener or SNI: connect on PRELOGIN. This is simple and needs no faking.
  • Route by login contents: answer PRELOGIN locally, hold the LOGIN7, set the cluster, then release both. This is the first half of section 2.5. The module’s PRELOGIN response must agree with what the real server will accept, especially the encryption option.

The connect modes, max_early_data_bytes and the runtime flag all exist in v1.40.2.

2.5 Case A2: Connecting only when the first query arrives

Delaying the connection until the first SQLBatch or RPC means the module must complete the whole login with the client itself. FreeTDS’s tdspool used the same faked-login technique.

client                     module                       tcp_proxy / server
  PRELOGIN ───────────────▶ hold bytes
           ◀─────────────── module's PRELOGIN response
  LOGIN7   ───────────────▶ hold bytes, parse user/db, set cluster
           ◀─────────────── module's LOGINACK + ENVCHANGEs + DONE
  SQLBatch ───────────────▶ inject PRELOGIN, LOGIN7, SQLBatch ──▶ connect
                            remove server's PRELOGIN response ◀──
                            check and remove login response   ◀──
           ◀─────────────── query results                     ◀──

Illustrative read-side logic (pseudocode, unbuilt):

on_network_filter_read(len):
    frame bytes from read buffer into TDS messages; drain them
    for msg in complete messages:
        match state, msg.type:
          (NEW, PRELOGIN):  held += msg; network_filter_write(fake_prelogin_reply)
          (PRE, LOGIN7):    held += msg; parse; set_filter_state_typed("envoy.tcp_proxy.cluster", c)
                            network_filter_write(fake_login_reply(captured template)); state = FAKED
          (FAKED, ATTENTION): network_filter_write(attention_ack)
          (FAKED, BATCH|RPC|TXN_MGR):
                            inject_read_data(held + msg); state = CONNECTING
          (FAKED, other):   inject_read_data(held + msg); state = CONNECTING   # don't guess
          (CONNECTED, _):   pass through
    return StopIteration unless CONNECTED

on_network_filter_write(len):          # server → client
    if CONNECTING: consume the PRELOGIN reply, then the login reply up to its DONE;
                   on login error or any ENVCHANGE that differs from the faked one:
                       send TDS error to client, close
                   else state = CONNECTED; let the remaining bytes through

The module never needs the password: it replays the client’s LOGIN7 bytes as received.

Limits:

  • Only SQL Server password logins. Windows authentication (Kerberos, NTLM) runs several round trips with the server during login, so it can’t be faked. The earlier report could not verify that Entra ID logins can be faked either. Send both through a listener that connects immediately.
  • TDS 8.0 or no encryption. With 7.x, the PRELOGIN-framed TLS handshake has to happen with the real server.
  • Login errors arrive late. A wrong password or a missing database surfaces on the first query, not at login. Test how your drivers and connection pools handle that.
  • The faked response must match the server’s. Capture database, collation, language and packet size from your real server for each login key. Close the session on any mismatch.
  • Small benefit if pools validate connections. This only saves connections that never send a query. Measure that count with the step-1 counters before building A2.

2.6 Effort

The Envoy integration is a small part of the work: one filter, a state enum, and two callbacks doing most of it. Almost all the effort is TDS: framing, the LOGIN7 parse, generating server tokens for refusals or faked logins, and a test matrix across drivers (SqlClient, mssql-jdbc, ODBC 18, go-mssqldb, tedious). The Rust crates mssql-tds and tds-driver may provide parsers. Check their licences and coverage.

3. Case B: Sharing Connections

3.1 Why tcp_proxy plus a module can’t share

Sharing means a session gives its server connection back when it is clean and later borrows another one. tcp_proxy holds exactly one upstream per client connection for the session’s whole life, and the module can’t take that connection or pass it to another session. The module interface has no pool-borrowing callback (section 1.2). So sharing inside Envoy’s pool is not possible from a module today.

3.2 B2: the module owns its sockets

main now documents this shape explicitly: “A terminal network filter that reaches its upstream itself, rather than through an Envoy upstream connection, reports that upstream and the outcome of the connection with these callbacks.” Set terminal_filter: true, drop tcp_proxy, and the module becomes the proxy. Its architecture:

  • Pool: owned by the module, keyed per login as the earlier report requires (no re-authentication in TDS). It can be per Envoy worker thread or process-wide. The process-wide option needs its own I/O thread.
  • I/O: sockets run on module-owned threads (for example a Rust async runtime). Results return to the session’s worker through network_filter_scheduler_commit. That adds a thread hop per message, and the module must stop those threads before worker shutdown.
  • Hosts: set_upstream_host needs an address the module already knows, and get_cluster_host_count returns only counts. The module therefore needs its own host discovery, such as DNS or config.
  • TLS to the server: the module’s own TLS library. start_upstream_secure_transport applies only to Envoy’s upstream connection, which doesn’t exist here.
  • Health, timeouts, circuit breaking, outlier detection: reimplemented.
  • Observability: module metrics, plus the main-only reporting callbacks for access logs. These are not in v1.40.2.

Everything the earlier report specified still applies on top: the release rule, the session-state walker, the scrub batch, pinning and Attention handling. The result is a standalone TDS pooler running inside Envoy. It keeps Envoy’s listener, downstream TLS and config delivery, and gives up the upstream half, which is most of the reason to use Envoy for this.

3.3 B3: the C++ filter

The terminal C++ filter on Tcp::ConnectionPool holds a lease while a session is dirty and releases it when clean, and Envoy supplies the pool, health checks, upstream TLS and stats. The cost is a custom Envoy build and tracking Envoy’s internal C++ headers. The earlier report covers the design.

3.4 Decision

A (module proxy) B2 (module, own sockets) B3 (C++ filter)
Custom Envoy build No No Yes
Envoy upstream features All None All
Server-connection savings None (A2: idle sessions only) Yes Yes
Works on v1.40.2 Yes Partly (no upstream reporting) Yes
Main risk TDS correctness Rebuilding an upstream stack Header churn, C++

Choose B2 only if a custom Envoy binary is ruled out and sharing is required. Even then, compare it with a standalone pooler outside Envoy, which would be the same code without the threading constraints.

4. Plan

  1. Module proxy, observe only (A, step 1). TDS 8.0 listener, framing and LOGIN7 parse, counters per user and database: sessions, sessions with zero queries, session duration, and transaction and temp-table use. No data-path changes. This is the census the earlier report asks for before any sharing work.
  2. Routing and policy (A, steps 2–3), if you need them.
  3. Delayed connect (A2), only if step 1 shows many sessions that never query.
  4. Decide on sharing from step 1’s numbers, using the earlier report’s ratios and gates. If you proceed, move the TDS crate into the C++ filter (B3) or rebuild it there. Under a C ABI, a Rust parser can link into the C++ filter (inference: check build integration).
  5. TDS 7.x encryption, as a separate prototype of a module transport socket, only if clients cannot move to TDS 8.0.

5. What Would Change This

  • A pool-borrowing callback in the module interface. Watch abi.h for network-filter callbacks that acquire and release upstream TCP connections. With one, B moves to a module and the C++ requirement goes away.
  • Upstream reporting callbacks in a release. They make B2 observable like tcp_proxy but don’t remove its other costs.
  • A working PRELOGIN-framed TLS transport socket. That would bring TDS 7.x clients into scope for A without client changes.
  • Step-1 numbers. Few idle or clean sessions per login key would end the sharing question in favour of case A alone.
