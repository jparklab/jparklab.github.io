Executive summary. Write one terminal C++ network filter, compiled into Envoy, that terminates TDS (Tabular Data Stream, the SQL Server wire protocol), logs in to SQL Server itself, and holds exclusive Tcp::ConnectionPool leases in per-principal pools. Pin by default, meaning a session keeps its backend until release is provably safe, and close on doubt. Make the release moment a per-listener setting: one_to_one, sticky (at client disconnect), or transaction (at a clean transaction boundary). Of the mechanisms whose APIs were read, only compiled C++ can hold a lease while a session is dirty and release it when clean [1] [2] [3] [4]. This is serial reuse. Concurrent multiplexing through MARS (Multiple Active Result Sets) should not host independent clients.

Sticky ships first because the transaction setting contains it: it proves login offload, a cap, and the parser against real drivers, with no connection savings for idle pools. Without the request scanner it must close each backend at disconnect. Going further is decided per login key and server build, because no measured TDS sharing ratio or official list of what a reset clears was found. The only SQL Server proxy found publishing its rules contradicts itself on whether transactions pin [5]. The transaction setting must be earned through a census, a reset test matrix, and shadow measurement.

1. What Sharing a Connection Can Mean on TDS

A SQL Server client logs in on a TCP connection and sends requests for as long as it stays open. The server keeps state against that session: transactions, SET options, temporary tables, prepared handles. MS-TDS (the protocol specification) says a session “persists until the transport-level connection is terminated” and has no concept of a proxy [9]. Sharing is therefore a policy imposed from outside, and policies differ in when a backend may move to another client.

1.1 The release boundaries

Boundary Backend moves Risk or cost Example
Per request After every response Severe: BEGIN TRAN and the next batch split across connections Generic Proxy (Envoy’s request/response framework) unbound [1]
Per transaction After a response leaving no transaction or pin Needs detection, reset, scrub; recovers idle clients’ connections PgBouncer, ProxySQL [10] [11]; unproven on SQL Server
Per logical session At the driver’s next reset bit Driver reset semantics None published; proposed here
Per connection (sticky) At client disconnect One reset point; saves only across disconnects, plus a queueing cap FreeTDS tdspool [8]
Concurrent on one socket Never; sessions interleave Shared identity and environment SMP (Session Multiplex Protocol), one client

1.2 Concurrent multiplexing is wire-capable and wrong

MARS runs on SMP, and SMP really is a multiplexer: its header carries a 2-byte session ID, per-session sequence numbers, and a receiver-driven window [12] [13]. The server models each session as a row with a parent_connection_id [14]. Nothing in the header forbids session IDs from different clients. The trouble sits above it:

  • Identity. Login is per connection, with no per-session LOGIN7 (the login message), so every session inherits one principal [9].
  • Environment. Each batch “receives a copy of the default environment”, and finished batches copy settings back [15].
  • Throughput. MARS “is defined in terms of interleaving, not in terms of parallel execution” [16].
  • Transactions. One left open at batch exit is rolled back [17].

Those facts jointly imply that fan-in would hand one client another’s login and let settings flow between tenants, without parallelism. Whether a server accepts foreign session IDs is untested, and the argument does not need refusal: a small serial pool beats the resulting queue. Redis-style pipelining fails likewise. A server should queue a request arriving during execution [9], but it would run in its predecessor’s session.

On one shared service login the identity objection falls, and fan-in stays plausible and untested. It is still rejected (inference): settings, security context, and top-level temp tables share one default environment [15], and the proxy would run SMP flow control for interleaving without parallelism.

1.3 Stacked partitioning decides the project

No source states this; it is inference from sourced parts. Pools are per worker, and a connection stays on its worker for life [18] [19]. Identity is fixed on the connection, so pools are keyed by principal, as in Microsoft’s driver [20]. Reset returns to the login’s defaults, so database and option flags join the key [9]. Reusable capacity therefore exists only inside one (worker, principal, database, login options) cell, among sessions unpinned and between transactions at the same moment.

With K login keys, W workers, L peak concurrent leases, P pinned sessions, and no measured inputs:

backends ≈ L + P + idle cache, with an idle floor approaching K × W

Three inferences follow:

  1. Sharing requires sessions far above K × W. Per-user logins push K toward the session count, and then no implementation helps.
  2. Sticky only helps churners. When a driver closes a pooled connection, “SQL Server receives nothing” [21]. A client pool holding its socket never disconnects from a sticky proxy’s viewpoint, so its backend is never reclaimed. This report assumes that idle pool is a common motive; no source establishes it.
  3. Long pins decay. Where a pin lasts until disconnect, as on RDS Proxy and Vitess [5] [22], the pinned fraction under long-lived pools only grows. Watch it against connection age.

1.4 When no extension is the answer

A client pool already shares sessions. ADO.NET defaults to 100 connections, queues excess requests for 15 seconds, and evicts idle connections after about 4 to 8 minutes [6]. If replicas times pool size exceeds the server’s limit and replicas are few, lowering the maximum gives a hard ceiling with no new failure domain (inference). A proxy earns its place when processes are too many or too short-lived, or one ceiling must span heterogeneous clients. tdspool’s motivating example is 35 Apache/PHP children sharing a 10-connection license [23].

2. Choosing the Envoy Extension Mechanism

Envoy accepts behaviour through compiled filters, loadable modules, sandboxes, and a request/response framework. It has no TDS filter: a maintainer said “This will require a new protocol aware filter for MSSQL”, and the issue closed as not planned [24]. The deciding test is whether a mechanism can:

  • Hold an upstream lease across requests.
  • Release it on a state-driven condition.
  • Run a login on a pooled connection.
Mechanism Lease a shared upstream? Maturity or cost Verdict
C++ terminal network filter Yes, any policy [25] Custom build [26]; contrib packaging later [27] Use this
C++ passive filter ahead of tcp_proxy No, one-to-one Postgres proxy’s shape [28] Pin census, if climbing
Generic Proxy codec and router Per request, or bound with no reuse [1] Router API work in progress [2] Stateless spike
Generic Proxy router clone Could hold a lease (inference) [29] Router API work in progress [2] Fits poorly
Dynamic module (Rust, Go, C++) No: writes go downstream; no lease callback [3] “Released ABI is frozen.” [30] Pin census, if stopping

Wasm network filter Host API not read “The Wasm filter is experimental” [33] Not shown capable
Lua Not established No source documents a network filter Not a candidate

Parsing is not the constraint: C++, Generic Proxy, modules, and Go can read TDS bytes, Wasm plausibly can, and only Lua is unestablished. For Wasm, only Envoy’s configuration page was read, not the proxy-wasm host API, so that row is unproven.

2.1 Generic Proxy: the strongest rival

Generic Proxy offers codec-only development with routing and stats included [34]. writeToConnection lets a codec answer locally, fitting a forged login, and the client codec lives in connection filter state, so it could remember reset debt across leases [35] [36].

It fails on the decisive requirement. The router has one listener-wide boolean, bind_upstream_connection [2]. Unbound, each request gets its own OwnedGenericUpstream [1]. Bound, “Shared upstream manager never release the connection back to the pool” [1]. Hold while dirty and release when clean has no setting. drainClose() on a dirty response protects isolation but silently loses the client’s transaction (inference) [37].

Three smaller problems compound this:

  • The seams are not configuration: RouterFilter takes its upstream factory only as a constructor argument, config.cc registers only RouterFactory, and ProxyFactory replaces the read filter, so a custom factory means a registered router clone or your own read filter [29] [38] [39]. A clone could hold a lease (inference), but PRELOGIN, TLS, and LOGIN7 fit a request router poorly: a judgment on fit, not an impossibility.
  • Attention (the TDS cancel message) maps poorly: inferred from code, not run, a later Attention arrives as a new request and, unbound, reaches a different connection [40].
  • couldRetry can reissue non-idempotent T-SQL after a reset [29].

This judgment rests on files read, not a repository-wide search, so a factory registry elsewhere would reopen it. A spike can show framing and driver behaviour for read-only sp_executesql traffic. It proves nothing about transactions.

2.2 Dynamic modules and the safer-language argument

Modules offer three SDKs, no custom binary [30], and StartTLS callbacks [3]. Tracking Envoy’s internal C++ headers for years is a legitimate objection (inference). The header settles it anyway. Writes go only downstream, upstream calls report on tcp_proxy’s connection, and the one raw-upstream path is an HTTP-scoped bridge [3]. A header search for tcp_conn_pool, upstream_tcp, and cluster_manager at the fetched snapshot found nothing; re-check at your commit. A module owning its own sockets loses cluster membership, TLS contexts, health checks, and stats.

2.3 The first extension is a decoder

A passive filter ahead of tcp_proxy changes nothing in the data path and sees everything, provided Envoy terminates TLS [28]. Run the release rule there in shadow, computing the decision without acting on it, and record how many leases each cell would hold. Write it in C++ if you expect to climb, or as a dynamic module if the measurement might end the project.

3. Writing the Terminal TDS Network Filter

A network filter is an object Envoy creates per TCP connection and feeds with bytes. A terminal filter is last in the chain and decides where those bytes go. Here it answers the handshake locally, acquires a backend only when a request needs one, and returns it when the session holds no server state. The whole filter is a per-session state machine around one lease.

3.1 Templates, build, and registration

“As of this writing there is no high level extension developer documentation.” [41] Copy tcp_proxy for plumbing: a Network::ReadFilter that is also a LoadBalancerContextBase, with watermark handling [42]. Copy Redis ClientImpl for protocol clients, whose init machine will “hold user requests so they cannot race ahead of the in-flight init command” [43]. Postgres and MySQL are passive, so they are only decoder and StartTLS templates [44].

Start from envoy-filter-example: Envoy as a Bazel submodule, with static-initialization registration, built by git submodule update --init then bazel build //:envoy [26]. Derive factories from Extensions::NetworkFilters::Common::FactoryBase<Proto>, overriding createFilterFactoryFromProtoTyped to return a Network::FilterFactoryCb that calls filter_manager.addReadFilter(...) [45]. Use REGISTER_FACTORY [38]. The base interface is reported as NamedNetworkFilterConfigFactory, and the factory must declare itself terminal. Confirm both at your pinned commit, since no source read verified them. typed_config needs your own proto message carrying cluster, release mode, and verified-builds path; BUILD rules were not read.

Build in this order:

  1. Framer, walker, and scanner in a passive filter (Stage 1).
  2. PRELOGIN and LOGIN7 codecs against a scripted backend.
  3. Envoy glue and lease in one_to_one.
  4. Framing-only sticky (Stage 2).
  5. Scrub and recycling with the scanner inline (Stage 3).
  6. mayRelease() for transaction (Stage 4).

Keeping parsers and codecs free of Envoy types makes them fuzzable (inference).

3.2 The object model

Connections stay on one worker, filters are fresh per connection, and nothing may block [19] [46]. FreeTDS’s comment “// FIXME not wait for server !!! asyncronous” is the warning [47]: every wait must be a state plus a dispatcher timer.

Object (proposed) Lifetime Owns
TdsProxyConfig Filter chain Cluster, mode, pin policy, timeouts
TdsSessionFilter Downstream connection State machine, lease, tracked SETs, pin reasons
TdsBackendState : Tcp::ConnectionPool::ConnectionState Upstream connection Pool key, last owner, expiry, dirty flag
TdsWorkerRegistry Worker (thread-local slot) Login templates, admission counts
TdsFramer, TdsRequestScanner, TdsTokenWalker Session Resumable parsers

3.3 The lease contract

Acquire through getThreadLocalCluster(name), tcpConnPool(Upstream::ResourcePriority::Default, this), and newConnection(*this) [31] [48]. The contract shapes every callback:

  1. Exclusive. TCP pool clients have a concurrent stream limit of 1 [49].
  2. Implicit release. “Open ClientConnections are released back to the pool for re-use when their containing ConnectionData is destroyed.” [25] An unintended destructor is a data-exposure bug.
  3. Asynchronous acquire. newConnection may call back synchronously and return nullptr; otherwise cancel its handle if the session dies [25].
  4. Stray-byte safety. With no callback attached, “data from the upstream will cause the connection to be closed”, so late tokens never reach the next owner [25].
  5. State survives leases. ConnectionState dies with the connection; a null connectionStateTyped<T>() means a new connection needing a login [25].

Put one logical server in a cluster, with priorities for failover, because sessions change connections on every release and round-robin replicas would break read-your-writes (inference).

3.4 The session state machine

EOM (end of message) is the packet status bit closing a message. A scrub is the proxy’s own cleanup batch for a new owner. A token walker is the parser stepping through response tokens.

State Leaves on
HANDSHAKE Login response → IDLE; one_to_one → DEDICATED
IDLE (no lease) First request packet → ACQUIRING
ACQUIRING onPoolReady → SCRUBBING or FORWARDING; failure → TDS error, IDLE
SCRUBBING Clean EOM → FORWARDING; error → close, ACQUIRING
FORWARDING Client EOM sent → RESPONDING
RESPONDING EOM and mayRelease() → release, IDLE; dirty → PINNED; Attention → ATTN_DRAIN
ATTN_DRAIN Acknowledged → re-evaluate; timer → POISONED
PINNED Next request → FORWARDING; reasons cleared at EOM → release
DEDICATED Either side closes → close both
POISONED Client leaves → close upstream

POISONED refines close-on-doubt. If the walker loses sync, the filter can stop walking, frame by EOM, forward verbatim, and guarantee the connection never reaches another owner.

3.5 The callback skeleton

// UNBUILT ILLUSTRATION. Never compiled. Tds* names and helpers are invented.
class TdsSessionFilter : public Network::ReadFilter,
                         public Upstream::LoadBalancerContextBase,
                         public Tcp::ConnectionPool::Callbacks,
                         public Tcp::ConnectionPool::UpstreamCallbacks {
  Network::FilterStatus onData(Buffer::Instance& data, bool) override {
    framer_.append(data);
    while (auto packet = framer_.next()) { onClientPacket(*packet); }
    return Network::FilterStatus::StopIteration;   // terminal
  }

  void onClientPacket(const TdsPacket& packet) {
    if (forwarding()) { lease_->connection().write(packet.bytes(), false); return; }
    holdRequest(packet);
    if (lease_ == nullptr && pending_ == nullptr) { acquireLease(); }
  }

  void acquireLease() {
    auto* cluster = cluster_manager_.getThreadLocalCluster(config_->cluster());
    if (cluster == nullptr) { answerWithTdsError(); return; }
    auto pool = cluster->tcpConnPool(Upstream::ResourcePriority::Default, this);
    if (!pool.has_value()) { answerWithTdsError(); return; }
    pool_data_ = std::move(pool);
    pending_ = pool_data_->newConnection(*this);   // nullptr if it already called back
  }

  void onPoolReady(Tcp::ConnectionPool::ConnectionDataPtr&& conn,
                   Upstream::HostDescriptionConstSharedPtr) override {
    pending_ = nullptr;
    lease_ = std::move(conn);
    lease_->addUpstreamCallbacks(*this);
    auto* backend = lease_->connectionStateTyped<TdsBackendState>();
    if (backend == nullptr) { startBackendLogin(); return; }
    if (backend->poolKey() != session_.key()) { closeLease(); reacquire(); return; }
    if (backend->lastOwner() == session_.id() && !backend->dirty()) {
      forwardHeldRequest();
    } else {
      sendScrubBatch(*backend);
    }
  }

  void onPoolFailure(Tcp::ConnectionPool::PoolFailureReason, absl::string_view,
                     Upstream::HostDescriptionConstSharedPtr) override {
    pending_ = nullptr;
    answerWithTdsError();                          // session survives
  }

  void onUpstreamData(Buffer::Instance& data, bool) override {
    walker_.feed(data);                            // desync marks doubt
    read_callbacks_->connection().write(data, false);
    if (framer_.responseAtEom() && mayRelease()) { releaseLease(); }
  }

  bool mayRelease() const {                        // separates the modes
    if (config_->mode() != TdsMode::Transaction) { return false; }
    return !session_.txnOpen() && !session_.pinned() &&
           !session_.attentionPending() && walker_.inSync();
  }

  void releaseLease() {                            // the only release site
    lease_->connectionStateTyped<TdsBackendState>()->setLastOwner(session_.id());
    lease_.reset();
  }

  void onDownstreamClose() {
    if (pending_ != nullptr) {
      pending_->cancel(Tcp::ConnectionPool::CancelPolicy::Default);
    }
    if (lease_ == nullptr) { return; }
    // recycleAllowedAndIdle() is false unless the scanner runs inline
    if (config_->mode() == TdsMode::Sticky && recycleAllowedAndIdle()) {
      markDirtyForNextOwner();
      releaseLease();
    } else {
      closeLease();                                // doubtful: never recycle
    }
  }
};

initializeReadFilterCallbacks registers a Network::ConnectionCallbacks object, as tcp_proxy does, whose close event runs onDownstreamClose; onNewConnection returns StopIteration [42]. startBackendLogin attaches TdsBackendState with setConnectionState once login succeeds, and closeLease clears the pointer before closing, because closing can re-enter callbacks [25] [36]. Cancel a pending handle in the destructor, and treat it as invalid after any callback [25].

One function releases, so an audit examines one place. onPoolReady re-checks the pool key, so a partitioning bug closes a connection instead of crossing an identity. And mayRelease() alone separates the modes. Sticky and transaction share listener, factory, framing, login, lease, and failure paths. Transaction adds a walker, a scanner, and a different boolean. Sticky has two forms. Framing-only sticky relays on packet framing and must close the backend at client disconnect, because the discard rules (sp_setapprole, EXECUTE AS ... NO REVERT) can fire only with the scanner. Recycling a backend across clients needs the scanner inline, so tdspool’s recycling [47] is a structural template, not a safety precedent.

3.6 Selecting a mode at two points

MARS is declared in PRELOGIN (the first negotiation message), authentication type in LOGIN7, and TDS 8.0 needs TLS before either [9]. A passthrough decided after terminating TLS is not true passthrough, so mode has two selection points:

  • By listener or filter chain, before any TDS. True TCP passthrough for Extended Protection Required and known MARS applications, on a chain without the filter. TDS 7.x clients wrap their ClientHello inside PRELOGIN, so SNI (TLS server-name indication) cannot see them and they need a separate port (inference).
  • By the filter, after LOGIN7. When the server build, read from LOGINACK’s ProgVersion [9], is absent from the verified list, transaction degrades to sticky. This mechanism is this design’s own.

The first-byte rule supports this routing: 0x16 means a TLS ClientHello from a TDS 8.0 client, and anything else must be a PRELOGIN [9]. Mapping listener TLS inspection onto TDS versions is inference needing an integration test.

4. Parsing and Rewriting the TDS Protocol

TDS messages travel in packets with 8-byte headers. The server answers a request with a stream of typed tokens: column metadata, rows, environment changes, completion markers. A proxy asks where a response ends and what it did to the session. The first question is cheap, and the second is the expensive part of this project.

4.1 Framing and state are separate problems

Framing needs no token parser, only the 8-byte packet header: Type, Status, big-endian Length, SPID (server process ID), PacketID, and Window [9]. “The EOM bit MUST be set to 1 in the last packet to signal that the stream ends.” [9] Wireshark reassembles on that bit, and FreeTDS treats needing bytes after EOM as being out of sync [50] [51]. No capture was examined, so verify this on your server. Do not copy go-mssqldb’s treatment of any non-zero status as final [52]. Dispatch on Type: SQLBatch 0x01, RPC 0x03, Tabular Result 0x04, Attention 0x06, BulkLoad 0x07, Transaction Manager 0x0E [53].

An EOM-only proxy still cannot release safely. ENVCHANGE tokens (server reports of environment changes) that open a transaction can follow rows, as in SELECT ...; BEGIN TRAN [9]. ROW tokens have no length prefix, so finding them means walking with the COLMETADATA (column metadata) token [9]. Release therefore requires five things:

  • EOM on the last packet.
  • Closed ENVCHANGE-tracked transaction state.
  • No pin reason.
  • No outstanding Attention.
  • A walker at a token boundary without doubt.

4.2 The handshake

  1. Discriminate on the first byte: TDS 8.0, where TLS precedes all TDS [54], or 7.x, where TLS rides inside PRELOGIN.
  2. Answer PRELOGIN yourself. Require whole-connection encryption and answer MARS off, because a MARS stream is SMP-framed and unparseable as TDS packets [9]. Client tolerance is an inference to test. Return INSTOPT 0 for fronted instance names [9]. Give clients an explicit port, since a fixed-port proxy bypasses SQL Browser’s UDP 1434 [55] (inference). tdspool’s hard-coded reply, marked “TODO proper one” [8], is a template for structure only.
  3. Parse LOGIN7: offset table, user, database, language, option flags, version, and FeatureExt (the optional-feature list). The password is obfuscated: “swap the four high bits with the four low bits and then do a bit-XOR with 0xA5” [9]. TLS is its only protection, so never log it.
  4. Answer login. The first client on a key relays a real backend login; later clients get a forged response.

4.3 What gets rewritten

After login, almost nothing is rewritten.

Field Treatment
Packet header Forwarded; PacketID is ignored, SPID debug-only [9]
PRELOGIN (0x12) Reply proxy-authored; negotiated per leg
LOGIN7 (0x10) Backend copy rebuilt; SESSIONRECOVERY (driver reconnection state) stripped
SQLBatch, RPC (procedure-call message), Transaction Manager Scanned, never edited; headers only in the first packet [56]
Status bit 0x08 Client’s forwarded; proxy sets it only on its scrub [57]
Tabular response Walked; bytes pass through
ENVCHANGE 20, 21 (routing) Never forwarded [58]

Transaction descriptors need no rewriting. One reading of the specification treats the 8-byte descriptor in ALL_HEADERS (the request header block) as the core rewrite, since the server mints it and the client echoes it. Outside a transaction it “MUST be 0”, and under pinning a backend never changes hands between begin and end [9]. Those facts jointly imply the client always echoes zero or its current connection’s value. Only a mid-transaction handoff would need rewriting, which no source reports any proxy attempting.

Packet size is dictated, not keyed. Since TDS 7.3, non-final client packets must equal the negotiated size or the server should disconnect, so re-chunking is unsafe [9]. But the server “MAY send a value different from the packet size requested by the client” [58], and the proxy is the client’s server. Announce the pool’s size in ENVCHANGE type 4, as tdspool does [8]. Driver tolerance is a matrix item (inference).

FeatureExt is contained through the backend login. The list keeps growing, now with JSON and vector support, and each type is something the walker must size [9]. Through RDS Proxy these columns arrive as nvarchar(max) [59]. A proxy originating the login can request only features its walker understands (inference), at the cost that clients lose those types and possibly column encryption.

4.4 The token walker

Build it to resume at any byte, because tokens span packets. Most tokens skip through zero-length, fixed-length, and length-prefixed classes [9]. The hard ones are [9]:

  • COLMETADATA (0x81).
  • ROW (0xD1) and NBCROW (0xD2, null-compressed rows), which need it.
  • PLP values (the chunked encoding for max types) straddling packets.
  • DATACLASSIFICATION, which breaks the variable-length rule [9].
  • ENVCHANGE type 15, which reports length 0x01 with payload following [58].

Do not scan for 0xFD to find DONE (the completion token), because that byte occurs in row data. DONEPROC (0xFE) and DONEINPROC (0xFF) replace DONE inside procedures, and its row count grows from 4 to 8 bytes at TDS 7.2. And do not use DONE_INXACT: the DONE page lists it, but the spec’s footnotes say this 0x4 bit “is not set by SQL Server” [60] [9]. A proxy trusting it releases inside open transactions. State comes only from ENVCHANGE, in stream order:

Type Meaning Action
8 Begin txn_open = true
9, 10, 12, 17 Commit, rollback, defect, ended txn_open = false
11, 15 DTC (distributed transaction) enlist, promote Pin, then discard
1, 2, 7 Database, language, collation Update replay state
18 Reset acknowledged Confirms scrub or client reset
20, 21 Routing Fail the backend login

“For transactions started/committed under auto commit, no stream is generated.” [58] Set fUseDB on the backend login, or database changes pass silently and replay goes stale (inference) [9]. Nested @@trancount changes emit nothing, which is fine because only the outermost span matters. A commit can carry a new begin, which in-order processing handles. Tokens also cover Transaction Manager requests, which begin and commit without SQL text [61].

4.5 The request scanner

The server reports no SET options, temp tables, or session context, so the proxy must read requests. The scanner is a T-SQL tokenizer handling comments, strings, and bracketed names in UCS-2, returning clean, tracked change, or pin.

It works by allowlist, because a denylist fails by leaking and an allowlist by losing an optimization. Unknown verbs pin, and so does a # outside a string. RPCs classify by ProcID: sp_executesql 10 needs no handle, then sp_prepare 11, sp_execute 12, sp_prepexec 13, sp_prepexecrpc 14, sp_unprepare 15, cursors 1 to 9 [9]. Named RPCs check a configured list, and one message can hold several calls. The scanner also reads the text parameters of ProcIDs 10, 11, and 13 with the same tokenizer and limits. Verdicts apply at response EOM, so requests stream unbuffered. Adopt AWS’s rule: “Any statement with a text size greater than 16 KB causes the proxy to pin the session.” [5] It is the right fail-closed shape for a parse window, paralleled by ScaleArc’s default of parsing 3 RPC packets [62].

5. Session State, Reset, and Pinning

A session accumulates state the next user of its connection would inherit. Drivers handle this with RESETCONNECTION, a status bit (0x08) on a request’s first packet telling the server to clean up first. They set it lazily, on the next request after reusing a pooled connection. A proxy uses the same primitive across clients, which raises the stakes on what it clears.

5.1 What reset does and what is unknown

The bit returns the environment to defaults, “effectively simulating a logout and a subsequent login”, and ENVCHANGE 18 acknowledges it [57] [58]. RESETCONNECTIONSKIPTRAN (0x10) preserves the transaction and must not be combined with it. No official list of what reset clears was found:

State Evidence Status
Isolation, on-premises “Distributed transactions and isolation levels are not reset.” [9]; driver team: “does not reset the isolation level” [63]; a repro [64]; a 2014 change reportedly reversed [65] Not reset

Two oblique hints exist for SESSION_CONTEXT, neither a guarantee. The row-level security page says @read_only prevents change “until the connection is closed (returned to the connection pool)” [70]. And known issues warn of “AV exceptions or wrong results” in parallel plans when the session is reset for reuse, on SQL Server 2019 cumulative update 14 and later, with trace flag 11042 as mitigation [71]. A multiplexer raises the reset rate far above a client pool’s (inference), so a defect a pool rarely hits could be hit routinely.

The optimistic argument says an always-on reset turns every detector miss into a lost optimization. Every pooling client depends on this primitive, which is real evidence it mostly works. But those clients stay within one process and connection string, while a multi-client proxy turns the same leak into a boundary between clients. Keep the reset on every handoff, because a rejected reset costs a reconnect while a leak crosses an application or row-level security boundary within one login. Count it as a backstop only for items tested on that exact build. An unverified backstop on a security boundary is not a backstop.

Cost multiplies too. A proxy resets per owner change rather than per checkout, each emitting a pooled Audit Logout and one that “initiates the process of redoing the login” [21]. A SqlClient maintainer warns of token revalidation: “The revalidation is not clearly defined yet but will likely become more strict in future.” [72] Nobody has measured this, so it is a gate.

5.2 The proxy-owned scrub batch

Setting the bit on the client’s first packet saves a round trip but delivers tokens the client never asked for, forcing the proxy to strip a stream it otherwise forwards verbatim. Instead, the proxy authors a batch and consumes its whole response before the client’s request touches the connection:

Status   0x09  = EOM | RESETCONNECTION
ALL_HEADERS    = Transaction Descriptor, descriptor 0, outstanding count 1
Text (UCS-2)   = SET TRANSACTION ISOLATION LEVEL READ COMMITTED;
                 <USE and SET statements replaying tracked state>

FreeTDS arrived at nearly this. pool_reset_member sends WHILE @@TRANCOUNT > 0 ROLLBACK SET TRANSACTION ISOLATION LEVEL READ COMMITTED with status 0x9, freeing the member on failure, though it blocks [47]. Microsoft’s mssql-python team now also sets isolation on reuse [63]. Recycling sticky keeps the rollback line, since a filter without a walker cannot know whether a transaction is open at disconnect (inference). Lazy scrubbing can leave locks and an open transaction on an idle backend, where Odyssey can “Execute ROLLBACK when returning connections with open transactions” [73]. A filter that cannot prove the transaction closed must close at disconnect or finish an asynchronous rollback first.

The batch pays off four ways:

  1. No response rewriting. The client’s stream stays byte-identical.
  2. A safe retry point (inference). No client SQL has run, so on revalidation, socket, or trigger failure the proxy retries invisibly. With the bit on the client’s request, a failure is ambiguous.
  3. A liveness probe for silently dead Azure SQL connections [74].
  4. An expected token. Absent ENVCHANGE 18 counts as doubt.

The cost is one round trip per owner change, skipped when a session regains its own last backend. If the client sets its own reset bit, forward it, discard tracked state, and let the client receive its ack. Driver tolerance is a test item.

State Seen through Treatment

Sharing cost concentrates in untracked SETs, temp tables, and prepared handles. The tracked list is AWS’s documented split: USE and 14 SETs reuse only among sessions with identical values, while 18 further entries pin [5]. This design replays instead of matching. Application roles are absolute because the client holds the sp_unsetapprole cookie [75]. Leaks are real. A tedious user found session values visible to the next borrower, framed as disclosing salaries or medical records because the value was a row-level security key [69].

5.4 Stored procedures: the likeliest deciding lever

A scanner cannot see inside procedures. Pinning every EXEC leaves little to share, and ignoring them is what RDS Proxy admits for MySQL and Postgres; its SQL Server section is silent [5]. A chain of sourced facts shrinks the problem:

  • A SET in a procedure or dynamic SQL string is restored on return [76].
  • EXECUTE AS in a module ends at exit [77].
  • sp_setapprole “can only be executed as direct Transact-SQL statements” [78].

Those premises narrow what a procedure can leave behind, but no source enumerates it. The candidates identified here are session context, CONTEXT_INFO, global cursors, session-owned locks, and global temp tables. So EXEC of an unlisted procedure pins by default, and procedures: reuse opens once those rows pass on your exact build. This is the one place reset carries real weight, all of it inference until a test earns it.

5.5 Silent wrong answers

Transaction release can also yield wrong results with no error. RDS Proxy warns that @@IDENTITY, @@ROWCOUNT, and SCOPE_IDENTITY “aren’t always accurate” [59], and tdspool’s README concedes that “querys that contain stateful information, such as the need to query @@identity after inserting, will not work” [23]. A client inserting in one autocommit batch and reading the identity in the next can land on another connection and receive a plausible wrong value. ProxySQL holds the connection after an auto-increment result, but TDS has no comparable signal [11]. The options are a grace hold after writes or declaring the application incompatible (inference). No runtime check catches this, so count leading reads during shadow and require application review. Sticky has no such exposure.

5.6 Driver settings and handles

  • JDBC: the source comment says “First execution, use sp_executesql”, later executions use sp_prepexec, and prepareMethod=none creates no server handle, sending direct SQL or an unprepared sp_executesql RPC [79] [80].
  • SqlClient without Prepare() uses sp_executesql [81].
  • ODBC was not established.

A moved handle raises error 8179, which JDBC retries only with statement pooling on, so pinning is correct and configuration avoids it [79]. But Microsoft scopes prepareMethod options to compatibility and migration, not general performance: plan reuse needs forced parameterization, and literals appear in traces and can cross the 16 KB pin (inference) [82].

Handle virtualization waits. PgBouncer’s renames client-chosen names [10], while TDS handles are server-minted and returned in responses, which would need rewriting [83]. Build it only if traces show sp_prepexec dominating among clients that cannot change. A per-cluster init batch, as AWS recommends, turns a matching SET NOCOUNT ON from a pin into a no-op [5].

5.7 Unpinning on client reset: an undocumented proposal

SqlClient marks the logical session boundary with the reset bit on the next command after reactivation [72]. Tedious resets only when reset() is called [84], so this applies only to drivers shown to send the bit at checkout. When a pinned client’s own reset is acknowledged and its pin causes have passed the matrix on this build, drop the pin and release at that response’s end. This slows long-pin decay, and no shipped proxy documents it. The client pool’s idle interval still holds the backend. It also rescues middle-tier row-level security, at an upper bound of one backend per logical session.

6. Authentication and Encryption

Client logins normally bind identity to the connection end to end. A sharing proxy must terminate login, hold or relay credentials, and open backends itself, and it must terminate TLS to read anything. Identity decides feasibility before any workload question, and encryption decides how much of the fleet a first release can serve.

6.1 No re-authentication, so per-principal pools

A search of MS-TDS for re-auth finds only pre-authentication, so it shows no re-authentication message [9]. LOGIN7 and its SSPI (Windows integrated authentication) or FEDAUTH (federated token) exchanges happen once per connection [9]. Microsoft’s pooler agrees: “The literal token is part of the connection-pool key.” [20] RDS Proxy keeps one secret per database user, limited to 200 per proxy [85] [59].

Client auth Proxy can Sharing Recommendation
SQL login, service account De-obfuscate, verify against a store, replay [8] Whole key Best first target
SQL login, per-user Same, one pool each [85] Shrinks with users Check census
Entra (Microsoft identity) token Forward on backend login, keyed on literal token [9] Per token Test; retire before expiry
Entra server-driven flow Relay FEDAUTHINFO on first login One to one Nonce echo leaves reuse unverified
Windows, Kerberos, NTLM No secret to replay (inference) None Passthrough listener
Extended Protection Binding ties to TLS channel None True passthrough

Forwarding each first login as a verifier makes a server login the cost of every client connection, the expense this project exists to remove, so use a secret store. If verification caches, a disabled login keeps working until the backend is replaced (inference to test). Case-sensitive collations can multiply secrets [85].

MS-TDS footnotes calling FEDAUTH unsupported do not describe current servers: Entra applies to SQL Server 2022 and later, except failover cluster instances [86]. RDS Proxy “doesn’t support connections that use Active Directory.” [59] ScaleArc advertises Kerberos offload through delegation [62], so Active Directory is outside this design rather than impossible.

6.2 The shared login is an experiment

One pool login carrying identity through EXECUTE AS or SESSION_CONTEXT would break the K × W floor. Microsoft documents WITH NO REVERT COOKIE as “useful in an environment in which connection pooling is used” and row-level security with a shared SQL user [77] [70]. It stays out of early stages:

  • It collides with the discard rules, deliberately setting state they call unreusable, with undocumented reset interaction.
  • Enforcement moves. Microsoft’s pattern assumes an application controlling its SQL. Through a transparent proxy, clients could issue REVERT or overwrite keys, making the scanner the security boundary.
  • The read-only variant likely defeats itself. A key that “can’t be changed again on this logical connection” suggests one connection per user [87].
  • Audit shifts. ORIGINAL_LOGIN() shows the pool login, and EXECUTE AS LOGIN is unavailable on Azure SQL Database [77].

No shipped TDS proxy using either technique appears in the sources read.

6.3 Encryption: TDS 8.0 first

TDS 8.0 is the easy path. ALPN (TLS protocol negotiation) value tds/8.0 identifies it, and stock TLS sockets fit both legs [9]. It covers SQL Server 2022 and later and Azure SQL. With Encrypt=strict, clients validate the certificate against the server name or HostNameInCertificate, so the proxy needs one they accept. Microsoft’s “standard network appliances are now able to filter and securely passthrough SQL queries” describes routing, not visibility [54].

TDS 7.x is the largest encryption unknown. The client sends “a TLS/SSL message obtained from the TLS/SSL layer encapsulated in TDS packet(s) of type PRELOGIN (0x12)” [9]. Envoy’s StartTls socket switches on a filter’s signal [88], and the Postgres precedent then does TLS directly on the socket [89]. Those facts jointly imply a stock switch would emit bare records where the peer expects PRELOGIN framing, so 7.x needs a custom transport socket that wraps handshake flights and steps aside. That is inference, no source describes the mapping, and a filter-level workaround may exist. Prototype it separately. It matters because JDBC defaults to encrypt=true, not strict [80], so a TDS-8.0-only release requires reconfiguring clients. Older servers need it on the backend leg. tdspool never solved this [90].

6.4 Forging the login response

Later clients get a template captured from a real backend login. tdspool’s 7.1 to 7.3 code order is database ENVCHANGE, message 5701, language, message 5703, collation, LOGINACK, packet size, DONE [8]; capture your own server’s response instead.

  • Build FEATUREEXTACK (feature acknowledgment) from what the client requested and the backend acknowledged, because a client must treat an unrequested feature as a protocol error [9].
  • Do not acknowledge SESSIONRECOVERY, since recovery fails anyway if a backend swap changes version or encryption [91].
  • Send a real ERROR token on bad credentials, where tdspool has TODO send nack before exiting.
  • Key pools on login options rather than patching them with SET ANSI_DEFAULTS OFF, which a later reset may undo (inference).

tdspool’s GPL header means checking licensing [47].

6.5 Channel binding, routing, and platforms

Channel binding compares tokens for that TLS channel [92]. Inference: a terminating proxy creates a different channel, so Windows authentication fails under Required. It “isn’t enabled by default for SQL Server connections”, so check each instance. Extended Protection “doesn’t apply to SQL authentication” [92], so SQL logins there stay candidates. Passthrough fixes framing and channel binding, not naming: a client addressing the proxy’s name may request the wrong SPN (service principal name). That is untested inference; the Kerberos SPN page was unreadable.

ENVCHANGE 20 or 21 redirects the client after login [58]. Forwarding bypasses the proxy, and a pooled connection cannot follow to a host outside the cluster (inference). Azure’s Redirect policy, recommended by Microsoft and the default inside Azure, uses ports 11000 to 11999, while the Proxy policy keeps 1433 at higher latency and lower throughput [93]. Use the Proxy policy first and treat any routing token as a failed login.

7. Connection Pool Design and Failure Handling

Envoy already provides per-worker pools, breaker limits, and health-driven eviction, and the filter reuses them. What Envoy does not know is that a database connection is scarce, slow to create, and bound to an identity. The work lies in partitioning correctly, staying under the server’s limit, and making every failure look like a database error.

7.1 Pool key and the filter-state route

The key is principal, initial database, language, LOGIN7 option flags, TDS version, FeatureExt set, read-intent, and application name if workloads depend on it. Packet size stays out. Database could leave by replaying USE; option flags must stay (inference from fODBC handling) [9].

Envoy allocates separate pools for downstream filter state objects “that are hashable and marked as shared with the upstream connection” [18]. After LOGIN7, set a hashable digest of the key and expose it through upstreamTransportSocketOptions() as tcp_proxy does [42]. The cluster manager’s hashing was not read, so verify this first. The fallback is Redis-style owned connections [95], rebuilding timeouts, TLS, and breakers. Never hash a raw credential.

7.2 The budget and its sharpest trap

Limits are shared, but “races between threads may allow limits to be potentially exceeded”, and the default is 1024 per cluster [7]. The trap is the floor. Even overflowed, a selected host gets one connection, bounding the total at cluster maximum connections + (number of endpoints in a cluster) * (connection pools for the cluster) [7]. As illustrative arithmetic and not a measurement, 8 workers, 200 principals, and 1 endpoint can mean 1,600 pools and a possible overshoot of 1,600 connections. “Connections automatically clean up; connection pools do not.” [7]

  • Require max_connections + endpoints × pools ≤ the server’s limit, with pools about W × K (inference). Near that limit the concurrent-pool cap and principal refusal are the binding controls. Draining connections count too [7].
  • Refuse logins past a configured principal count with a TDS error.
  • Run a small dedicated Envoy, since --concurrency is process-wide, with listener connection balancing for long-lived connections [19].
  • Disable preconnect [96], and shed idle connections by timer [49].
  • Retire connections below credential lifetime. One maintainer saw revalidation about every 10 hours, one observation and no constant [72].

7.3 Queueing and backpressure

Busy pools queue to the pending limit, then fail with Overflow [96]. Translate that to an ERROR token and a DONE with the error bit, so the session survives. Add an acquire timer, because SqlClient’s 30-second request timer otherwise fires first and sends an Attention [9]. Under sticky, a queued client waits on someone’s disconnect, so read common waiting as demand for transaction release.

Three interactions need budgeting, all inference:

  • ADO.NET’s login-failure blocking period, 5 seconds doubling to one minute, can amplify shed logins [6].
  • An application holding a transaction while opening a second connection waits forever if peers hold every backend, a deadlock SQL Server cannot see, so waits must be finite.
  • A slow client holds a scarce connection, so read-disable upstream on watermark and close on a timer [42].

7.4 Attention

Attention is an 8-byte packet and the only way to interrupt a complete request [97]. “After a client has sent an interrupt signal to the server, the client MUST read returning data until the interrupt has been acknowledged.” [9] The ack is DONE with DONE_ATTN (0x20), and other responses can precede it, so EOM is no boundary while one is outstanding [60]. For a late Attention, the server “MUST send an attention acknowledgment” [9]. Conformance is untested, and FreeTDS’s client-side suppression says nothing about servers [98], so keep the timer.

Arrives while Action
Lease held Forward; release only after DONE_ATTN; on timeout, poison
ACQUIRING Cancel handle; answer locally with DONE_ATTN
SCRUBBING Drop held request; finish scrub; answer locally
IDLE Answer locally; never touch an upstream
Partial request Forward client’s IGNORE plus EOM; server sends DONE_ERROR [97]

A late Attention in IDLE cannot reach a shared connection, because the session has none. Local acks are inference needing per-driver tests. Keep reading downstream during responses, up to a buffer bound.

8. Lessons from Existing Proxies

Most sharing proxies target Postgres and MySQL, whose protocols report more session state than TDS. The SQL Server record is far thinner, and several apparent precedents turn out not to be.

System What it does Lesson
RDS Proxy USE and 14 tracked SETs; broad pins; per-user secrets [85] Pin list and credentials, not transaction reuse
tdspool Forged login; sticky; no encryption [47] Token order, recovery batch
Heimdall, ScaleArc Heimdall: generic multiplexing, Postgres/MySQL examples, no SQL Server detail [101]; ScaleArc: SQL Server guide, protocol-aware settings, no multiplexing or pin rules in pages read [62] Plausibility only
PgBouncer Transaction mode by contract; untracked SETs “leak to other clients” [10] Explicit client contract

RDS Proxy contradicts itself. Its page says “SQL transactions on a client connection can multiplex between underlying database connections by default.” and, for SQL Server, lists “Creating temporary tables, transactions, cursors, or prepared statements.” as pin causes [5]. Searches found no resolution [102]. Release after ENVCHANGE 9 or 10 is therefore this design’s own proposal, justified by protocol signals and not precedent. An RDS test watching DatabaseConnectionsCurrentlySessionPinned would settle it.

tdspool’s code contradicts its README. The README describes per-query allocation [23]. user.c assigns at login with the comment “so deassign only when disconnected” [8], and the stream.c walker, noting XXX 12 for TDS >= 7.2, goes uncalled [103]. Inference: query-level pooling was planned and the tool settled on stickiness.

Commercial material supplies no TDS method. Heimdall’s up-to-20x Odoo gain, from a generic article not about SQL Server, needed delayed transactions, because that ORM’s per-activity transactions “would normally prevent multiplexing from providing benefits” [101]. PgBouncer is candid: transaction pooling “breaks client expectations of the server by design” [104].

Sharing collapse is silent. A ProxySQL guide warns a proxy can have “silently degraded into a 1:1 connection relay with overhead”, and that “A transaction-heavy service may legitimately run at 3:1, while a read-heavy API should achieve 20:1 or better.” [105] Those are MySQL rules of thumb, showing spread and not TDS results. Its top cause is connectors issuing session setup per connection.

The absences rest on a bounded search. It covered scholarly sweeps, open-source TDS proxies, vendor pages, driver source, and RDS and Microsoft documents. TDSProxy’s source, Dispatch, the Azure gateway, and driver issue trackers went unsearched. Among these, only RDS Proxy publishes TDS pin semantics. Rmg.Tds [106] and TDSBridge [107] forward packets without sharing, and SQL Relay [108] shows no TDS front end. No open-source TDS multiplexer, fetched vendor page claiming SQL Server multiplexing, shipped handle virtualization, shipped unpin-on-client-reset, or measured ratio was found. The record searched is empty; the technique is not shown impossible. Copy the vocabulary; do not import the confidence.

9. Build, Test, and Rollout Plan

One filter is built in stages, each ending at a gate where stopping is legitimate. The earliest stages need no filter, because the most valuable output is the missing measurement. Testing guidance and gates are this design’s recommendations, and thresholds are the operator’s, since no source supplies defensible numbers.

9.1 The census and the two ratios

Stage 0 needs VIEW SERVER STATE, or VIEW DATABASE STATE on Azure SQL Database. This unrun query uses documented DMVs (dynamic management views) [14] [94]:

-- UNBUILT ILLUSTRATION.
SELECT s.original_login_name, s.database_id, s.language,
       s.client_interface_name, c.auth_scheme, c.net_transport,
       COUNT(*) AS sessions,
       SUM(CASE WHEN s.open_transaction_count > 0 THEN 1 ELSE 0 END) AS in_txn
FROM sys.dm_exec_sessions AS s
JOIN sys.dm_exec_connections AS c ON c.session_id = s.session_id
WHERE s.is_user_process = 1
GROUP BY s.original_login_name, s.database_id, s.language,
         s.client_interface_name, c.auth_scheme, c.net_transport;

Sampled over a day, it approximates K (LOGIN7 flags stay invisible). It also gives the Windows share from auth_scheme, the MARS share from net_transport = Session, and the driver mix. Tune next: lower pool maximums, evaluate prepareMethod=none per application, remove needless SET batches. Name the binding limit (license, session cap, workers, memory, login storms). An idle connection costs about 3 × packet size + 94 KB [109], about 106 KB at a 4 KB packet by this report’s arithmetic, so idle count alone proves no need. Then compute required ratio R = peak connections otherwise needed ÷ connections you can afford, and stop if R ≤ 1. The passive decoder computes, per cell, concurrent sessions and concurrent leases under the transaction rule, giving achievable ratio A = sticky peak ÷ transaction peak.

Handle virtualization and the shared login sit beyond these stages, by default unbuilt. Keep one_to_one as a config-push kill switch, which may reach only new connections (inference).

Transaction release needs seven gates together:

  • Benefit: A ≥ R per cell, including pins and the worker floor.
  • Eligibility: never-pinned share supports it.
  • Matrix: each row passes or has a discard rule.
  • Framing: captures confirm EOM and late Attention.
  • Silent results: no multi-batch identity reads, or owners accept.
  • Reset cost: server and audit load acceptable.
  • Operations: sticky ran with no unexplained closes.

9.3 The reset matrix

Per platform, build, and TDS version: client A sets state, the proxy scrubs, client B reads, and a second session observes sys.dm_exec_sessions. A failure means pinning or discarding that state on that build. Run it in CI on each update, because behaviour has moved across server versions [110]. Any commercial proxy you evaluate should face it too.

  • Always scrub: isolation level, including BeginTransaction rollback [111], TransactionScope, and sp_executesql; USE before reset.
  • Pin until passed: SESSION_CONTEXT, normal and @read_only=1; CONTEXT_INFO; temp tables; global cursors; prepared handles; sp_getapplock; each SET on RDS’s lists.
  • Discard until passed: EXECUTE AS variants; application roles, with and without cookie.
  • Observe: 0x08 and 0x10 inside local and DTC transactions; tokens accompanying ENVCHANGE 18; disabled logins and logon triggers; SESSION_CONTEXT in parallel plans under load; late Attention; EOM across Attention and large results.

9.4 Test layers

  • Parsers. Fuzz all three, splitting every message at every byte: DONE chains, NBCROW, PLP straddles, ENVCHANGE 15, a commit carrying a begin. Use the specification’s hex examples [9], mssql-tds constants [53], and Wireshark’s dissector [50].
  • Envoy integration. Adapt tcp_proxy_integration_test.cc: FakeRawConnection, AbortReset, readDisable, waitForCounter, plus a scripted TDS backend [45]. Add Attention in each state, identity mismatch, idle stray bytes, and overflow at --concurrency 2.
  • Drivers. SqlClient, mssql-jdbc, ODBC 18, go-mssqldb, tedious, FreeTDS: pooling, cancel, strict encryption, forged logins, dictated packet size, MARS refused, client reset under pin.
  • Faults and isolation. Kill the server mid-transaction, delay acks, truncate mid-token, expire credentials; run two row-level security contexts on one key, asserting zero cross-visibility.

9.5 Operating it

Export per-key sessions, leases, backends, queue wait, lease hold, scrub failures, pin_reason.<reason>, closes by reason, walker_desync, attn_timeout, sessions_per_backend, and stale_read_risk, alongside upstream_cx_overflow and upstream_rq_pending_overflow [7]. Copy ProxySQL’s per-session pin reason [11], and alert on change from baseline [105].

Run canaries from sticky onward: probe the session’s own sys.dm_exec_sessions row, including transaction_isolation_level, context_info, and open_transaction_count, and diff against the login baseline; a diff closes the backend and alarms [94]. This cannot see unnamed SESSION_CONTEXT keys, which is why they stay pinned. Expect attribution loss: client_net_address shows the proxy, and host and program names come from whichever login opened the backend [14]. Review logon triggers and resource governance before sticky ships.

9.6 Where this could go

Identity is moving against sharing. If Entra tokens become per-user and short-lived, K grows and backend lifetimes shrink [86]. A server-side re-authentication message would invert this, though nothing in the specification suggests one. TDS 8.0 adoption helps, retiring the wrapped-TLS socket and extending SNI routing.

The C++ requirement is the most perishable assumption. Dynamic modules aim to match built-in extensions [30]. A lease callback family would let the Envoy-free parsers move to Rust and remove the custom binary, helped by mssql-tds and tds-driver [112]. SESSIONSTATE might also beat text scanning. The server reports fRecoverable when SESSIONRECOVERY is negotiated [9], and ODBC’s “marked by the server as unrecoverable” error hints at server judgment [113]. This is unverified; multiplexed logins strip that feature, so test it on a lab or shadow connection.

Run the census, build the sticky concentrator if it justifies one, and enable transaction release only where shadow data and the matrix agree on that exact build. A team stopping at recycling sticky with short-lived connections has shipped the right product. A per-user Windows estate should stop at the census. A shadow ratio near 1 is a good result, because it ended the project cheaply. Publishing the resulting matrix and ratio would fill the largest gap in this field.
