Since llm-d v0.9, choosing scorers has mostly been a question of structure, not weights. The well-lit-path guides run the prefix-cache-affinity-filter, one load scorer matched to the resource that saturates first (token-load-scorer for prefill-bound pools, active-request-scorer for decode-bound ones), and max-score-picker. With one scorer, the weight cannot change any routing decision, so tuning means calibrating the filter’s release gate: a measured peakPrefillThroughput multiplied by a maxTTFTPenaltyMs taken from the time-to-first-token (TTFT) budget. The gate is the right default but needs ongoing attention: in late 2026 it missed slot-bound queues and decode hotspots, triggered a production overload cascade, and had its estimator changed on 11 November. Pin the router version and watch the load_override counter. Weights still matter where a profile combines signals (tiered caches, fairness, LoRA, context length, topology); set them with effective-weight arithmetic and confirm with repeated benchmarks. Predicted-latency routing is the next step for homogeneous pools with high-variance traffic and service-level objectives (SLOs).

1. How EPP Scoring Works: Filters, Scorers, Weights and Pickers

The EPP (Endpoint Picker) is the scheduling component that the llm-d router shares with the upstream Gateway API Inference Extension. For each request it chooses one model-server pod: filters remove ineligible pods, scorers rate the rest, and a picker chooses one. How these stages combine determines what a weight can do.

1.1 Profiles, producers and configuration rules

A profile handler selects one or more scheduling profiles per request. Each profile runs filters, then weighted scorers, then exactly one picker. Under P/D disaggregation, where prefill and decode run on separate pools, the handler runs a prefill profile and a decode profile [1].

Scorers read signals from data producers. The approximate prefix producer infers cache contents from routing history. The precise producer ingests KV-cache events (the KV cache is the attention key/value memory reused across requests that share a prefix). The in-flight producer counts dispatched but unfinished work [2]. The precise producer must be named in prefixMatchInfoProducerName, or the scorer silently falls back to the approximate one [1, 3]. Defaults also bite: an omitted weight is 1.0, a missing picker becomes max-score-picker, two pickers in one profile fail at startup, configuration is read only at startup, and omitting schedulingProfiles activates every declared plugin [3].

1.2 The scoring arithmetic

An endpoint’s score is the sum of each scorer’s output, clamped to the range 0 to 1 and multiplied by its weight: weight 2.0 on a score of 0.8 plus weight 1.0 on 0.5 gives 2.1 [1, 4]. Metric-based scorers leave endpoints with missing metrics unscored, which counts as zero [5, 6]. Three consequences follow:

  1. Only weight ratios matter under max-score-picker. GORGO’s learned router fixes one weight to 1 because “only the ratio of weights matters in this design” [7]. With a single scorer, the weight is inert.
  2. A scorer’s real pull is its weight times the spread of its scores across candidates, so the same weights behave differently at different loads.
  3. A filter is not a heavy weight. When the affinity gate releases, every endpoint passes, and “Nothing tells the scorers that a break happened; they apply the same weights to whatever candidates arrive” [8].

The picker can matter more than the weights. With bursty traffic, no shared prefixes and eight Llama-3.3-70B replicas at concurrency 800, a weighted-random picker cut mean TTFT from 2083 ms to 367 ms and P99 TTFT by 73% versus max-score, which herded on stale scraped metrics [12]. Because randomness dilutes affinity, the filter README recommends weighted-random only inside the sticky set, the combination the predicted-latency guide ships [8, 13].

2. The Scorer Catalog: Signals, Strengths and Failure Modes

Each scorer turns one signal into a value between 0 and 1. Absolute scorers apply a fixed formula. Relative (min-max) scorers give the best candidate 1 and the worst 0, however small the gap. Capped scorers peak below 1, and neutral scorers sometimes return the same value for every pod.

2.2 Families, freshness and prefix accuracy

The catalog falls into four families: one affinity mechanism, load signals, capability scorers, and one spreader (no-hit-LRU). Most bad configurations stack two members of one family, such as a prefix scorer behind the filter or three gauges measuring the same load.

Freshness separates the load signals. Token-load and active-request read EPP-local counters updated at dispatch; gauge scorers read lagging scraped values. In the BLIS simulator at eight instances and 80 requests per second, metrics-only routing gave mean/p99 TTFT of 401.8/964.5 ms, against 105.4/186.0 ms with the in-flight producer [28].

Accuracy separates the prefix producers. The approximate index sees only routing history [1]; a cache-freshness fix was folded into another issue in September 2025 [29]. The precise index sees resident blocks, but with speculative indexing off it briefly reports zero for a cold endpoint just sent a long prefix, a window the November 2026 overload incident named as a contributor [30]. The precise guide sets speculativeIndexing: true [31]. Under heavy eviction the gap is large: at 73% cluster cache demand, precise routing reached a TTFT p90 of 0.54 s against 31 s for approximate, on an older scheduler [32].

3. Deciding Which Scorers to Enable by Workload and Deployment Shape

Two questions decide the composition: which resource saturates first, and what the base pair (the affinity filter plus one load scorer) cannot see.

3.1 Decision procedure

  1. Confirm that the engine caches prefixes. If not, drop the filter, as the project’s NPU overlay does; otherwise it “would pin requests to endpoints it believes are cache-warm while the model servers reuse nothing” [33].
  2. Name the saturating resource. Long prompts with modest outputs are prefill-bound; short prompts with long outputs are decode-bound. If vLLM sits at max-num-seqs with a queue while KV use stays low, the pool is slot-bound, which the default gate cannot see [34]. If the shared prefix never reaches 0.8 of the prompt, the filter does nothing, as with the 250-token prompt in the reasoning benchmark [35]. Where affinity recovers only a few points of hit rate, pinning skew can make it a net loss: CacheRoute measured 0.50–0.67× the capacity of flat load balancing when hit rate rose only from about 1% to 12% [36]. Compare the filter against a load-only profile at production load, or in a BLIS replay, before adopting it.
  3. Pick one load scorer for that resource and a prefix source: approximate by default, precise under heavy eviction or with tiered caches.
  4. Check whether decode load is two-dimensional. Where short turns mix with 24k–100k contexts, active-request can overflow KV while token-load stacks requests onto full batch slots [18]. An unmerged length-adaptive prototype cut peak decode KV from 92.6% to 78.8% and long-request P99 TTFT by 10.7% across three seeds, which no fixed per-profile weight can imitate [18]. A capacity ledger tracking KV blocks, step tokens and slots is also proposed [37]. Until either lands, enable addEstimatedOutputTokens, cap KV with a utilization filter, or use the predictor.
  5. Add capability scorers only for what the base pair cannot see.

The rule underneath: the single-scorer default fits only when the gate’s own signal can see the bottleneck. When it cannot, the downstream scorer never gets a vote.

4. Default Configurations and Weights in llm-d Guides

llm-d’s well-lit-path guides are Helm values files encoding the authoritative configuration per deployment shape, but a cluster can end up running a different one.

4.1 How the defaults moved

The v0.4-era quickstart weighted prefix 3, queue 2, KV 2 and no-hit-LRU 2 [44]. Version 0.9 announced that “Sticky-until-saturated routing is now the default strategy across all guides” and that it “balances cache reuse against load distribution without manual tuning” [45]. The maintainers’ reasons: the blend’s “emergent behavior was hard to predict and harder to tune”, and affinity without “an explicit saturation release” overloads the warm endpoint [35]. Router v1.0.0 was tagged on 15 October 2026 [21].

4.2 What ships today

4.3 Three defaults, and why the version must be pinned

Guides, chart and reference thus disagree: a bare install gets the 3/2/2 blend, which starves freshly scaled pods at low load [21]. A pending pull request adds no-hit-LRU to the chart default, relying on a fix merged on 29 October 2026, after v1.0.0 [48]. The guides also pull the floating ROUTER_CHART_VERSION=v0 channel [49].

The documentation advertises two router replicas [40], but the values files pin one. Active-active replicas would each see only part of the per-endpoint load and so mis-gate the affinity filter [31]. An earlier tiered-cache pull request’s −48.9% mean TTFT and +33.3% throughput from tuned scorers are confounded with enabling CPU offload, and its weights were not recorded [50].

Nor is the new default tuning-free. It replaced four weights with about five workload-specific constants, and the multimodal guide changed two of them to reach only “benchmark-validated to parity with the previously shipped weighted blend” [35]. Treat 3/2/2 as historical, and 15,928 tok/s as one measurement rather than a portable default.

5. Tuning Scorer Weights: Method, Ratios and Measurement Loop

Single-scorer profiles need the gate calibrated; blends need weights set by arithmetic before any sweep. Both feed one measurement loop.

5.1 Tier 1: calibrating the gate

With the default estimator, the gate is a token-gap threshold, τ = peakPrefillThroughput × maxTTFTPenaltyMs: stickiness breaks when the sticky endpoint carries τ more uncached tokens than the best alternative [35]. The maintainers derive throughput from one prefill chunk, R_peak = B / T(B), for chunk size B and its prefill time T(B). For Qwen3-32B, 8192 tokens in 0.40 s on H100 gives 20,480 tok/s, and a 14 s budget gives τ = 286,720 tokens [35]. The shipped 15,928 tok/s × 18 s gives about 286,704 tokens, but the match comes from offsetting choices. The two throughput methods differ by 29% on the same path, and the 14 s came from where b2b-saas (a small repeated-prefix benchmark corpus) saturates, not from a user SLO [33, 35]. Keep the method and penalty default paired.

Measure throughput; do not copy it. calibrate.sh sends random-token prompts of exactly CHUNK_SIZE, which should equal --max-num-batched-tokens so every request misses cache, and prints CHUNK_SIZE / median(TTFT) without applying it [33]. Run it repeatedly: one NPU calibration ranged from 12,504 to 13,101 tok/s over five runs, and the project used the median [33]. Measured values span 1,970 tok/s on CPU to 39,065 tok/s for gpt-oss-120B on H100, and some vendor rows are borrowed rather than measured [51]. A transplanted τ sets gpt-oss-120B’s gate about 1.9× too low and Qwen3-VL on H200’s about 1.3× too high, and one matrix row was twice the corrected figure [35, 51]. For P/D, calibrate through KV transfer [11].

Treat maxTTFTPenaltyMs as a budget: the extra TTFT accepted to stay cache-warm rather than re-prefill elsewhere. At 4,274 tok/s, 18 s is about 77k tokens, which let 38 requests pile onto one endpoint, while 4 s released at about 9 and cut TTFT p90 from 4.4 s to 0.65 s [16]. Too small a τ fails too: on b2b-saas the cluster is bistable in τ, and small changes flip it from a stable partition into eviction churn with a collapsed hit rate. No τ-sensitivity curve is published, so sweep the penalty around the derived value at more than one load point and watch hit rate alongside TTFT [35]. At 15,928 tok/s, 5 s is 79,640 tokens, so one 80k-token cold spill trips the gate [30].

Match the penalty to the estimator. ttftEstimate: full, merged on 11 November 2026 after v1.0.0, adds the request’s own uncached prefill; under it the 18 s default makes the filter “much stickier”, so full needs a lower penalty [8, 34, 52]. Maintainer runs on the stacked queue-wait PR found no difference from backlog [52, 53]. An open queue-wait term turns the penalty into a queueing budget; under it, 18 s queues settled at 8–10 s [53].

Set the remaining parameters:

  • Keep affinityThreshold below the largest cacheable fraction, and queueThresholdTokens above in-flight peaks, or pods tie at zero [8, 15].
  • Raise maxPrefixTokensToMatch for long contexts, since its 131,072 default counted 7–8× too many uncached tokens on ~262k-token prompts [53].
  • With KV offload, disable the approximate producer’s autoTune, which counts HBM blocks only, and size lruCapacityPerServer manually, as the agentic guide does [54].

5.2 Tier 2: budgeting a blend by effective pull

Effective pull is the weight times the scorer’s spread:

  • Relative scorers swing their full weight on any difference, so queues of 1 and 2 matter as much as 100 and 200 [6, 55].
  • Capped scorers swing half: load-aware tops out at 0.5 and needs weight 4 to match queue at 2 [19].
  • Absolute scorers (prefix, KV, token-load) swing only as far as their signal varies.
  • Neutral scorers swing nothing; no-hit-LRU adds 0.5 × weight to every pod on warm requests and never reorders them [20].

Take the legacy blend: prefix P = 3, load weights queue 2 and KV 2 (L = 4), and a request fully cached on pod Hot.

Case Hot: prefix, queue, KV → total Cold: prefix, queue, KV → total
Under load 1.0, 0 (longest queue), 0.3 → 3.6 0, 1.0, 0.9 → 3.8
Low load 1.0, 1.0 (queues equal), ~1.0 → 7 0, 1.0, ~1.0 → 4

Under load, Cold wins only because min-max queue scoring hands it a full two-point swing, identical whether Hot queues one request or a hundred. At low load Hot always wins, and for a new prefix the pods tie at 4.0 and a coin decides; the chart-default issue measured 0 of 20 cached-prefix requests reaching a new pod [21]. A blend’s release point is implicit and moves with load; the gate’s is explicit, in tokens and seconds.

The same arithmetic explains the README’s strictest rule. After a release, load scorers can favor a non-sticky endpoint by at most L, while a prefix scorer penalizes it by P times the prefix-score gap. With P ≥ L a zero-match endpoint can at best tie; with P ≥ L ÷ affinityThreshold it can never win. A prefix weight of 3 over token-load at 1 shuts the gate for every cold endpoint, hence “Scorers running after this filter must not include a separately weighted prefix-affinity scorer” [8].

For any blend, classify each scorer’s spread, then choose P:L to state how much full-range load advantage should beat one unit of prefix match; in 3 vs 2+2, a cold pod needs more than 0.675 of the range to beat a 0.9 match. Add no-hit-LRU near the queue weight.

Tuning does pay inside blends. On production-shaped traffic, moving from (1,1,1) to a workload-tuned (3,2,2) cut E2E (end-to-end) p50 from 16.42 s to 13.42 s, E2E p95 from 35.06 s to 26.55 s and TPOT p99 from 103 ms to 63 ms, while TTFT p50 rose from 2.86 s to 3.38 s [42]. GORGO’s online (1+1) evolution strategy on rolling p95 TTFT learned weights that held on held-out windows, improving p95 TTFT by 6.9–15.5% and p95 E2E by 14.3–30.9% [7].

5.3 The measurement loop

  1. Screen in BLIS. It runs the real router with an unchanged EndpointPickerConfig and traces per-endpoint score margins, showing whether a weight change moves any decision. Sweep P:L from 0.5 to 2 at several concurrencies, with the deployment’s --refresh-metrics-interval in router.epp_flags so stale-scrape herding appears [28]. No source documents a systematic weight search beyond this ratio arithmetic and sweeps. It is a screen, not a verdict: median latency error is 7–9% at about 200× cluster speed, with no published rank-fidelity figure [56], and replayed logs miss the cache and queue evolution another policy would cause [7].
  2. Validate with inference-perf, a load-generation benchmark: workload-matched presets, with and without the change, as the maintainers require for gate changes [34].
  3. Track TTFT and TPOT percentiles, prefix hit rate (vllm:prefix_cache_hits_total ÷ queries_total) and per-pod queue and KV use [49], plus per-endpoint QPS (queries per second) and preemptions [57].
  4. Watch llm_d_epp_prefix_cache_affinity_filter_decisions_total{outcome="load_override"} most closely. If it climbs while the sticky endpoint’s queue holds steady, the gate is firing without changing routing, the signature of a stacked prefix scorer [8].
  5. Re-calibrate after changes to model, accelerator, parallelism, batch size, engine, router or reuse pattern; Google Kubernetes Engine (GKE) documentation treats frequent re-tuning as the cue to adopt the predictor [27].

6. Evidence, Disagreements and Pitfalls

Nearly every llm-d comparison is a single first-party run without confidence intervals, issue measurements come from single reporters, and the peer-reviewed work studies other systems.

6.1 Weighted blend versus filter and gate

The gate wins on robustness in its authors’ single runs per cell, made with the pre-estimator token-penalty form, so the result supports the design rather than the current estimator. It reached 2.0× knee throughput on b2b-saas, while the blend cliff-failed on code generation and hot-spotted above concurrency 50 on reasoning [35]. An earlier llm-d benchmark found that under heavy prefix sharing, prefix-only scoring served about 55% of requests, against 100% for prefix plus load [61].

The blend’s one win is real. On b2b-saas it held a 96–97% hit rate against 70–73% at 50+ QPS, with the best TTFT p90, because “the legacy blend has no such valve”. The authors concede that “a carefully tuned weight set will outperform a general configuration on the specific workload it was tuned for”, yet call that small, bistable corpus “a poor benchmark for hyperparameter sweeps” [35].

The gate is the right default and the blend a scoped exception for multi-signal profiles or benchmarked corpora. The gate’s failures concentrate risk in knobs whose meaning changed between releases.

6.2 Static calibration versus predicted latency

The predictor beat the tuned (3,2,2) blend on E2E p50 (9.06 s vs 13.42 s) and TTFT p50 (0.97 s vs 3.38 s), tying on synthetic cache-churn scenarios [42]. Its documentation states that “No fixed weight configuration is correct in all regimes” [25]. Lodestar extends the critique to thresholds: the best prefix-hit threshold was 20% for one workload and 60% for another, both trailed a learned router by 300–400 ms. At high request rates, a prefix-and-load heuristic averaged 3,468 ms TTFT against 1,409 ms for plain least-request [43]. In one scale-out run the predictor gave new replicas 73–74% of traffic, and the reporter called it “the better option today” for that case [53].

Its rationale is that cache reuse concentrates load while low utilization spreads it, and the right balance shifts with the workload [42]. The costs: homogeneous pools only, an 18-vCPU router pod, about 300 QPS per prediction server, stream: true for SLO mode, and a heuristic fallback during warm-up that brings weights back [25, 26, 27]. Tuning moves rather than disappears: the guides still set affinity thresholds (0.8, plus a stacked 0.99 filter in SLO mode) and a 5000 ms penalty [13, 47]. No benchmark compares the predictor with the calibrated gate. It is the escalation path for homogeneous pools where request cost varies by orders of magnitude and per-request SLOs or hit-rate stability matter.

6.3 How strong affinity should be

Dynamo calls its default overlap credit of 1.0 “a reasonable starting point” and adds decay against starvation [58]. Lodestar documents the downside: bursts of long, prefix-matching requests saturate one pod’s KV cache into eviction and preemption [43]. The strongest independent evidence is DualMap (ICLR 2026). It keeps affinity until pending prefill tokens would breach a threshold derived from the TTFT SLO, then routes to the least-loaded instance. The full system reached up to 2.25× capacity; the SLO-aware step alone cut P50/P90 TTFT by 23.5%/18.5%. It also finds per-request minimum-TTFT routing lands between affinity and least-loaded on both hit rate and balance, and argues that single-mapping hybrids cannot achieve both [62].

Its threshold is R_peak × T_max under another name. That supports SLO-derived release thresholds, not llm-d’s design as a whole. A sticky set whose release reopens every endpoint is such a hybrid, consistent with the gate’s 70–73% hit rate on b2b-saas and the #4042 cascade, which bounded spillover targets [30, 35]. Start affinity at the shipped 0.8, a value never swept for llm-d and, per Lodestar, workload-dependent [43], with a load-gated release and a cold-start mechanism. The remaining disputes, documentation versus guides and blog versus recipe throughput, reflect lag rather than substance.

Pool-wide saturation Flow control admits requests, gated by a utilization detector fusing queue depth and KV pressure, before any scorer runs [64] Tune admission; weights only place admitted requests

Gate failures are observable through load_override, but only the decode hotspot and the slot-bound queue have configuration workarounds. The cascade has only an off switch, and the real fixes are unmerged or closed code [30, 53, 63]. The blend’s failures are not all structural either: its cold-pod tie yields to a configuration change, adding no-hit-LRU [48].

7. Recommended Playbook

  1. Classify the workload: prefill- or decode-bound, slot- or token-bound, shared prefix above 0.8, homogeneous pool, engine prefix caching on.
  2. Copy your release’s guide values file and pin the router chart.
  3. Run the base profile: affinity filter plus token-load (active-request if decode-bound; one per P/D profile), max-score, no weights, one EPP replica.
  4. Calibrate peakPrefillThroughput on your own serving path, taking the median of five runs, as the project did.
  5. Set maxTTFTPenaltyMs from the TTFT budget, check τ against your prompt sizes, and lower it under full. For agentic short turns, one reporter’s 4000 ms with addEstimatedOutputTokens is a starting point.
  6. Add capability scorers only where needed, sized by effective pull; add no-hit-LRU or small exploration if the pool autoscales; never add a weighted prefix scorer after the filter.
  7. If a blend is unavoidable, set P:L by arithmetic, screen in BLIS, and, we recommend, validate with five repeats per load point, matching calibration.
  8. Monitor load_override, hit rate, per-pod spread, and estimated versus measured TTFT. Use maxTTFTPenaltyMs: 0 only as a short emergency brake: it disables the release and reintroduces warm-endpoint hotspots.
  9. Escalate to predicted latency only for homogeneous, high-variance pools with SLOs, and re-calibrate after every model, hardware, engine or router change.

Pending gate work moves the estimate toward real TTFT: the request’s own prefill cost, queue wait, bounded spillover that warms one extra endpoint rather than the whole pool, and estimate-versus-actual histograms. The capacity-ledger and length-adaptive proposals bring multi-signal combination back, computed per request rather than fixed per profile. Weights will likely survive as derived or learned coefficients rather than YAML constants, and the operator’s question will shift from choosing weights to checking whether the calibration still holds.

Two caveats remain. Per-request precision could revive the instability DualMap documented, so bounded spillover and stable thresholds are the features to watch. And no multi-run benchmark yet compares a tuned blend, the calibrated gate and the predictor on one workload, so every number above is a starting point to verify.
