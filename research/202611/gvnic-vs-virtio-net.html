gVNIC vs virtio-net on Google Cloud: Device Model, Performance and Migration

gVNIC (Google Virtual NIC) is a Google-only paravirtual PCI network device that replaces virtio-net on Compute Engine. The main difference is not one feature. virtio-net is an open, vendor-neutral standard that every guest OS can drive. gVNIC is a Google-specific device with its own register layout, admin queue and descriptor formats, built for Google’s Andromeda network stack. In practice the choice is mostly made for you. Third-generation and later machine series, Arm VMs, Confidential VMs, Tier_1 networking (50–200 Gbps), jumbo frames and the GPU machine families all require gVNIC. virtio-net remains an option only on first- and second-generation VMs at default bandwidth. It does keep one advantage there: up to 32 queues per vNIC against gVNIC’s 16. Google’s own benchmarks show gVNIC cutting MPI latency by 26% and raising 100 Gbps throughput by 57% compared with virtio-net. These are vendor numbers from 2021, and no independent replication was found. Moving from virtio-net to gVNIC is an image and driver task. The image must carry the GVNIC guest OS feature and load the gve driver. Most migration failures come from skipping one of those two steps.

1. What gVNIC Is

Google describes gVNIC as “a virtual network interface designed specifically for Compute Engine” and “an alternative to the virtIO-based ethernet driver.” It also calls gVNIC “the next generation network interface which succeeds VirtIO.” For all new machine types (Generation 3 onward), gVNIC replaces virtio-net as the only supported interface [1]. Google gives three reasons: better performance, more consistent performance through fewer noisy-neighbor effects, and network capabilities that virtio cannot offer [1]. The 2021 launch post adds that gVNIC is “tightly integrated with our high performance, flexible Andromeda virtual network stack.” It also says gVNIC is required for the 50–100 Gbps bandwidth configurations [4].

To the guest, gVNIC is an ordinary PCI Ethernet device with Google’s own identity. It uses vendor ID 0x1AE0 (Google), device ID 0x0042, subsystem 0x1AE0/0x0058 and class 0x200 (Ethernet) [2]. It exposes three 32-bit memory BARs. BAR0 holds the configuration and status registers, BAR1 the MSI-X vector table, and BAR2 the interrupt, RX and TX doorbells [2]. The driver controls the device in four ways [2]:

  • MMIO registers for initialization and status.
  • An Admin Queue (AQ). This is one page of command slots. The driver fills slots, rings GVE_ADMIN_QUEUE_DOORBELL, and polls an event counter until the device has executed the commands.
  • Device reset, triggered by writing 0 to the AQ PFN register. The device then releases every resource the driver allocated.
  • Two kinds of interrupt. A management interrupt tells the driver to read GVE_DEVICE_STATUS. Per-notification-block interrupts schedule NAPI polling of the queues.

The Linux driver is called gve. Google maintains it upstream in the kernel and also as an out-of-tree DKMS package (for example version 1.4.6) for distros whose built-in copy is old [2, 13]. Windows uses an NDIS miniport driver that binds the same 1AE0:0042 device. FreeBSD and DPDK drivers also exist [1, 14, 7].

2. How gVNIC Differs from virtio-net

2.1 Standard device vs proprietary device

virtio is a specification for a family of paravirtual devices. A virtio device can sit on PCI, MMIO or channel I/O transports. The driver and device negotiate capabilities through feature bits and exchange buffers through virtqueues in guest memory [3, 6]. Any virtio-net device must use PCI vendor ID 0x1AF4. Its device ID is derived from the virtio device type: 0x1041 for the network card, or transitional 0x1000 [3]. The same guest driver therefore works on QEMU/KVM, on hardware virtio NICs and on any cloud that exposes virtio [3, 6]. The backend can be QEMU or the in-kernel vhost-net, and the guest never knows which. In vhost-net, a kernel worker thread polls for guest notifications through ioeventfd and injects interrupts through irqfd, so packets bypass the QEMU process. The Red Hat write-up notes these backend changes “are completely transparent to the guest who still uses the standard virtio interface” [5].

gVNIC drops that portability. Its control plane (admin queue, registers, reset protocol) and its data plane (descriptor formats) are defined only by Google’s driver documentation [2]. In exchange, Google controls both sides of the interface and can shape it around its own host stack.

2.2 Queue and descriptor formats

virtio-net has two ring layouts:

  • Split virtqueue. The original layout, and the only one in virtio 1.0 and earlier. It keeps a descriptor table plus separate available and used rings [3, 6].
  • Packed virtqueue. Added in virtio 1.1 and negotiated through VIRTIO_F_RING_PACKED. It folds everything into one descriptor ring of up to 2^15 entries. Each descriptor carries a buffer ID, address, length and flags. The device writes completions back over the driver’s descriptors, and event-suppression areas control notifications [3].

gVNIC has its own two descriptor formats, which “have entirely different descriptors” from each other [2]:

  • GQI. Each queue is a power-of-two descriptor ring paired with a buffer and assigned to a notification block. The head advances through a big-endian doorbell in BAR2 and the tail through a big-endian counter. Every queue’s buffers must be pre-registered with the device as a queue page list (QPL), and packet data can only live in those pages. On transmit the driver copies packets into a FIFO built from the QPL. On receive, a data ring the same length as the descriptor ring advances in lockstep with it [2].
  • DQO. This is a submission/completion design, closer to modern hardware NICs. TX and RX buffer queues post descriptors and ring MMIO doorbells. Separate completion queues return results and use a generation bit to mark new entries. TX packets carry a 16-bit completion tag and RX buffers a 16-bit buffer ID, so completions can arrive out of order. DQO descriptors are little-endian. Packet buffers are DMA-mapped directly, and a received packet can span several fixed-size RX buffers [2].

Separately, gVNIC has two addressing modes. QPL uses a fixed, pre-registered page set. RDA (raw DMA addressing) uses a dynamic page set, so “the packet buffers can be anywhere in guest memory” [2]. DPDK’s driver documentation names the three combinations that exist: GQI_QPL, GQI_RDA (deprecated) and DQO_RDA. It explains the cost of QPL directly: TX “needs to copy packets to QPL memory” and RX must “copy packets from the address to get real packets data” [7]. Under RDA, by contrast, the driver writes physical addresses into descriptors “like usual NICs” [7].

That leaves a real design difference. virtio-net always lets the device read and write driver-supplied buffers in place. gVNIC offers both a bounce-buffer mode (QPL) and a direct-DMA mode (RDA). The device tells the driver which queue format to use; it is not a guest choice [2, 7].

2.3 Offloads and newer features

virtio-net negotiates its offloads as feature bits. Examples include [3]:

  • Checksum offload (VIRTIO_NET_F_CSUM).
  • TSO in both directions (HOST_TSO4/6, GUEST_TSO4/6).
  • Mergeable receive buffers (MRG_RXBUF).
  • Multiqueue with automatic receive steering (VIRTIO_NET_F_MQ, which requires the control virtqueue).
  • RSC and failover standby.

The software stays portable, but each feature works only if the host backend implements it.

gVNIC’s newer features ride on the DQO format and on Google’s driver:

  • Header split. Merged into Linux in March 2024 and controlled with ethtool’s tcp-data-split ringparam. The series adds a 128-byte header buffer per RX descriptor and raises the maximum RX buffer to 4096 bytes. It also adds counters for split packets and for packets left unsplit (when the header overflows its buffer or has zero length) [8]. Header split is a precondition for zero-copy receive paths in the kernel.
  • RSS and flow steering. DPDK’s gVNIC driver supports RSS with a 40-byte key and a 128-entry redirection table. It also supports 5-tuple receive flow steering through the rte_flow API [7].
  • Hardware timestamps. Per-packet RX timestamps and read_clock work only in the DQO format [7].
  • Jumbo frames. On Compute Engine these require gVNIC driver 1.3 or later (or IDPF on bare metal), not virtio-net [10].

The DPDK documentation is internally inconsistent. The same page says the poll-mode driver supports only the GQI formats, and that only the GQI_QPL format is in use on GCP. Yet it lists a timestamp feature that needs DQO [7]. That part of the page is probably out of date. Check the DPDK release notes for your version before relying on DQO in DPDK.

2.4 Queue counts

The two device types also get different default queue allocations, and gVNIC is the more limited of the two here:

Configuration Default queues per vNIC Max per vNIC
Gen1/Gen2 VM, virtio-net vCPUs ÷ vNICs 32
Gen1/Gen2 VM or M3, gVNIC vCPUs ÷ vNICs ÷ 2 16
Gen3+ VM (Titanium), gVNIC vCPUs ÷ vNICs 16

Sources: [9, 10].

Custom queue counts let you raise these numbers. The cap is still “with virtIO, the maximum queue count is 32, while with gVNIC, it’s 16” [9]. In return, gVNIC with Tier_1 on N2, N2D, C2 and C2D allows queue oversubscription. That means 16 queues per vNIC even when the total exceeds the vCPU count. In Google’s multi-NIC network-appliance test, this raised aggregate throughput from about 50% to about 99% of the VM’s stated bandwidth [9].

3. Performance, Bandwidth Tiers and Machine-Series Requirements

3.1 Where gVNIC is mandatory

The machine generation decides most cases [1]:

  • Generation 3 and later (C3, C4, N4, Z3, A3, and so on, excluding bare metal): gVNIC is the only virtual NIC. Bare metal uses Intel’s IDPF driver instead [1, 17].
  • Generation 1 and 2 (N1, N2, N2D, C2, C2D, A2, G2…): virtio-net is allowed. gVNIC is required if the VM runs on Arm, is a Confidential VM, or needs 50–100 Gbps through Tier_1 networking or the A2/G2/N1 high-bandwidth GPU configurations [1].

3.2 Tier_1 networking

Per-VM Tier_1 networking raises a VM’s egress ceiling. The limits run from 50 Gbps up to 200 Gbps on large C3, C3D, C4, C4D and Z3 shapes [11, 10]. N2, N2D, C2, C2D, M3 and C4A top out at 100 Gbps under Tier_1 [10]. Tier_1 “requires the gVNIC virtual network driver and a gVNIC-compatible OS or custom image.” Gen3+ VMs also need driver 1.4.2 or later to reach the highest bandwidth [11]. The setting is tied to the NIC type: Tier_1 can be enabled at creation only “if the instance doesn’t use the VirtioNet interface.” It can be added later only if the instance was created with gVNIC or IDPF [11]. So a virtio-net VM stays at default bandwidth. On a large N2, for example, that is 32 Gbps internal versus up to 100 Gbps with Tier_1 [11].

Google’s bandwidth guide lists “using VirtIO instead of gVNIC with compute instances that support both network interface drivers” as one factor that can lower achieved bandwidth [10]. It also warns that large C3, C4 and Z3 VMs can hit NUMA bottlenecks above 100 Gbps whichever driver you use [11].

3.3 GPU machines

GPU families use gVNIC for their general-purpose (non-RDMA) networking. For most GPU instances, Google recommends gVNIC to get rates of 50 Gbps and above [12]. The NIC layout differs by family:

  • A4 (B200) and A3 Ultra (H200) VMs have eight ConnectX-7 RDMA NICs for GPU-to-GPU traffic and two gVNICs for regular VPC traffic. Each gVNIC must attach to a different VPC network [12].
  • A3 High, Mega and Edge (H100) layouts attach their NICs per PCIe/NUMA domain [12].
  • A4X also uses gVNIC for its VPC networks [12].
  • A5X and A4X Max, the newest shapes, move those VPC interfaces to IDPF [12].

3.4 Measured differences

The only head-to-head numbers found come from Google’s 2021 HPC post. That test used c2-standard-60 VMs with compact placement and the HPC CentOS 7 image with gve 1.2.3 [4]:

Benchmark Result for gVNIC vs virtio-net
IMB PingPong, 2 kB–4 MB messages, default tier 26% lower latency on average
OSU multi-pair bandwidth, Tier_1 100 Gbps 57% higher throughput (gVNIC required for 100 Gbps)
WRF v3 CONUS 12 km, 24 VMs / 720 ranks 51% faster
ANSYS Fluent 13% faster
ANSYS LS-DYNA 11% faster

Two cautions apply:

  • The 57% throughput figure partly reflects Tier_1 itself, since virtio-net cannot use Tier_1 [4, 11].
  • All of these are vendor benchmarks on one 2021 machine type with no independent replication found, so treat them as directional.

4. OS, Driver and DPDK Support

Linux. The gve driver is in the mainline kernel, and Google also ships an out-of-tree DKMS build from GitHub. Distros listed as gVNIC-capable ship a native driver. The DKMS build can replace it “to get the latest enhancements” and supports clean, non-EOL LTS kernels [13]. Native drivers often report version 1.0.0 regardless of their real feature level, and the repository says to ignore that string [13]. Feature gates are tied to driver versions: jumbo frames need 1.3+ and full Tier_1 bandwidth on Gen3+ needs 1.4.2+ [10, 11]. An old distro kernel can therefore run gVNIC but miss features. virtio-net has no such gap, because its features are negotiated and the in-kernel driver is mature everywhere [3].

Windows. The gVNIC driver ships as the GooGet package google-compute-engine-driver-gvnic [1, 14]. Use version 1.0.0@45 or later. Earlier versions cause poor throughput on Windows Server 2022 and Windows 11 [17, 1]. The GitHub README still describes the driver as Early Access, which looks out of date given that the product docs present it as generally supported [14, 1].

DPDK. Both device types work with DPDK on Compute Engine. Google labels gVNIC “Recommended” and VirtIO-Net the open-source alternative. Both VPC networks in a DPDK setup must use the same vNIC type. Tier_1 with DPDK requires gVNIC [15]. When unbinding DPDK, the guest driver directory is gvnic for gVNIC and virtio-pci for virtio-net [15]. The DPDK drivers differ:

  • net_gve is based on gve kernel driver 1.3.0 and supports multi-queue, TSO, checksum offload, RSS, flow steering and timestamps [7].
  • net_virtio is the generic virtio driver. It supports split and packed rings, mergeable buffers and hash reports in packed mode. It also inherits virtio’s dependence on what the backend negotiates [16].

5. Choosing and Migrating Between the Two

Choosing. On Gen3+ machines, Arm, Confidential VMs, GPU families, Tier_1 or jumbo frames, there is no choice: use gVNIC [1, 10, 11, 12]. On Gen1/Gen2 at default bandwidth, Google recommends gVNIC but virtio-net still works [1]. Keeping virtio-net makes sense in three cases:

  • The guest OS has no usable gVNIC driver.
  • You need a single image that boots unchanged on other KVM platforms.
  • A network appliance needs more than 16 queues per vNIC [9].

The last reason does not carry forward. A virtio-net VM with more than 16 custom queues per vNIC cannot change its machine type to a Gen3+ series. It has to be rebuilt as a new instance [10].

Migrating a VM. The NIC type belongs to the instance, and the guest feature belongs to the image. You need both:

  1. Tag the image. Create the image with --guest-os-features=GVNIC (or guestOsFeatures: [{type: GVNIC}] in REST), starting from a gVNIC-capable source image [1]. If you skip this, creation fails with NetworkInterface NicType can only be set to GVNIC on instances with GVNIC GuestOsFeature [17].
  2. Make sure the driver loads. If the VM boots but has no network, the driver usually didn’t install or load. Check with modinfo gve and lsmod | grep gve on Linux, or look for gvnic.inf in dism /online /get-drivers on Windows [17]. When replacing the in-tree module by hand, run rmmod and modprobe on a single line, because running rmmod alone drops connectivity. Regenerate the initramfs so the out-of-tree driver loads at boot [13].
  3. Create the VM with nic-type=GVNIC on every interface. Mixing NIC types on a multi-NIC VM is allowed but not recommended [1]. Add Tier_1 at creation, or later only if the VM already uses gVNIC [11].
  4. Check MTU and queues afterward. If the VPC’s jumbo MTU isn’t taking effect, the driver is too old [17]. Expect queue counts to change per the queue-count table above [10].

GKE. Standard node pools enable gVNIC with --enable-gvnic when you create or update a node pool, and disable it with --no-enable-gvnic. Either change recreates the nodes. Autopilot nodes on 1.30.2-gke.1023000 and later get gVNIC automatically [18]. The GKE page says gVNIC “is not supported on memory-optimized machine types.” This conflicts with the Compute Engine page, which says Gen3+ series, including M3, support only gVNIC [18, 1]. Treat the GKE statement as possibly stale, and check it for the specific M-series you plan to use.

The bottom line. virtio-net’s strengths are portability and a generous queue cap. gVNIC’s strengths are Google-specific: a device co-designed with Andromeda, with its own DQO completion queues, header split, timestamps and access to Tier_1 bandwidth. Google ties all new machine series and high-bandwidth features to it. For any new deployment on Compute Engine, the practical question is no longer which NIC to pick. It is whether your image carries the GVNIC tag and a recent enough gve driver.
