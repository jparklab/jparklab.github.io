Use Cases for an MSSQL Proxy: What SQL Server Proxies Are Used For, Who Ships Them, and Where the Evidence Is Thin

A proxy that speaks SQL Server’s wire protocol (TDS) is used for six things: sharing backend connections, keeping clients connected through failover, splitting reads from writes, caching results, enforcing security and audit policy, and brokering identity. Managed proxies (AWS RDS Proxy, the Azure SQL gateway) cover pooling and failover. Commercial products cover read/write split, caching (Heimdall, ScaleArc, F5) and security (DataSunrise, Teleport). Open-source TDS proxies are small, partial projects. The engine and DNS already handle some of these jobs: availability group read-only routing, client-side driver pooling, and DNS aliases for migration cutover. That narrows the case for a proxy to workloads that can’t change their application code or connection strings. Almost all adoption evidence is vendor-published, and several of the strongest case studies concern PostgreSQL or SQL Server 2012-era deployments.

1. What an MSSQL Proxy Is

An MSSQL proxy is a process that accepts TDS connections from SQL Server clients on port 1433, or on a port of its choosing, and opens its own connections to one or more SQL Server backends. Because it terminates the client session, it can do things a network load balancer cannot. It can reuse a backend between clients, hold a client while the backend changes, inspect each batch, and refuse or rewrite what it sees.

The pattern is common inside SQL Server’s own cloud platforms. Azure SQL Database puts a gateway in front of every logical server. Clients connect to the gateway on port 1433, and depending on the connection policy the gateway either redirects or proxies the traffic to the right database cluster [1]. In Proxy mode all connections go through the gateway, which Microsoft says increases latency and reduces throughput. Microsoft recommends Redirect, where clients reach the node that hosts the database directly [1]. Azure SQL Managed Instance went further and made redirect the default in October 2025. It describes proxy as a legacy mechanism that trades performance for compatibility with TDS drivers older than 7.4 [2]. The platform vendor’s own guidance therefore treats a full-session proxy as a cost to minimize, not a feature. Third-party proxies have to justify that hop with functions the gateway lacks.

Proxies differ by how much of the protocol they understand:

2. Use Cases

2.1 Connection pooling and multiplexing

The most widely deployed use case is absorbing connection churn. AWS describes the target workload directly. Applications built on serverless functions, PHP or Ruby on Rails open and close database connections frequently. Establishing thousands of new connections consumes database resources that could otherwise process queries [5]. RDS Proxy keeps a pool of backend connections. It shares one database connection among many application connections when it is safe to do so, which helps applications with idle connections or long think time between transactions [5].

Pooling also gives the proxy an admission-control role. RDS Proxy queues or throttles application connections it cannot serve immediately from the pool. When connection requests exceed configured limits, it rejects them, which AWS explicitly calls shedding load [3]. Heimdall makes a similar claim. It establishes only as many backend connections as there are concurrent queries, and lets operators limit connections per user and in aggregate [7].

The limit on this use case is session state. A multiplexing proxy can reuse a backend only between transactions that leave no state behind. RDS Proxy pins a client to one backend connection for the rest of the session when it detects a state change that isn’t safe to share [6]. For SQL Server the pinning triggers include:

  • multiple active result sets (MARS) and distributed transaction coordinator (DTC) communication;
  • creating temporary tables, transactions, cursors or prepared statements;
  • a long list of SET statements;
  • any statement over 16 KB [6].

The proxy tracks a short list of settings, such as USE, SET ANSI_NULLS and SET TRANSACTION ISOLATION LEVEL, without pinning, and reuses connections only among sessions with matching values [6]. A SQL Server application that leans on temp tables, prepared statements or MARS will see little multiplexing.

2.2 High availability and failover hold

The second use case is hiding failover from clients. RDS Proxy connects to the standby instance after a Multi-AZ failure and preserves application connections [4]. It bypasses DNS caches, so clients don’t wait for a stale record to expire [5]. In an AWS test on one m5.xlarge instance, RDS Proxy improved failover time by up to 36% over the Always On listener endpoint, 59% over the RDS endpoint, and 83% over a database mirroring endpoint [5]. These are vendor numbers from a single instance class, and AWS notes that in-flight transactions may still have to be retried [5].

Commercial proxies built on the same idea. Heimdall queues front-end connections when it detects a failover and transparently moves them to the standby [7]. A ScaleArc case study describes a financial services company on SQL Server 2012 whose AlwaysOn and log-shipping setup made failover slow and error-prone. The company used ScaleArc as an abstraction layer to get automatic failover with zero application downtime, a migration path to SQL Server 2014 and multi-data-center DR. It reports DR testing cut from about two weeks to a few hours [13]. The customer is anonymous, the case study is vendor-hosted, and it describes a SQL Server 2012 deployment, so treat it as a historical example.

A plain L4 balancer does not provide this. One operator put HAProxy in front of two SQL Server 2019 AG nodes with round-robin balancing, and connections landed on the read-only secondary. The operator concluded that HAProxy does not know which node is primary [12]. A TDS-aware product solves this with a health check that asks the replica its role. F5’s MSSQL monitor can send SELECT role_desc ... FROM sys.dm_hadr_availability_replica_states WHERE is_local = 1 to find the primary [10].

2.3 Read/write split and query routing

Splitting reads to replicas without changing the application is the use case that statement-aware proxies sell hardest. Heimdall routes each query to the primary or a replica, accounting for replication lag and transactional state [7]. It addresses three problems developers otherwise face [8]:

  • reads issued right after a write can see stale data;
  • DNS caching can pile many connections onto one replica;
  • choosing the nearest reader in a global deployment is hard to code.

Its lag logic is concrete. With a 10-second lag window, a table last written 20 seconds ago can be read from the replica, while one written 5 seconds ago is read from the primary [9].

F5 BIG-IP takes a coarser approach for SQL Server. It routes by the user issuing the commands, using a pool flag for whether users can write by default plus a read-only or write-enabled user list [10]. F5 identifies a write request by keywords: create, update, insert, delete, into, alter, drop, rename, exec and execute [10]. Because exec counts as a write, every stored-procedure call goes to the primary. For SQL Server applications built on stored procedures, that severely limits what keyword routing can offload.

The baseline these products compete with is built into the engine. Since SQL Server 2016, an availability group listener routes connections that declare ApplicationIntent=ReadOnly to a readable secondary, and it can load-balance across a set of read-only replicas [11]. Native routing is per connection and depends on the client declaring intent. A proxy routes per statement and needs no change to the client. The proxy’s value is greatest when the connection string can’t be changed, such as with third-party applications, which Heimdall names as a target [7].

2.4 Result caching and SQL offload

Heimdall caches query results in a local heap or Redis, decides from its own analytics which queries to cache, and invalidates automatically without manual TTLs [7, 8]. Multiple proxies coordinate caching and invalidation, and scaling out means adding proxies [8]. The customer evidence comes from PostgreSQL rather than SQL Server. Questis, on Aurora PostgreSQL, estimated an in-house data-access layer at more than a year of work and chose Heimdall for read/write split, caching and analytics [9]. Tornado, a brokerage, chose it for out-of-the-box read/write split with zero application changes before a traffic launch [8]. Neither case study gives SQL Server numbers.

Not everyone accepts the premise. A Microsoft forum thread asked about SQL Server proxies for pooling, caching and read/write split. A respondent replied that pooling is a client-side mechanism and that SQL Server already caches data in its buffer pool [23]. The original poster answered that buffer-pool caching improves scalability but does not cut round-trip latency [23]. Proxy caching saves the network round trip and the engine’s work, but only for queries whose results can tolerate the invalidation rules.

2.5 Security: database firewall, masking and SQL injection blocking

Security vendors use the proxy position to enforce policy the engine does not. DataSunrise’s SQL Server firewall, in proxy mode, sits between clients and the database. It audits and logs traffic and blocks queries that violate policy [14]. DataSunrise claims it blocks several SQL injection techniques (out-of-band, time-delay, boolean, union and automated exploitation) on SQL Server 2005 and later [14]. The vendor runs three modes: sniffer (passive monitoring only), proxy (active protection, including the firewall and data masking) and database audit trail [15]. Blocking and masking need the proxy, because a passive observer cannot change a result set. These are vendor descriptions with no independent test behind them.

The open-source SQLumAI project shows how hard statement inspection is at the TDS level. It reassembles SQL Batch and RPC packets and recovers batch text. It applies rules with best-effort regex for simple INSERT and UPDATE statements and fails open, forwarding unchanged whatever it cannot parse [21]. It does not rewrite MERGE, CTEs or nested queries. It does not guarantee SQL_VARIANT, XML or table-valued parameters. It needs TLS termination, off by default, to read payloads at all [21]. Commercial firewalls face the same protocol, so how a product handles encrypted TDS and complex T-SQL is the first thing to test.

2.6 Audit and database activity monitoring for managed databases

Managed databases block the traditional way of auditing. Imperva notes that on-premises database activity monitoring relied on agents installed on database servers, and that a server-side agent is not practical on DBaaS because the cloud provider controls the host [16]. It names a database reverse proxy, working like a web application firewall, as one option. It adds that a reverse proxy brings back the operational burden a managed database was meant to remove [16]. DataSunrise’s audit-trail mode reads native audit logs, the non-proxy alternative [15]. A proxy is one of three ways to audit a managed SQL Server, alongside native audit logs and client-side agents. The cost of running it is the deciding factor.

2.7 Identity brokering and access control

A proxy can also translate identities. RDS Proxy can enforce IAM authentication for clients and connect to the database with IAM or credentials from Secrets Manager, so applications don’t embed passwords [3, 4]. Teleport’s Database Service joins the SQL Server’s Active Directory domain. It authenticates to SQL Server with Kerberos, using either a keytab or PKINIT certificates trusted by AD, and forwards user traffic after applying Teleport’s RBAC [17, 18]. This lets an organization give engineers short-lived, audited access to SQL Server without handing out SQL logins. Teleport’s enforcement is coarse for SQL Server. Its docs warn that database-name restrictions are only enforced for PostgreSQL, MongoDB and Cloud Spanner [18]. Access is controlled at the server and user level, not per database.

Identity support differs by product. RDS Proxy does not support connections that use Active Directory, and IAM authentication requires clients that support token properties [3]. F5 supports only basic authentication when proxying SQL Server, so user names and passwords must be synchronized across every backend [10]. DataSunrise says it supports Kerberos and LDAP for use as an authentication proxy [14].

2.8 Migration and cutover

A proxy that owns the client-facing address can move clients between backends. ScaleArc was sold partly as an upgrade path from SQL Server 2012 to 2014 [13]. Practitioners usually solve this without a proxy. Microsoft’s guidance for cutting over to Managed Instance is a DNS CNAME listener endpoint. Clients resolve one name, and cutover repoints the alias, with downtime bounded by the record’s TTL [19]. The approach has hard limits:

  • the on-premises server and Managed Instance must both listen on port 1433;
  • it cannot refer to a named instance such as SERVER01\INSTANCE01;
  • encrypted clients must set TrustServerCertificate=true [19].

A 2025 SQLServerCentral thread asked how to move a standalone named instance to an AG without changing connection strings. The answers were a SQL client alias, a DNS alias, or a load balancer placed in the connection strings for this and future moves. Named instances made redirection harder [20]. A TDS proxy is the general form of that load-balancer answer. It fits best where DNS aliasing fails: named instances, non-default ports, or the need to hold sessions during the switch.

2.9 Observability

Statement-aware proxies collect per-query data as a side effect. Heimdall reports cache hit rate, database processing time, overall response time and query plans [7]. Questis cited SQL performance analytics as one of three features it used [9]. ScaleArc’s customer credited its real-time analytics with finding query issues before users did [13]. No source showed observability alone justifying a proxy. It is a byproduct of deploying one for routing or caching.

2.10 Multi-tenancy

No source in this survey describes a SQL Server proxy deployed to route or isolate tenants. Per-user connection limits [7], per-user routing [10] and per-user RBAC [17, 18] are building blocks for it, but tenant routing as a deployed SQL Server proxy use case is not documented here.

4. Adoption Evidence and Limits

4.1 What the evidence shows

Adoption evidence for SQL Server specifically is thin and almost entirely vendor-published:

Evidence Engine Source type Strength
RDS Proxy failover improvements of 36%, 59% and 83% [5] SQL Server Vendor test, one instance class Moderate, measured but vendor-run
ScaleArc financial-services case study [13] SQL Server 2012 Vendor case study, anonymous customer Weak, dated
Questis: in-house build estimated at more than 1 year [9] Aurora PostgreSQL Customer-authored partner blog Moderate, but not SQL Server
Tornado: load tests handled several times prior load [8] Aurora PostgreSQL Customer quote in vendor blog Weak, not SQL Server
Forum demand for a SQL Server pooling/caching proxy [23] SQL Server Forum thread, 2021 Shows demand, no answer

In 2021 a user asked for any SQL Server proxy that handles front-side connections. The reply questioned whether such a thing was needed, and the only products named were ScaleArc and ProxySQL [23]. No independent benchmark of a SQL Server proxy turned up in this survey.

4.2 Limits that apply across products

  • Session state defeats multiplexing. SQL Server features that carry state (MARS, DTC, temp tables, cursors, prepared statements and many SET options) pin sessions [6]. A proxy’s pooling benefit depends on how the application uses the connection, not just how many connections there are.
  • Semantics can change. RDS Proxy warns that @@IDENTITY, @@ROWCOUNT and SCOPE_IDENTITY aren’t always accurate through the proxy, and that MARS connections skip initialization queries [3]. Anything that reuses backends risks this class of bug.
  • Identity gaps. Active Directory authentication, the norm in many SQL Server shops, is unsupported in RDS Proxy [3] and absent from F5’s proxy mode [10]. Teleport and DataSunrise support it [14, 17].
  • Protocol coverage. TDS has many packet types, data types and RPC forms. A partial parser has to fail open, as SQLumAI does, which weakens any security guarantee [21].
  • Extra hop. Microsoft’s own gateway guidance says proxying every packet increases latency and reduces throughput [1, 2].
  • Native alternatives. AG read-only routing [11], client-side driver pooling [23] and DNS aliases for cutover [19, 20] each remove one reason for a proxy.

5. Summary: Which Use Cases Justify a Proxy

Use case When a proxy is worth it Native or simpler alternative Products
Connection pooling / admission control High connection churn (serverless, PHP, Rails); need to cap and shed connections [3, 5] Client driver pooling when the app is long-lived [23] RDS Proxy, Heimdall
Failover hold Clients that fail badly on reconnect; DNS caching slows failover [5] AG listener with tuned timeouts [5, 11] RDS Proxy, Heimdall, ScaleArc
Read/write split App or connection string can’t be changed; need lag-aware per-statement routing [7, 9] ApplicationIntent=ReadOnly with AG read-only routing [11] Heimdall, F5
Result caching Read-heavy, rarely changing data; latency matters [8] Application cache; buffer pool for engine work [23] Heimdall
Firewall / masking / injection blocking Must change or block results inline [14, 15] Native audit, engine-level masking and permissions DataSunrise
Audit for managed SQL Server No host access for agents [16] Native audit logs [15, 16] DataSunrise, Imperva
Identity brokering Short-lived, centrally audited human access via AD [17, 18] SQL logins, AD groups Teleport, RDS Proxy (IAM)
Migration cutover Named instances, non-1433 ports, or sessions held during the switch [19, 20] DNS CNAME listener endpoint [19] ScaleArc, load balancer

The strongest cases are connection churn with admission control, and read/write split for applications whose code or connection strings can’t be changed. Those are where managed and commercial products ship real features and where native SQL Server has no per-statement equivalent. Security and identity proxies form a separate product family with their own justification: inline enforcement and access brokering that the engine cannot do on its own. Caching, observability, migration and multi-tenancy are secondary. Each is either a byproduct of a proxy deployed for another reason, served well enough by DNS or the engine, or undocumented for SQL Server. Anyone building a new TDS proxy should budget most of the engineering for session-state tracking and protocol coverage. These are the two places where existing products show their limits [6, 21].
