SQL Server has no feature named load shedding. By this report’s reading of section 3, boxed SQL Server (the self-hosted product, on-premises or on cloud VMs) ships no counter that refuses work on workers or running requests; its one instance-wide refusal is the static user connections ceiling, 17809 [1]. Azure SQL Database refuses new work at per-database worker and session counters, ends sessions that over-consume, and silently delays CPU, log rate and I/O [2, 3]. On boxed SQL Server, Resource Governor mostly delays work and aborts only on per-request or per-group budgets [4], and KILL remains a human emergency tool. RDS Proxy and ScaleArc refuse by connection count after a wait [5, 6, 7]. Callers can refuse without spending an engine worker, but no SQL Server outcome from those tools was found. Searches across eight vocabularies found no named customer organization describing how it refuses work to protect SQL Server; reported incidents show diagnosis, capacity changes and manual KILL.

1. What Load Shedding Means for SQL Server

1.1 The strict definition

Load shedding means deliberately refusing part of the incoming work as a server nears overload, so that accepted work can still finish. Amazon frames the purpose as preserving goodput, the throughput completed without error and fast enough to be useful [8]. Google defines the act, “Load shedding drops some proportion of load by dropping traffic as the server approaches overload conditions” [9], and treats graceful degradation as doing less work per request. Both warn that rejection has its own cost [8, 10].

Among vendor documents read, only AWS applies the word to a SQL Server path, saying RDS Proxy “rejects application connections (that is, it sheds load)” [5]. Microsoft’s pages speak of limits, governance and throttling [2, 4]. Three verbs cover the territory: refuse (work never starts), delay (work waits or runs slower) and kill (running work is ended). Andrew Baker’s stop-versus-slow split of Resource Governor is the closest SQL Server taxonomy, a recommendation reporting no deployment [11].

1.3 Queueing as the boxed default

A worker is the engine thread that executes a task, assigned only to an active request and released when the request is served [14]. A dbi services post compresses this to “Sleeping costs nothing, suspended costs a worker” [20]. When every worker is busy, new tasks wait on THREADPOOL; a login needs a worker too, so new connections then fail by timeout rather than refusal [14, 21]. Azure, whose governance is built on Resource Governor, refuses at a per-database counter set below physical exhaustion [2, 3]. By this report’s reading of section 3.1, boxed SQL Server ships none keyed to workers or running requests.

2. Overload Signals Used to Trigger Shedding

2.1 Signals by layer

An overload signal shows that work is arriving faster than it can finish. Two wait types dominate SQL Server guidance: THREADPOOL (a task waiting for a worker) and RESOURCE_SEMAPHORE (a query waiting for a memory grant). No published threshold or control loop that converts any signal into automatic refusal on customer-run SQL Server was found in the sources reviewed, which use them for diagnosis.

Signal Reader Documented caveat
In-flight count [22] Caller No view of other callers (design logic)
Pool exhaustion, SqlClient counters [23] Caller Can mean a leak, blocking or slow queries
Connection count, DatabaseConnectionsBorrowLatency [6, 8] Proxy Count is an imprecise load proxy
THREADPOOL; 60-second log message that queries were not picked up by a worker thread [24, 25] Operator Seen with at most 300 of 701 workers used, from memory over-commitment
Memory Grants Pending [26] Operator Says nothing about workers

sys.dm_user_db_resource_governance [2, 21] Azure operator Workers can far exceed requests under parallelism

Errors 10928, 10929, 40501 [2, 3] Caller Absent when CPU, log or I/O merely delay

2.2 Cautions and signal access

Practitioner thresholds are diagnostic: Erik Darling treats total THREADPOOL wait around 5% to 10% of uptime or more as a consistent problem [27]. Michael J. Swart, at an online-education company, watches User Connections against the ceiling [19], while Amazon concluded that maximum connections “was too imprecise to provide the complete answer” [8].

Shedding distorts its own telemetry: a service shedding 60 percent of traffic can show a flattering median latency, and shedding at the autoscaling CPU target can suppress scaling [8].

Workers process logins as well as queries [14], and sessions waiting on THREADPOOL have no session ID yet [27]. Tara Kizer reports monitoring tools failing to connect during the event [28]. No source draws the conclusion, but together these imply that a shedder hosted inside the engine is least reliable when most needed.

3. Shedding Inside the Engine

3.1 What each control does at its limit

Engine controls act after a connection reaches the server. Resource Governor classifies sessions into workload groups inside resource pools and applies per-group or per-request limits. Query Store hints attach options to one query without changing its text.

Control Action at limit Client sees

Logon trigger, custom rule [29, 30] Refuse session 17892, severity 14
Query governor, estimated cost [12] Refuse before execution 8649
Query Store hints, 2022 on [31] Cap grant or parallelism None
ABORT_QUERY_EXECUTION, 2025, named query [13, 31] Refuse execution 8778, severity 16
GROUP_MAX_REQUESTS [4, 21] Delay in wait state RESMGR_THROTTLED, no error
CAP_CPU_PERCENT, MAX_CPU_PERCENT [15] Delay None

REQUEST_MAX_MEMORY_GRANT_PERCENT, user groups [4] Lowers parallelism, then fails 8657

By inference from these rows, only the user connections ceiling refuses on an instance-wide count; only the memory grant queue and worker pool respond to instance load, by running out; logon triggers and watchdogs do so only if coded.

3.2 Resource Governor: containment and the worker pool

Microsoft documents that at the GROUP_MAX_REQUESTS limit “a session in that group can be created, but is placed in a wait state” [4]. No page read says whether that wait holds a worker. The one measurement found is a dbi services blog test on one SQL Server 2025 Standard lab with 2 vCPUs. There, 100 sessions into a group capped at 22 left 56 queued on RESMGR_THROTTLED and 123 active workers against 45 at rest, a difference of 78 that equals 22 in flight plus 56 queued [21]. Worker holding is probable, an inference from one lab; the 600-session test under this cap was not run [21]. Baker’s contrary claim, that a queued session holds “a connection and, when it eventually runs, a worker”, has no measurement behind it [11]. The author’s summary: “Resource Governor protects the service being called. It does not protect the instance” [21].

Microsoft’s announcement quotes Ola Hallengren of Saxo Bank crediting the feature with isolating trading workloads [32]. Baker argues that “Throttling is only safe when something else is guaranteed to end the work” [11]. Bob Dorr shows that a CPU cap’s forced wait stalls sessions sharing its state. A 1% capped user alone ran 192 transactions per second, an uncapped user alone 435 and the two together 240, while two uncapped users ran 920 and adding the capped user raised that to 1125; he calls it an edge case [15]. Containment of a known noisy workload has first-party and testimonial support; protection of the worker pool has none in the sources.

Raising max worker threads is the reverse of shedding, since it enlarges the queue; Microsoft says a shortage is probably not the real cause [18].

3.3 Refusing logins

A logon trigger is T-SQL that runs after authentication, the only native hook that can refuse a session on custom logic. Microsoft’s example denies a login above three sessions and warns that a trigger can lock out sysadmins [29]. The reserved admin connection is unaffected [30]. The DISA STIG (a US defense security baseline) for SQL Server 2022 requires per-user session limits, names a logon trigger as an example, and says limits at a web or application server alone are insufficient [33]. No source reviewed reports a logon trigger used to shed load.

The one field report concerns a security allowlist trigger: a 2016 SQLServerCentral poster saw innocent logins rejected in bursts at over 90% server CPU with no audit row, and the cause was never established [34]. The Resource Governor classifier cannot refuse, an inference from its return semantics. It yields a group name, failure lands in the default group, and slow logic can cause connection timeouts [35, 36].

3.4 KILL and Accelerated Database Recovery

KILL ends a session and rolls back its open work. Brent Ozar’s December 2025 sp_kill design, a kill procedure for people who would otherwise restart the server, proposed logging suggested kills by default and declining to act while a rollback has run about 30 seconds [17]. sp_kill shipped as a first draft in the April 2026 First Responder Kit for a client, in a release its author advised skipping for reliability, and gained @EmergencyMode in July 2026 [37, 38]. Those notes do not confirm the design rules shipped. Baker recommends, reporting no deployment, an Agent job every 30 seconds that kills listed logins’ requests past an elapsed-time limit, because SQL Server has no such control [11].

Accelerated Database Recovery (ADR) versions row changes so undo does not replay the log, and Microsoft states that “Transaction rollback is instantaneous, irrespective of the time that the transaction has been active or the number of updates that have been made” [39]. It is off by default on boxed SQL Server, always enabled in Azure SQL Database and Managed Instance, and needs an exclusive database lock to enable [39, 40]. No timed KILL with ADR on was found in the sources reviewed.

Case ADR Reported figure
SQLShack insert killed at about 3 minutes [41] Off / On Estimated 3567 s rollback / quick, no time given
SQLShack crash recovery [41] Off / On 1802 s / 12 s
Darling, version cleanup [42] On About 37 MB in about 21 min; about 75 MB in about 15 min
Straight Path client, SQL Server 2019 [43] Not stated 9-10 hours in rollback
dbi, KILL of a waiting session [21] Not applicable Worker freed at once

Darling’s formulation is “the ROLLBACK is instant, but cleanup isn’t” [42]. Microsoft warns that high abort rates pressure the version cleaner [39]; with Darling’s cleanup times, this implies that mass kills under ADR move cost to background cleanup, though no source measures one. Reading the 9-10 hour case as ADR-off is an inference from the default. By inference from the dbi result [21], waiting sessions are cheap to kill and read-only ones likely so, untimed in the sources. Writers are the disputed class.

3.5 The dedicated admin connection

The dedicated admin connection (DAC) reserves one sysadmin session per instance, local unless remote admin connections was enabled beforehand [44]. Microsoft qualifies it: “SQL Server makes every attempt to make DAC connect successfully, but under extreme situations it might not be successful” [44]. In the dbi lab the DAC answered while sqlcmd logins failed, at 556 active workers with 154 tasks queued on THREADPOOL, and KILL freed workers at once [21]. No published failure under starvation was found in the sources reviewed, weak evidence given how few tests exist. The single-session limit and sysadmin requirement jointly imply that a watchdog holding the DAC would occupy the only path an operator has [44]. The DAC is a recovery path, not automated shedding.

4. Shedding in Managed SQL Server Services

4.1 Service comparison

Managed services run the same engine family under provider-set limits. Azure SQL Database builds its governance on Resource Governor, extended with Windows Job Objects and File Server Resource Manager [2]. Its limits behave in three ways: admission rejection (“New requests are rejected when session or worker limits are reached, and clients receive an error message” [2]), per-session kill of running work, and silent delay. Around 2012 Microsoft announced a machine-level loop on SQL Azure: above 305 workers per machine, “the database with the highest requests per second is throttled” [45].

Service and behavior Effect Client sees, and limits
Azure worker and session counters [2, 3] Refused 10928, 10936; Resource ID 1 workers, 2 sessions; parallel plans reach the worker limit sooner
Azure server or engine throttling [3] Refused 10929, 40501, 49918
Azure outbound REST, 15% of workers, cap 175 [2, 21] Refused 10928, Resource ID 4; procedure page says 10%
Azure per-session: long transaction, tempdb, log space, memory [3] Killed 40549, 40551, 40552, 40553; 40552 is log space, not rate
Azure data size quota [2, 3] Growing writes refused 40544, elastic pools 1132; SELECT and DELETE continue
Azure CPU, log rate, I/O [2] Delayed Latency, governor waits, queued I/O stalls; no error number
Azure memory [2] Neither at the limit No error from reaching it; rare out-of-memory errors; fits none of the three
Managed Instance: 30000 sessions, 105 × vCores + 800 workers, user Resource Governor [4, 46] Capacity limits 10961 at CPU limit by default; no worker-exhaustion error named
RDS for SQL Server: Resource Governor, default-group grant 1 to 70 [36] As boxed, by inference Not documented; complex classifier can cause login delays

4.2 Refusal against queueing in one lab

On a 2-vCore Azure database, 100 sessions calling a 30-second endpoint produced 22 completions and 78 immediate 10928 rejections, leaving 128 of 150 workers free, while the boxed lab with a group capped at 22 served all 100 in waves ending at 150 s with no error [21]. The refusal came from Azure’s outbound-call cap (Resource ID 4) on serial requests; the general worker limit was not load-tested [21].

4.3 Managed Instance and RDS

AWS does not say what happens to over-limit requests on RDS, so queueing there is an inference from the shared engine and Microsoft’s wait-state wording [4, 36]. AWS warns a complex classifier can time out logins, including RDS automation sessions [36]. Managed Instance pairs fixed session and worker limits with user Resource Governor [4, 46]. The pages read establish no load-keyed rejection path on either service.

5. Shedding at Proxies and Gateways

5.1 Product comparison

A proxy sits between callers and the engine, so it can bound traffic without application changes, limited by how much of Tabular Data Stream (TDS, SQL Server’s wire protocol) it understands.

Product SQL Server position Excess handling
RDS Proxy [5, 6] RDS for SQL Server; not major version 2025 Queues or throttles, then rejects on connection limits; ConnectionBorrowTimeout 120 s default
ScaleArc, archived 2021 vendor article [7] Listed for SQL Server Surge queue, then “Connection timeout in Server Queue” after 60 s default
Envoy [47] No TDS on the page read Closes new TCP connections at accept on its own resource pressure
ProxySQL [48] Index lists MySQL, PostgreSQL, ClickHouse; no SQL Server section Not applicable
Heimdall [49] Marketplace listing names SQL Server Limit behavior could not be read

5.2 What the documented proxies do

Among proxies whose documentation was read, refusal is count-based and follows a wait, and none documents rejecting SQL Server statements on a load signal [5, 6, 7]. AWS advises keeping MaxConnectionsPercent at least 30% above recent peak usage, which treats it as headroom [6]. A queue longer than the client’s patience converts refusal into a client timeout: ScaleArc warns of this, and SqlClient’s Connect Timeout defaults to 15 seconds against ScaleArc’s 60 [7, 23].

Amazon treats proxy connection limits as a last resort and warns that surge queues can cause brownouts (partial service loss) because the server cannot tell how long a request waited [8]. That advice assumes a server able to shed on load, which by inference from section 3.1 the boxed product is not. RDS Proxy reuses database connections across client connections [5] and idle sessions hold no worker [14]. Together these imply that its cap nears a concurrency cap, except for pinned connections (held for one client) [6]. No source measures this for SQL Server, and none documents a proxy synthesizing a server-style error on load.

6. Shedding in the Application Tier

6.1 Tools

A refusal made in the calling application spends no engine worker. The vocabulary is the pool cap, the concurrency limiter (a bound on in-flight calls), the bulkhead (capacity isolated per dependency), the circuit breaker (which stops calling a failing dependency) and the retry budget (a cap on total retry volume).

Mechanism Action on excess SQL Server evidence
SqlClient pool, Max Pool Size 100 [23] Waits, then client exception at Connect Timeout, 15 s Default on; reported mainly as a leak signal
ASP.NET Core concurrency limiter [22] Rejects or queues; QueueLimit 0 disables queueing None found
Polly concurrency limiter [50] Example: 100 concurrent, queue of 50; RateLimiterRejectedException None found
Netflix priority shedding [51] Drops low-priority work past the autoscale target Not SQL Server
Semian bulkhead and breaker [52] Fails fast No SQL Server adapter listed
Google adaptive throttling and retry budget [10] Local drop once requests exceed twice accepts; stop retrying at 10% per client Not SQL Server

6.2 Pool caps and fleet arithmetic

The pool cap was not designed as a shedder, and its server-side budget is Max Pool Size multiplied by every pool in every application instance [23]. Swart describes hundreds of elastically scaled web servers approaching the ceiling [19]. As an illustration from documented defaults, six instances at the default pool size can present 600 active connections to a server with 4 or fewer logical CPUs, which has 512 default workers [14, 23].

No source reviewed publishes a limiter sizing for SQL Server. Reserved workers follow concurrent branches times runtime parallelism [18], which implies a request-count limit must allow for plan shape. ASP.NET Core counters live in each instance, multiplying the effective limit [22].

6.3 Limiters and breakers

Explicit limiters are documented and recommended, and no SQL Server outcome from them was found. During an infrastructure outage, Netflix’s Play API limiter let prefetch availability fall as low as 20% while user-initiated availability stayed above 99.4% [51]. Semian has run in production since October 2014 with adapters for mysql2, Redis, net_http, Trilogy and PostgreSQL; no SQL Server adapter is listed in the README [52]. Of calls to sp_invoke_external_rest_endpoint on boxed SQL Server, the dbi author writes “If you want the Azure behavior, the refusal has to come from the code that makes the call, or from the application in front of it” [21]. Applying this to general SQL Server work is this report’s inference, from one lab and no reported deployment.

7. How Rejection Reaches Clients over TDS

7.1 The ERROR token

A server-side refusal reaches the client as an ERROR token (value 0xAA) carrying Number, State, Class (severity), MsgText, ServerName, ProcName and LineNumber [53]. Class 17 covers running out of resources or exceeding an administrator-set limit, and classes 20 to 25 are fatal to the task, usually ending the connection [53]. Drivers decide retriability by error number [54, 55].

Outcome Number (severity) Surface; driver retry list
Azure cap, database [3, 54] 10928 (20) ERROR token; SqlClient
Azure cap, elastic pool [3, 54] 10936 (20) ERROR token; not in SqlClient lines read
Azure server too busy [3, 54] 10929 (20 database, 16 elastic-pool table) ERROR token; SqlClient
Azure service busy; not enough resources [3, 54, 55] 40501 (20); 49918 (16) ERROR token; SqlClient, JDBC
Azure session killed [3, 54] 40549, 40551 to 40553 (16) Session ends; not listed
Connection ceiling [1, 19, 54] 17809 (not stated) Handshake or network errors; not listed
Logon trigger [30, 54] 17892 (14) Login failure; not listed
Cost limit; budget aborts [4, 12, 16] 8649, 8657, 10961; 1138 (17) ERROR token; not listed [54]
Boxed worker exhaustion [20, 21] None Driver “Login timeout expired”
Query timeout [56] None Client exception after attention

Derived from Azure’s error table [3]:

  • Back off: 10928, 10936, 10929, 40501, 49918.
  • Reconnect: 40613, 40197 (severity 17, not load signals).
  • Stop retrying until the cause changes: 40544, 40549.

7.2 Asymmetry and its consequences

Azure’s refusal is machine-readable, while boxed saturation mostly surfaces as a driver timeout with no server number [20, 21]. Azure’s delay classes carry no code [2], so a limiter keyed only to error numbers reacts to counter-bounded overload alone. A severity-20 rejection generally ends the connection while a login needs a worker [2, 53]. By inference, a retry after 10928 or 40501 is probably a new login charged against the limit that refused it, which no source measures.

7.3 The retry contract

Published guidance is not uniform: the 40501 message says 10 seconds and Azure’s troubleshooting page says at least 5 seconds growing to 60 [3]. JDBC defaults to a single immediate retry with a 10-second connectRetryInterval for later attempts [55]. JDBC resiliency covers only the initial connection and idle restoration, and retryConn without a leading plus replaces the built-in list [55]. SqlClient’s blocking period after authentication failure, five seconds doubling to one minute, is the one anti-storm device found, and its Auto setting disables it for recognized Azure SQL endpoints [23]. None of these pages sets a budget across a fleet.

7.4 Attention and timeouts

A query timeout is client-side: the client sends an attention (a TDS cancel signal) and the server aborts at its next opportunity [56]. “An attention doesn’t rollback open transactions, and it doesn’t stop the currently executing query on a dime” [56], and a frozen client never sends one, so a query can finish after the deadline [57]. One traced cancel after about 10 s took about 45 s to answer because of rollback [57].

8. Production Experience and How the Layers Combine

8.1 What named accounts report

Public evidence comes as production accounts, vendor testimonials and labs, and few involve refusing work.

Source and evidence type What was done Refused on load?
Swart, 2020, production [19] Monitored connections, consolidated pools, shortened queries, offloaded reads No
Kizer, Straight Path client, 2023, production [25] Traced THREADPOOL to memory after asynchronous commit did not help; lowered memory settings No
Warren Departee, Straight Path client, 2025, anecdote [43] Client KILL, then waited out the rollback Manual kill
Nick Craver, Stack Overflow, production [58] Hunted a 150-connection pool that filled and never released Pool cap only, treated as a leak
Hallengren, Saxo Bank, vendor testimonial [32] Isolated workloads by CPU and memory No evidence of refusal
SQLServerCentral poster, 2016, forum [34] Allowlist trigger rejected innocent logins Unintended

No named customer organization’s account of refusing work to protect SQL Server was found. Searches used the vocabularies load shedding, THREADPOOL, max connections, Resource Governor, logon trigger, HAProxy throttling, Polly bulkhead and circuit breaker, and named-party queries (Saxo Bank, bwin, a SQLCAT customer, Stack Overflow). Microsoft’s 2012 account of its own throttling [45] is a platform operator’s. Stack Exchange could not be searched, and private runbooks and conference talks remain unchecked. Worker holding, KILL and DAC timing, and retry storms (including a 40501 query) had targeted searches. Control loops and limiter sizing rest only on the sources collected. Every absence stated in this report carries these limits. Public evidence shows what is available and recommended rather than what organizations run.

8.2 What fails

Observed failures are a 9-10 hour rollback [43], an allowlist trigger’s unexplained rejections [34] and monitoring tools unable to connect [28]. The one credited fix is Kizer’s memory-setting change [25]; Swart’s list reports no result [19]. Retry storms are well theorized; no SQL Server measurement was found. Google shows that if three layers each issue “3 retries (4 attempts)”, a single user action may create 64 attempts [9]. It adds that a 10% per-client retry ratio cuts growth from about 3x to 1.1x [10]. Microsoft’s generic pattern warns that aggressive retries “could further degrade a busy service” [59]. SQL Server accounts are qualitative, such as Kizer’s queries “all blocked, timing out and retrying” [28]. Google’s rationale for retrying assumes other tasks may be healthy and advises retrying only at the layer above the one rejecting [10]. A single primary offers no other task, so by inference the case for retry is weaker there.

8.3 How the layers would combine

No deployment in the sources reviewed assembles these layers for SQL Server. This arrangement is a design inference from Amazon’s layered-protection model [8] and the mechanisms above.

Control, in request order Protects against Support
Application limiter, short queue Worker exhaustion from known callers Documented; one outbound-call lab for the need [21, 22, 50]
Pool budgeted across the fleet Connection and login floods Production accounts [19, 23]
Retry budget at one layer Amplification Google, no SQL Server data [10]
Proxy cap, wait below client timeout Callers that cannot be changed Documented; default wait needs lowering [6, 7]
Resource Governor budgets, query governor Runaway statements Documented [4, 12]

The stack assumes a controlled caller fleet. On Azure SQL Database, callers can treat 10928, 10929 and 40501 as signals to back off and still need a latency signal for the delay classes [2, 3].

8.4 Open disagreements

On placement, Amazon favors decisions at the overloaded server [8], Google adds that callers must also throttle because rejection still costs the backend [10], and the dbi author places refusal for outbound REST calls in the calling code or application [21]. The STIG requires per-account limits in the database, not total sessions, because callers can connect by other means [33]. On goals, Amazon and Google design for overload [8, 9] while Kizer’s incident ended with a memory setting [25], and Swart argues both sides, calling connection exhaustion almost always a symptom but sometimes the root cause once other limits are cleared and demand keeps rising [19]. On Resource Governor, Saxo Bank’s containment testimonial [32] and the dbi worker count [21] answer different goals; the open point is worker holding, where Baker’s unmeasured claim [11] meets the dbi count [21].

8.5 Outlook

SQL Server 2025 extends Resource Governor to Standard edition and adds tempdb ceilings and ABORT_QUERY_EXECUTION [13, 16, 32], widening in-engine containment. sp_invoke_external_rest_endpoint, by contrast, held a worker per waiting call with no cap on boxed SQL Server in the one lab that measured it [21]. If slow outbound calls spread, worker exhaustion without a blocking chain becomes more likely and pressure for a load-reactive boxed counter would grow, a projection from one lab.

Four experiments would settle most of what is contested:

  • A per-task worker capture at a saturated GROUP_MAX_REQUESTS cap.
  • A timed KILL of a large writer with ADR on and off.
  • Repeated DAC attempts under full starvation.
  • A measured retry storm against 40501 with and without a budget.
