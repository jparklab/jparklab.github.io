mssql_proxy: architecture of the TDS network filter

A dynamic-module network filter that sits in front of tcp_proxy on the TDS 7.x filter chain. It either watches the TDS stream unchanged or terminates TLS on both legs, so it can read LOGIN7, apply a login policy, pick the backend cluster and authenticate Kerberos clients itself. Pick a mode to light its path; click any box for details.

Mode

One routed login, step by step

  1. PRELOGIN

    The client opens with PRELOGIN (0x12). With routing on, the bridge answers it itself and nothing reaches tcp_proxy yet. Without routing it is forwarded, with the client-certificate bit cleared.

  2. Client TLS handshake

    The TLS handshake travels inside PRELOGIN packets. The proxy is the TLS server here and presents its own certificate chain.

  3. LOGIN7 read

    LOGIN7 is decrypted and parsed: user, database, app, host, library and the SSPI token. The password is never decoded. The policy may refuse with error 18456 and close.

  4. Route

    The first matching route sets envoy.tcp_proxy.cluster. tcp_proxy, in ON_DOWNSTREAM_DATA mode, only connects now.

  5. Server leg

    The bridge sends PRELOGIN upstream, runs its own TLS handshake as the client and forwards LOGIN7. Toward a login-only server, only LOGIN7's first packet is encrypted.

  6. Login result

    The server's reply is scanned for LOGINACK or ERROR and the packet size. The verdict goes into dynamic metadata, and messages are re-encrypted per leg from then on.

Reference

Encryption per leg

  • None: plain TDS throughout.
  • Login-only (server ENCRYPTION=OFF): TLS handshake in PRELOGIN packets, the first LOGIN7 packet in one TLS record, then plain TDS both ways.
  • Full (ON or REQ): the handshake, then TLS records only.
  • With local PRELOGIN the two legs may differ; the bridge asks the server for at least login encryption.

Kerberos options

  • Unset: Kerberos logins are relayed unread.
  • read_ticket: the service keytab decrypts the ticket to learn the client principal; the AP-REQ goes on unchanged.
  • terminate · service_account: the proxy accepts the client with its own SPN, then logs in as its own account.
  • terminate · delegate: logs in as the client with a forwarded TGT, or with S4U2Proxy constrained delegation.

Config switches

  • no tls: ConnectionTracker only. Bytes are never changed.
  • tls: TlsBridge terminates both legs.
  • routing: local PRELOGIN; match on database, user, server_name, app_name, client_host, library or principal.
  • auth: deny list; NTLM pass_through, v2_only or deny; Kerberos mode.

What closes a connection

  • Malformed framing, or a unit that breaks the encryption mode: mssql_proxy_protocol_error.
  • A TLS failure on either leg.
  • A login the policy refuses: error 18456 + DONE is flushed first, then mssql_proxy_login_denied.
  • A stream that doesn't open with PRELOGIN is not closed: the filter goes passive and passes it through.

Outside the module

  • TDS 8.0 strict: starts with a TLS ClientHello, so tls_inspector sends it to a chain with only tcp_proxy. No routing or policy applies there.
  • Connection sharing: not possible with the v1.40.2 module ABI.
  • Forged LOGINACK: never; the client always gets the server's own reply.
